# Agent Note: 已持有组密钥的一端可以作为较大 Fingerprint 发起配对

Status: implemented

[English](2026-11-05-secret-holder-may-open-pairing.md) | 中文

## Problem

自动发现会建立连接，但自动配对的发起端仍只按 Fingerprint 顺序选择：较小的一端
总是拨号。这个规则对两台全新设备是正确的，却没有覆盖它本不该承担的场景。当较早
成员和较晚加入者互相看得见，但加入者的入站 TCP 端口不可达时，较早成员通常正是
较大的 Fingerprint。它因此拒绝拨号，而较小的加入者不断拨向无法应答的端口。两台
设备都保持可发现，却彼此离线。

## Decision

自动配对对全新配对仍保留 Fingerprint 顺序，并增加一条例外：已经持有组密钥的
设备，即使 Fingerprint 更大也可以发起开放配对，但只对名单外的对端成立。名单内的
对端仍沿用较小 Fingerprint 规则，因此配对完成到会话端口广播之间的窗口不会再发起
第二次握手。这个例外是安全的，因为两端已经共享密钥，或能按确定规则
合并密钥；开放配对不会为已有成员同时铸造两个互不相关的组密钥。该配对采用的名单
也是较早成员得知较晚加入者的途径，随后由发起端在实际可达的方向上拨出第一条会话。

`PairingService` 新增 `dialTransport` 接缝，理由与 `LinkManager.dialSocket` 相同：
测试需要让一个方向的配对拨号失败，而不削弱生产拨号。`LocalTransferController`
从构造函数透传它。

## Alternatives considered

**所有自动配对都保留 Fingerprint 顺序。** 否决：这正是缺陷。排序能防止全新配对
生成两个密钥，却也让已有成员在较晚加入者无法接收入站 TCP 时，无法使用唯一可达
方向。

**完全移除 Fingerprint 顺序。** 否决：两台全新设备可能同时发起开放配对并生成
互不相关的组密钥。在设备持有密钥之前，排序仍负责选出唯一发起端。

**保留规则并要求使用手动地址。** 否决：手动地址连接的是已知的会话端口，不是配对
监听端口，而且把本应由自动扫描完成的诊断交给用户。

**只改会话拨号。** 否决：缺失的事实是组成员关系和共享密钥，只有配对能恢复。先拨
会话端口无法让较早成员知道较晚加入者的存在。

## Consequences

- 自动发现到本机名单外的设备时，如果本机已持有组密钥，即使 Fingerprint 更大也能
  通过开放配对完成准入。
- 全新自动配对仍只有一个发起端，因此两个互不相关设备不会同时创建冲突的组密钥。
- 名单内的对端仍沿用较小 Fingerprint 规则并交给会话扫描；乱序配对不会把配对后
  窗口或重连竞争变成第二次握手。
- 接收端不变：仍会自动准入并确认有效的开放配对请求。
- `test/app/app_controller_test.dart` 覆盖入站被拦的场景：较小 Fingerprint 设备
  无法到达较大一端的配对或会话端口，而较大一端可以到达它，会话仍会建立。
