# Agent Note: A peer's disappearance is read, and the Pairing Secret is confirmed

Status: implemented

English | [中文](2026-09-30-peer-teardown-and-secret-confirmation.zh.md)

## Problem

构建 [LinkManager](../../architecture/2026-09-30-link-manager-owns-the-sockets.md) 时
需要下层真正提供两样东西，而为管理器写的测试把两处缺失都抓了出来：

**1. Session 从不知道自己那一端已经消失。** `SocketByteTransport` 用 `Socket.done`
来完成自身的 `done` future。在本平台实测：当**对端**关闭连接时该 future 永不完成——
它只在本地这一侧关闭套接字时才完成。一个探针（服务端接受连接、客户端调用 `destroy()`、
给每个可观察事件打时间戳）显示：读侧大约 1ms 就报出 `onDone`，而 `done` 在整个两秒窗口
内一直悬着；而当没有任何人读这个套接字时，则什么都不会报。于是 `SessionLost` 无法触发，
设备会一直显示一个早已不可达的对端。

**2. 与不持有 Pairing Secret 的对端也能建立 Session。** 握手交换 `hello` 与 `helloAck`，
用 X25519 交换结果与秘密派生密钥，然后返回。整个过程没有任何一步**检查**过双方派生出
了相同的密钥：使用两个不同的秘密时，双方都返回了 `SecureLink`，不匹配直到第一条真实
消息才以解密失败的形式浮现。把「Session 已建立」当作事实的调用方——传输引擎、剪贴板
镜像、LinkManager 都是——其实依赖了一件没人验证过的事。

## Decision

**传输完成信号改由读侧派生。** `SocketByteTransport` 在入站流结束或出错时完成 `done`，
同时保留 `close()` 与 `Socket.done` 作为额外的完成路径。其后果写在需要它的地方：dart:io
对没人读的套接字什么都不报，所以没有读者的传输无法察觉对端离开。本代码库里的每个消费方
都在读——只要 Session 存在，帧解码器就已订阅——因此没有任何逻辑依赖「不读」这一情形。

**握手在返回链路之前先确认秘密。** 派生出密钥后，双方各发送一条用握手派生密钥封装的
`SessionConfirmMessage`，并要求收到对方的同款消息。这条消息不携带任何数据：它的认证标签
就是全部载荷，因此持有不同秘密的对端无法产出能通过解密的记录。确认帧与后续 pump 使用
同一个帧迭代器读取——这是安全的，因为 pump 只在有人订阅时才启动，而那不可能发生在
`establish` 返回之前——并且它被握手消费掉，所以上层消费者永远看不到它。发现对方确认
无法解密的一方会立刻关闭传输，而不是等自己的超时：对方没有任何理由继续等待一个永远
不可能工作的 Session。

线上协议版本仍为 1。尚未发布任何东西，不存在需要互操作的已部署版本；确认步骤就是
已交付的 v1 握手的一部分。

## Alternatives considered

**保留延迟失败并把它写进文档。** 否决：「Session 存在」是整个上层依写的契约。一个建立
成功却连一条消息都送不出去的 Session 是谎言，它把每个调用方都变成特例，而且失败会以
解密错误的形式出现在某个无关传输上，而不是在连接的那一刻。

**给确认消息加载荷——版本标签，或发送方 Fingerprint。** 否决：标签需要有东西去比对，而
Fingerprint 握手时已经以未认证的形式携带过，并且在上面明确只是「声称」。不携带任何东西
的确认只有一种含义，也没有解析面。

**只在一侧确认。** 否决：那样只有 responder 能得知秘密不对，而 initiator 拿到一个首次
使用即死的 Session——问题只解决一半。

**用专门的帧类型而不是 wire 消息承载确认。** 否决：为了一帧不携带数据的东西，双方都得
再约定一套帧词汇；而且在那里每增加一种帧类型，都是敌对端可以多发一样东西。

**轮询套接字，或定期发保活包，来探测对端消失。** 否决：这是花流量和时间去回答 TCP 已经
回答了的问题。对端离开的瞬间，读侧就知道；bug 在于从错误的地方去读这个信号。

## Consequences

- `SessionLost` 在两个方向上都能及时、可靠地触发，包括对端进程被杀而非正常关闭的情形。
- 错误的 Pairing Secret 在握手中失败，错误信息点名秘密本身，且双方都失败。两个固定旧行为
  的既有测试——「不认识配对秘密的对端无法被理解」与「不同的配对秘密派生出不同的短串」——
  被替换为固定新行为的测试，因为旧行为已不复存在。
- 握手多一次往返：两条封装记录，各一个方向。对于一条将要传输文件的连接，这是噪声。
- 调用方如今只能靠消息文本区分「对端秘密不同」与「对端消失」；两者都是
  `HandshakeException`。这是刻意的——无法认证的对端与不存在的对端，对「我能和它说话吗」
  而言是同一个答案。
