# Agent Note: 两次改写都没能改倒的那个探针

Status: implemented

[English](2026-10-20-the-probe-that-survived-two-rewrites.md) | 中文

## Problem

连续两次发版，推了 tag，没有产出任何制品。

`v0.1.9` 与 `v0.1.10` 都过了版本号校验、Android APK 也打出来了，然后死在**同一处**：
Windows 打包脚本要验证 zip 里的 `app.so` 确实是当前代码编出来的，而那个验证找不到它自己要找的文案。

这个验证是有用的。`build/dist/*.zip` 不会自己更新，所以 `flutter test` 全绿说明不了 zip 里的东西 ——
本仓库出过一次「测试全绿、包还是旧的」：用户报「为什么别人打开是灰色的」，而对方装的二进制里根本没有那个修复。
所以脚本要在打包出来的 `app.so` 里搜新功能的那几句文案，搜不到就让这次打包失败。

问题出在这些文案是什么。那个清单里写死的是**中文句子本身**：

```powershell
$newProbes = @(
    '还没有对话。只要扫描到设备，它就会自动出现在这里，可以直接连接。',
    ...
)
```

PR #103 改写了其中一条消息 —— 「关于」页里那段说明这个程序做什么的文案（`aboutDescription`），
现在它要提到程序会按设定频率去问有没有新版本。句子变了，key 没变。包里装的是新句子，
脚本还在找旧句子，于是整条发布流水线永久变红。

**同样的事此前已经发生过一次。** 同一份文件里记着上一次：`conversationListEmpty` 与
`conversationPickOne` 的文案被改写，旧句子得手工换掉。清单上方那段注释写得很清楚：
*「这个列表是『必改项』：每加一个功能，把该功能独有的句子加进来，把被它替换掉的句子删掉。」*

而这条指示恰恰是它失败两次的原因。它在「开发者改一句措辞」与「发布能走通」之间放了一个手工步骤，
而这个步骤很容易忘 —— 它住在脚本里，离它关心的那句话隔着几个文件，忘了也不会有任何东西报错。
唯一会发现这件事的是发布流水线，而它的发现方式是「拒绝发布」。

所以代价不止一次发版失败：从 `v0.1.8` 之后什么都没有发出去，
而 `v0.1.9` 与 `v0.1.10` 两个 tag 就在 `master` 上，指着两个并不存在的发布。

## Decision

**探针清单存 l10n 词条 key，脚本去 `app_zh.arb` 里读当前的文案。**
清单搬到了 `scripts/packaging-probes.json`，按 key 点名：

```json
{ "probes": ["conversationListEmpty", "aboutDescription", ...] }
```

脚本拿每个 key 去 `lib/l10n/app_zh.arb` 里解析出**此刻**的文案，再拿它去搜 `app.so`。
于是改一句措辞不需要任何动作：key 没变，探针自己跟过去。

key 才是稳定的那一个。一个词条只有在真的离开产品时才该从清单里删掉 ——
而现在脚本会在那种情况下说出来，点名是哪个 key 没了，而不是打印一句没人能搜的中文。

**清单住在 JSON 里，不再内联在脚本里。** 内联数组只能用正则从脚本源码里抠出来，
而这份源码的注释里就有单引号（`'发送图片'` 探针**必须删掉**）。拿正则去读这样的源码，
就是等着被注释咬一口。JSON 由程序读，不靠模式。

**`test/process/packaging_probes_test.dart` 守住剩下的那部分判断力。**
`dart test` —— 那是任何一台开发机上都总能跑的那道门禁 —— 现在会检查：
清单里的每个 key 都在 `app_zh.arb` 里存在、没有一个带占位符（带占位符的词条在 `app.so` 里只剩片段）、
也没有哪一个出现在应用的另一个词条里。

最后一条正是旧注释用散文说过的那件事：像「对话」这种词也出现在「原生对话框」里，
所以找到它证明不了包里是哪个构建。本仓库在这件事上栽过一次。现在它是会失败的测试，
而不是注释里的一句提醒。

**长度不是判据。** 那道测试的第一版要求四个字以上，理由是短词证明不了什么。
这是错的：「离线」只有两个字，却只出现在整个应用的一个词条里，作为证明不比任何整句差。
真正要紧的是**有没有别的词条包含它**，所以测试查的就是这个。

## Alternatives considered

**再手工改一次探针，设计照旧。** 否决：同一个缺陷的第三次出现，而上一次就是同样方式修好的。
它能撑到下一次改写为止。

**既然老是它坏，就把探针检查删掉。** 否决，理由与
[第一次发版那篇 note](../process/2026-10-12-a-tag-builds-the-three-packages.md) 相同：
它是整个仓库里唯一在读**交付物本身**、而不是读产出它的那棵树的东西，
而且它已经抓到过两件真问题 —— 一句本该删掉的句子，以及一份不再被重新生成的图标字体。
包就是用户拿到的东西；打开它的校验是最后一道诚实的门。

**改成探 app.so 的哈希，而不是探它的文案。** 否决：哈希证明的是「和上一次不一样」，
不是「就是当前代码」。同一份源码构建两次会不一样，一份过期的包也会不一样 ——
只有在没人改任何东西时它才「一样」。

**把应用里的每个词都探一遍，于是清单永远不会过期。** 否决：那些词只在代码走得到的地方
才进 `app.so`，而一个编译进来却从不显示的词条根本不在里面可供寻找。
更重要的是，探针的全部价值在于它点名了**具体**的东西：那是有人刻意挑过的清单，
所以缺了一句时能报出它的名字。

**保留内联的句子，但由 ARB 生成那个文件。** 否决：这要加一个代码生成器和清单的第二个住处，
去解决一个「读一个 JSON 文件」就解决了的问题。

**把这项检查搬进 `release.yml`，而不是留在打包脚本里。** 否决：只有打包脚本手里有打包出来的
`app.so`，而 CI 跑的就是那个脚本、而不是它的第二套实现 —— 另起一条打包路径，
正是[打 tag 出三个包那篇 note](../process/2026-10-12-a-tag-builds-the-three-packages.md)当初要防的事。

## Consequences

- **改一句措辞不再牵动发布。** 探针跟着 key 走。
- **清单仍然是人的判断，但现在是被检查着的判断。** 不存在的 key、带占位符的 key、
  与别的词条相撞的 key，各自都会让 `dart test` 失败 —— 在开发机上，在打 tag 之前。
- **`scripts/packaging-probes.json` 是一个新文件、一种新格式。** 打包脚本与那道测试都读它，
  它是探针清单唯一住处。
- **门禁仍然看不见打包出来的制品。** `dart test` 检查的是探针清单**站得住**，
  不是包里**装着**它；最后那一步只有 Windows 构建做得了，而那正是发布流水线做的事。
  这篇 note 关掉的那个缺口是「改一句措辞就让发布变得不可能」，不是「包是旧的」那个。
- **`v0.1.9` 与 `v0.1.10` 仍然留在 `master` 上，指着两个并不存在的发布。**
  它们没有被移动、也没有被删除 —— 已发布的 tag 不可覆盖 —— 所以下一次发布是 `v0.1.11`，
  而那两个 tag 就是两次「准备好了却没发出去」的记录。
