# Agent Note: 对话行以地址作为主标题

Status: implemented

[English](2026-10-23-a-conversation-row-leads-with-its-address.md) | 中文

## Problem

对话列表原先用对端的主机名作为每一行的主标题。两台设备可能宣告相同的主机名，
而主机名也不能告诉用户自己准备联系的是局域网里的哪一台机器。地址本来就已经可用，
也出现在会话界面的其他位置，但列表却把信息量更小的事实放在了主标题上。

同一个列表还少走了一步。选中对话会在列表旁打开输入区，却把光标留在原来的位置。
用户选好对话后，下一步通常就是输入，因此还得再点一次输入框，让这次选择显得没有完成。

## Decision

对话行的主标题改为 `PeerView.address`。尚未被 Discovery 定位的对端没有地址，
此时回退到 `displayName`，避免出现空标题。行的测试查找键仍保留显示名；这个键用于
识别测试中的目标行，不是第二个可见标题。

列表搜索同时接受当前显示的地址和显示名，因此换掉标题不会让别名变得不可搜索。

选中一行时，页面在同一次状态变更里设置已有的输入框聚焦请求。`ConversationView`
把这个边沿传给 `ConversationComposer`，后者在帧结束后让自己的 `FocusNode`
请求焦点。复用这条路径，可以让焦点始终落到实际挂载的输入框上，包括切换对端导致
视图 key 变化的情况。

## Testing

对话列表的 widget 测试断言：有名称的对端，其行内包含地址，且不以别名作为标题。
选中行的测试会等待输入框的 `FocusNode` 在点击行之后获得焦点。

## Alternatives considered

**保留主机名作为标题，只在副标题里放地址。** 否：会碰撞的是主机名，而用于区分
用户正在选择的机器的是地址。

**把主机名和地址放在同一行。** 否：这一行本来只有两行的高度预算，把两个标识拼在
一起既会让主标题更难扫读，也没有消除促使这次修改的歧义。

**在页面上持有一个 `FocusNode` 供输入框使用。** 否：选中对端变化时输入框会重建，
页面持有的节点可能指向旧的输入框。现有的 `autoFocus` 从 false 到 true 的边沿绑定
在实际挂载的输入框上。

**把焦点留在选中的行上，依赖键盘导航。** 否：用户选中对话后要输入，而应用已有的
到达行为本来就把这次选择当成开始输入的邀请。

## Consequences

- 对话行用机器的网络身份作标签，而不是可能重复的名称。
- 没有发现地址的对端仍然有可读的标题。
- 搜索仍可按地址或显示名找到对端。
- 选中一行（包括已经选中的那一行）会把光标交给输入框，不需要第二次点击。
- 对有名称的对端，可见标题与测试查找键有意不同；需要表达「Bob 那一行」的测试
  使用 `ConversationRow.peer`。
