# Agent Note: 监听端口被系统保留时回退，而不是阻止启动

Status: implemented

[English](2026-10-22-reserved-listener-ports-fall-back.md) | 中文

## Problem

Windows 可能为 WinNAT、Hyper-V、WSL 或 Docker 保留一段 TCP 端口。即使没有任何
进程监听，绑定这段范围内的端口也会以 `WSAEACCES`（`errno = 10013`）失败。有一台
开发机保留了 `47622-47721`，会话端口 `47655` 和配对端口 `47656` 都在其中。已配对
设备启动时会绑定会话端口，于是 `SocketException` 从 `start()` 冒出来，应用没有
打开，直接显示了致命启动页；同一个保留范围还让配对监听器无法应答新的请求。

固定端口是有用的：只拿到地址的对端不用等待发现层，就能直接拨号。但它不值得让
整个应用在操作系统拒绝绑定时无法启动或无法配对。

## Decision

两个监听器都把非零的配置端口当作偏好。控制器先尝试请求的端口；如果绑定失败，
就在同一个监听器上绑定端口 `0`，并记录一条同时写明两个端口的提示。请求的端口
本来就是 `0` 时没有第二选择，因此失败仍然向上抛出。

会话端口的回退放在应用层，而不是 `LinkManager.serve`。`LinkManager` 保持字面
契约，控制器则拥有这项策略，也拥有必须广播实际端口的那层发现机制。
`manager.advertised` 和 `LinkManager.listenPort` 继续报告真正绑定的端口。

配对监听器采用同样的策略。`PairingService.receive` 仍然报告绑定失败，而不是
静默选择其他端口，所以显式选择端口的调用者仍能依赖返回结果。

发现报文里的 `DeviceDescriptor` 在会话端口之外新增可选的 `pairPort`。控制器用
配对监听器真正绑定的端口填充它，点击配对的流程拨这个值。不发送该字段的旧版
对端，或者没有在应答配对请求的对端，仍然回退到已知端口。

## Testing

`test/app/app_controller_test.dart` 用真实的 `ServerSocket` 占住端口。一条用例
让两台设备完成配对，再让其中一台把被占端口当作会话端口偏好重启，并检查它监听了
其他端口、提示写明了替换、发现层又把它接了回来。另一条用例用被占端口启动配对
监听器，检查回退提示，等待对端从发现层学到实际端口，并只凭主机地址完成配对。

`test/identity/identity_test.dart` 检查两个端口都能通过描述符的 JSON 往返，并检查
越界的配对端口会被拒绝。

双窗口端到端套件不再用发布配置里的固定配对端口，而是要一个属于自己的端口。
`flutter test` 会并行跑各个测试文件，另有文件会把整个 `LocalTransferApp` 立在
已知配对端口上，两者抢同一个端口，抢输的那个会挂掉一个本身没有毛病的测试。端口
填 `0` 就让这套件独占一个端口；对端仍然找得到主设备，因为主设备会说自己在哪里
应答。同一个竞争也是端到端套件在全量并行跑时偶发失败的原因。

Windows 打包冒烟检查的是应用真正占着的端口，而不是固定的那两个端口号。
GitHub 的 Windows runner 保留了 `47622-47721`，会话端口和配对端口都在其中，
于是那里的应用会回退 —— 回退本身是对的 —— 而断言 `47656` 会把这一次正确的回退
读成包坏了。冒烟检查要验的是两个 TCP 监听器和 UDP 发现套接字都在；端口号是多少，
那是系统的事。

## 变化的描述符不得重建发现服务

设备监听的两个端口不是同一时刻知道的。会话层先绑定，配对监听器之后才起，
所以控制器交给发现层的描述符，在服务已经起来之后至少会变一次。

这个变化过去会重建服务：在同一个 transport 上新建一个 `DiscoveryService`。
而 transport 的接收流是单订阅的，单订阅流不能被第二次监听 —— 就算第一次订阅
已经取消也不行。于是第二个服务从 `start()` 里抛出
`Bad state: Stream has already been listened to`。应用把它当成致命启动错误，
把所有监听器都关掉了，于是打包出来的应用只剩 UDP 套接字，两个 TCP 监听器一个
都没起来。

测试用的内存 transport 是广播的，而广播流可以被监听任意多次。所以内存 hub
根本暴露不出这个缺陷，只有真实的 socket 才会。

出路在于：变化的描述符描述的是**同一个**设备。指纹才是身份；名字、能力、
以及那些端口，是随着各层起来而变化的事实。所以新的描述符交给正在运行的服务，
由它重新编码广播报文并立刻广播出去 —— 对端不用等满一个广播周期才知道该往哪里
拨。每个设备在每个 transport 上只有一个服务，并且始终是它唯一的监听者。

`test/discovery/single_subscription_transport_test.dart` 把两半都钉住了：
在单订阅 transport 上再建一个服务会抛错；而把变化后的描述符交给正在运行的那个
服务，它会带着新端口继续运行。

## Consequences

- 首选端口被 Windows 保留或被其他进程占用时，已配对设备仍能启动并提供会话。
- 配对端口被保留时设备仍能应答；点击配对的对端会从发现层拿到替换端口。
- 发现报文和握手广播真正绑定的端口，因此自动重连和配对环境都不需要用户知道
  发生过回退。
- 设置页的提示会解释每次替换，而不是把它藏起来。
- 手动地址不填会话端口时仍默认使用 `47655`；发生回退后，用户需要填写应用显示的
  端口。
- 手动配对地址在发现层知道该主机时使用学到的配对端口，否则仍默认 `47656`。
- 发现层对每个设备只保留一个服务，端口或名字变化的设备仍以同一身份继续广播。

## Alternatives considered

**换一个固定默认端口** —— 这只是把冲突挪个位置。Windows 保留的范围是动态的，
不同机器上也不一样。

**固定端口绑定失败仍然视为致命错误** —— 这正是缺陷：一次本地端口保留就能让应用
完全打不开。

**始终绑定任意端口** —— 这样就放弃了「已经知道地址的对端可以不经过发现层直接拨号」
这个有用场景。

**启动应用前先停掉 WinNAT** —— 这是机器级绕行办法，会破坏 WSL、Hyper-V 和 Docker，
而且应用无法代替用户执行。

**让核心监听器静默回退** —— 核心层就不再执行调用者要求的事情，显式选择端口的
调用者也无法再依赖结果。控制器才是知道这个端口只是偏好、并且能广播替代端口
的那一层。

**把 transport 的接收流改成广播流** —— 那样第二个监听者就无害了，但真实的 UDP
socket 只有一个数据报流，在核心层里假装有另一条只会把问题藏起来。缺陷在于
重建了服务，而不在于 transport。
