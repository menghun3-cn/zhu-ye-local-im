# Agent Note: The README showed nothing

Status: implemented

English | [中文](2026-10-21-the-readme-showed-nothing.zh.md)

## Problem

The README on `master` showed six broken images and a development section that
read as a wall of diff text.

Two independent defects sat behind the report:

1. **The file was corrupt.** Commit `a975b4f` ("docs: update README to Chinese
   with screenshots") appended raw patch hunks instead of the file it meant to
   write. What shipped was 292 lines: a partial README, then six repeated
   blocks of literal `N + ` prefixed text, twice over. The two shell code
   fences were single-backticked (```` `sh ````), so Markdown rendered them as
   inline spans rather than as blocks.
2. **The images could never have loaded.** The README pointed at
   `design-preview/_shots/*.png`, and `.gitignore` ignores `design-preview/`.
   Those files are not in the repository, so GitHub served a 404 for every one
   of them.

The second defect has a precedent: `2026-10-13-the-hero-finally-shows-the-thing.md`
reached the same conclusion for the marketing site's hero image and **copied**
the binary into a tracked path rather than referencing the untracked one.

## Decision

**The README points at tracked images, and the images are generated by a
tracked script.**

- The pictures live in `docs/screenshots/` — conversation, devices, clipboard,
  transfers, settings. That directory is tracked, so a fresh clone of `master`
  has every image the README references.
- `tool/screenshots/capture_screenshots.dart` produces them. It drives the
  shipping widget tree over the shipping controller through the existing
  `test_flutter/support/ui_harness.dart`, so a picture cannot drift from the
  interface it shows. It is a script, not a test: it writes files, and a suite
  that rewrote the repository's own documentation on every run would be a
  suite nobody could trust to be green.
- The script lives under `tool/` rather than `test_flutter/`, so
  `flutter test test_flutter` does not run it. The gate that does run it is
  the one a maintainer runs by hand when the interface changes:
  `flutter test tool/screenshots/capture_screenshots.dart`.
- The README's development section now lists the gates the repository
  actually enforces — `dart test` for `test/` and `flutter test test_flutter`
  for `test_flutter/` — rather than the single `flutter test` that would
  discover neither the pure-Dart suite nor the widget suite correctly.
- The corrupt content is gone. The README is 58 lines: what the project is,
  five screenshots, and how to build and test it.

### What the pictures show

The capture harness is a test rig, and a test rig lies by omission unless it is
made to tell the truth about the two facts a reader would otherwise take away
wrongly:

- **A real LAN address, not a loopback one.** The in-memory discovery hub every
  `Device` shares in a test reports peers at `127.0.0.1`, because that is
  where the socket it speaks over lives. `AddressedBeaconTransport` re-reports
  every heard datagram at `192.168.1.115`, so the address in the picture is
  one a LAN tool could actually show.
- **A plausible folder, not the harness's temporary one.** The settings
  surface would otherwise display
  `C:\Users\admin\AppData\Local\Temp\local-transfer-shot-52ea63b4`, which is a
  fact about a test run rather than about the product.

The device names, addresses and ports in the pictures are examples, and the
README says so.

## Testing

- `flutter test tool/screenshots/capture_screenshots.dart` completes and writes
  five PNGs. Each was opened and read: every surface draws its Chinese text
  with real glyphs, the conversation shows a text bubble, a file bubble and an
  image bubble, and the picture in it is decoded rather than left as a
  placeholder.
- The six gates pass, unchanged by the README itself.

## Alternatives considered

**Referring to `design-preview/_shots/` and adding a `.gitignore` exception for
it.** Rejected: that directory is a design workspace — annotation layers,
scratch files, drafts — and tracking all of it to reach six images would put
workbench state in the repository. The site already decided this question
against the same directory.

**Hand-cropping five images out of `design-preview/` and committing those.**
Rejected for the same reason the hero was copied rather than referenced, and
for a second one: a crop is made once and never refreshed, so the pictures
would show an interface that drifts further from the real one with every
release. A script that drives the shipping tree cannot drift.

**Keeping the capture under `test_flutter/` as a test.** Rejected: it writes
five PNGs into the repository on every run, which makes the working tree dirty
after every `flutter test test_flutter` and makes the gate's green/red state
depend on a side effect. It stays a script, invoked by hand.

**Pointing the README at the released installer's screenshots.** Rejected:
there are none, and inventing a place for them would be a second place to
keep in step.

## Consequences

**Bought.** The README on `master` shows its pictures, the development section
is readable, and the images can be regenerated by one command when the
interface changes.

**Given up.** The repository now carries five binary assets, and the capture
script is one more thing that can go stale — a maintainer who changes the
interface and does not re-run the script ships pictures of the old interface.
The README says how to regenerate them, but nothing enforces it.

**Owed.** The capture depends on Windows font paths and on a fixed LAN address
(`192.168.1.115`); it runs on the machine that ran it, and on a machine with a
different address the pictures would show a different one.
