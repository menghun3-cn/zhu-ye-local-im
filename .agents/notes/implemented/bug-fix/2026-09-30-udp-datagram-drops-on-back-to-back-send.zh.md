# Agent Note: The UDP transport re-sends a datagram the socket refused

Status: implemented

English | [中文](2026-09-30-udp-datagram-drops-on-back-to-back-send.zh.md)

## Problem

[`UdpBeaconTransport`](../../../../lib/core/discovery/udp_beacon_transport.dart)
把每个数据报都直接交给 `RawDatagramSocket.send`，并忽略它返回了什么。而这个返回值
是 UDP 发送方唯一的信号：`send` 返回它实际收下的字节数，**当套接字还有一次写入在途
时返回 0**。数据报套接字一次只收一个数据报，因此落在这个窗口里的第二次 `send` 既不会
排队、也不会响亮地失败——它返回 0，数据报就此消失。没有错误，也没有可等待的完成回调。

这一层里有两条路径会背靠背发送，且都属于常态而非罕见：

- `broadcast` 对每个目标各做一次 `send`。`defaultBroadcastTargets` 返回受限广播地址
  **加上**每个子网的定向广播地址，在任何有真实网卡的机器上都是两个或更多——而这份重复
  是刻意的，因为有些接入点只转发其中之一。被丢掉的就是第一个之后的每一个目标。
- `DiscoveryService` 会应答探测包，而在公告定时器触发的那一拍里，可能同时到达两个探测包。

这个失效从外部完全看不出来。信标根本没发出去，于是对端就是发现不了：没有日志、没有异常，
一台明明在场的设备会一直从列表里缺席，直到它下一次公告恰好落在一个空窗口里。

因此它表现成这类缺陷一贯的样子——**偶发的测试**。
[`udp_beacon_transport_test.dart`](../../../../test/discovery/udp_beacon_transport_test.dart)
的「a malformed datagram is dropped and the receive loop survives」在一次全量运行中失败过
一次，而每次单独重跑都通过。对裸套接字做的探针点出了元凶：一轮里连发三个数据报并打印
`send` 的返回值，得到 `[1, 0, 0]`；而一个除了 `send` 什么都不做的循环，在多数轮次里只
交付了第一个数据报。

第一个假设错在了线的另一头。排空**接收**侧（`while ((datagram = receive()) != null)`）
是救回丢包的常规做法，但它什么也没改变——一个对照探针仍然丢了 900 个中的 59 个。这些
数据报根本就没到过。

## Decision

**传输层把待发数据报排队，并把套接字拒收的那个再发一次。** `send` 与 `broadcast` 将
数据报压入一个 outbox；一个排空循环取出最旧的那个交给套接字，当 `send` 报告写满了整份
长度就把它移除，否则等待一毫秒后把**同一个**数据报再交一次。于是发送被串行化了，而对
调用方没有任何可见变化：接口仍是同步的、队列保持顺序、每个数据报最终都会发出。

数据报在入队时会被拷贝一份，因此调用方可以继续复用自己的缓冲区——`DiscoveryService`
就是拿同一份 `_announceBytes` 发给每个目标、以及每个探测者的。

`close` 丢弃仍在队列里的内容。套接字在发送时抛异常则清空队列并停止排空，因为那时
`send` 早已返回，已经没有任何调用方可供告知。

## Testing

`udp_beacon_transport_test.dart` 里的两个用例把这一行为钉住，且在没有修复时都会失败：

- 「every datagram in a burst is delivered」预先把 32 个信标编码好，然后循环里除了
  `send` 什么都不做。在两次 send 之间做编码会掩盖那个窗口——构造一个信标所花的时间足够
  上一次写入完成——所以这个循环必须是赤裸的，缺陷才会显形。这同样解释了为什么这里需要
  新增用例，而不是把断言加到既有用例上。
- 「a broadcast sends to every target, not only the first」向两个解析为同一地址的目标
  广播十轮，因为两个套接字无法共用一个 UDP 端口；被检验的是「每个目标各做一次 `send`」。

那个窗口只有几百微秒宽，因此单轮可能侥幸溜过；两个用例于是都重复到必然命中为止。对整个
测试文件反复运行测得：修复前 4/4 轮失败，修复后 5/5 轮通过。

## Alternatives considered

**用 `while ((datagram = receive()) != null)` 循环排空接收侧。** 依据实测否决：一个在
每次事件里排空所有可用数据报的探针仍然丢了 900 个中的 59 个，并不比不排空时的 51 个更好。
损耗在发送侧，那里唯一的证据就是返回值，而 `receive` 报告不了它。之所以记下来，是因为
这是任何人首先会去抓的那根稻草。

**等待 `RawSocketEvent.write`，每个事件发一个数据报。** 否决：该事件是一次性的。五轮实测
显示它在 bind 之后 0–7 毫秒内恰好触发一次，此后无论有多少数据报完成都不再触发——因此
事件驱动的排空在第一个数据报之后就会停滞。

**就地重试，不排队。** 否决：`send` 是同步的、无法 await，而自旋到套接字空闲会阻塞那个
负责完成写入的事件循环。那是活锁，不是重试。

**把 `send` 与 `broadcast` 改成异步，让调用方 await 投递。** 否决：`DiscoveryService`
的 `announce` 与 `probe` 由定时器和到达的数据报驱动，两者都与结果无关，接口会因此长出
一个唯一消费者直接丢弃的 `Future`。队列把投递保证放在拒收发生的地方，同时让契约保持
`void`。

**用 `Future.delayed(Duration.zero)` 退避。** 依据实测否决：零延迟下重试仍然丢了 200 轮
中的 2 轮，因为写入在几十微秒内完成，而零时长定时器并不能可靠地等到那么久。一毫秒下
200 轮丢失 0 轮，最多重试两次。

## Consequences

- 曾被丢掉的信标现在能送达了。发现过程不再取决于第二个广播目标是否恰好赢了那场竞态，
  而 `defaultBroadcastTargets` 里那份重复本来正是为此存在的。
- 套接字忙时，传输层会持有一个小队列和一个一毫秒定时器。套接字空闲时不产生任何等待，
  而这是常态；一个数据报至多付上前一个所需的几十微秒。
- [`BeaconTransport`](../../../../lib/core/discovery/beacon_transport.dart) 的 `send`
  与 `broadcast` 现在写明了此前只是隐含、且从未被检查的契约：投递是异步的、并且应当
  发生；而「广播」意味着每个目标，而不是恰好吃到第一个的那个。这条缺失的契约正是缺陷
  溜进来的方式——接口什么都没承诺，于是什么都没被验证。
- 顺序此前没有承诺、现在也没有承诺，但队列让它在**经由同一个传输层发送**时实际上成立。
- 全量测试作为门禁重新可信了：暴露出这个问题的偶发失败不再偶发。而「flaky」从来就是这个
  意思——代码在每一次运行里都是错的，只是有时才可观测。
