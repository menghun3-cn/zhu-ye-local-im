# Agent Note: 设备改名后，已连接的对端仍显示旧名

Status: implemented

## Problem

给设备改名，传不到**已经连上它的**那些设备那里。`peers` 构建每一行时会把四个知识来源
合并起来，让后写的来源覆盖先写的：Owner Group、记住的 Known Device 记录、Discovery，
最后是活着的 Session。而最后这一项带来的名字来自
`session.handshake.device.alias` —— 握手是一次**快照**：对端在 Session 建立的那一刻
自报的描述符，而它在这条 Session 活着的整个期间**不会变**。这不是实现的疏漏，`rename`
的文档里就把它写成「改名要付出名下所有 Session 的代价」的理由。

后果是：只要对端还持有一条指向改名方的 Session，它就一直画旧名字，而且会一直画到那条
Session 消失为止 —— 一条悄悄变成半死的 Session，可以拖到无限久。给笔记本改名，正在跟它
说话的手机就一直用旧名字叫它。

症状表现为一个偶尔失败的用例：`renaming keeps the group and changes what is
announced`。它被看见过两次，两次都被记成「环境敏感」，依据是底下做配对的是真的 loopback
TCP。它不敏感。它就是这个 bug：断言成不成立，取决于 Bob 那条 Session 恰好在 Alice 下一
个 beacon 到达**之前**掉没掉。红色才是真相，而它被放过了两次。

## Decision

**让这四个来源按「谁知道的更多」排序，而不是按它们恰好被应用的顺序。**
`_PeerFacts` 新增 `fromDiscovery`，在 Discovery 那一轮布置设备时置位。于是 Session 那一轮
**只在 Discovery 对这个设备无话可说时**（比如它只被手工地址拨过、从没在链路上出现过）
才提供 `alias` 和 `platform`。Session 提供的其它一切原样不动：它实际运行的那个地址、
session 端口、以及「对端是连着的」。活着的 Session 仍然是**对端在哪里**的权威；它只是
不再是**对端叫什么**的权威。

让这条规则成立的判据是新鲜度，而且差距不小：beacon 每三秒重发一次，带的是对端**当前**
的名字；握手只采集一次，两者中较旧的那个可以老到等于设备的开机时长。两者都存在时，
beacon 才是答案。

**改成调换循环顺序则是错的，而这一点值得记住。** 把整个 Session 循环挪到 Discovery 循环
之前，也会把 Session 的 `address` 放到最后 —— 而那是一条当时**特意**放上去、并在原位写了
文档的规则：Discovery 可能重启过，Known Device 记录可能压根没写过，但一条活着的 Session
才是对端**确凿所在**的地方。优先级必须**逐字段**不同，这正是那个标记所记录的东西。

## Alternatives considered

**对握手里的 alias 用 `??=`，只补空缺。** 更简单 —— 不用新字段 —— 但把错的一对拿来排序。
它要补的那个字段早已经被记住的 Known Device 记录填上了，而那条记录是配对时写下的、
可以有几个月的年纪。于是这是拿「几分钟前的握手名字」换「几个月前的记忆名字」。那条记忆
记录恰恰是 Discovery 只要看到对端在链路上就会覆盖掉的东西，而这个改法会在 Discovery
根本看不见对端的那种情况下，把名字交还给记忆。

**干脆不再从握手里读名字。** 那么只被手工地址拨过的对端 —— 按定义 Discovery 从没布置过
它 —— 就没有名字可显示，只能退回指纹，尽管握手明明带着它的名字。这是为了修一个不成立的
情况，去弄坏一个今天能用的。

**改名时重新握手，或者刷新 Session 的描述符。** 没有可挂的事件：握手只在 Session 建立时
发生一次。为了一件外观上的改动去发明一种重做它的办法，等于重新打开一次已认证的交换。

**把改名当成一条独立的消息放到线上广播。** 新增一种 beacon kind 或一条控制消息，去传达
Discovery 每三秒本来就在广播的东西。为显示细节做协议改动，而且给一个**已经有**单一事实
来源的名字再加上第二个。

**把 Session 循环挪到 Discovery 循环之前。** 名字修好了，地址坏了。单独列出来，是因为它
是这个改动看起来最像的那一版。

**放松这条测试 —— 接受两个名字之一，或者把超时加长。** 这正是产出两轮「环境敏感」的形状。
这条断言从头到尾都是对的；放松它会把一个真 bug 变成永久且看不见的东西。

## Consequences

**改名现在在一个广播周期内就传开，而不是等到下次重连。** 对端的 beacon 带着新名字，而
再没有东西压得住它，所以对面最多三秒就更新。在此之前，已连接的对端可以顶着旧名字一直到
那条 Session 消失。

**只被手工地址拨过的设备，仍然显示握手时说的名字。** 行为不变，而且是对的：那是人们唯一
有的名字。

**Session 刚建立的几秒内，名字仍由握手提供**，直到第一个 beacon 落地。与改动前相同，而且
两者在实践中一致 —— 握手用的就是那个对端当前正在广播的描述符，除非它中间改了名。

**传输层与 Session 层一点没动。** 这是一条 getter 内部的优先级规则，在本来就负责「该画
什么」的那一层。

## Testing

`test/app/app_controller_test.dart` 的「renaming keeps the group and changes what is
announced」就是回归用例，而它的断言一个字都不用改 —— 要改的只是它的名声。它被证明是
**既有失败**而非在途改动引入的，办法是用 `git archive` 把干净的 `HEAD` 导出到一个一次性
目录、在那里跑同一条用例，失败得一模一样；这套手法不碰任何工作树，也不涉及切分支。

这条测试现在带了一条注释，点名它的机制，因为它失败的方式恰恰就是它被两次解释掉的方式：
断言变绿还是变红，取决于 Bob 那条 Session 是否在 Alice 下一个 beacon 之前掉线，所以
「有时红」听起来像时序噪声。不是 —— 红的那一种，正是过期的握手压住了活着的 beacon，也
正是这个 bug。修完之后，无论那条 Session 走向如何，只要 beacon 到达断言就成立。

另外用一份一次性、加了打印的同类用例手工确认过：这两种情形是真的不同，而不是「碰巧都过」。
修好之后，Bob 的列表在那条过期 Session 还在的时候就自己更正了；没修之前，列表全程顶着
旧名字，直到 Session 结束。
