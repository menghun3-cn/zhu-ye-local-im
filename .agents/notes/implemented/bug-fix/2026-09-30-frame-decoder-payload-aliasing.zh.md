# Agent Note: A decoded frame owns its bytes, not the decoder's buffer

Status: implemented

English | [中文](2026-09-30-frame-decoder-payload-aliasing.zh.md)

## Problem

[`FrameDecoder`](../../../../lib/core/protocol/frame.dart) 把每一个帧都在同一个可增长
缓冲区里重组，并在连接存续期间复用该缓冲区，而 `next()` 交出的载荷是**指向该缓冲区的
视图**（`Uint8List.sublistView`）。这个缓冲区并非只追加：一旦某个帧够长，`_compact()`
就会把存活的尾部整体下移，盖到那个帧刚用过的字节上。于是仍引用着这些字节的帧，载荷会
在它脚下被改写。

这不是理论风险：传输路径每个分片发 512 KiB，而一次真实的套接字读经常交付一整条记录
**外加下一帧的头几个字节**。一次 `add()` 把两者都放进缓冲区，随后的第一个 `next()`
解码完那条大记录、把游标推过它，然后——因为下一帧的开头字节已经在缓冲区里——执行那次
把它们搬到偏移 0 的 compaction。而偏移 0 正是这条记录的 nonce 与密文起始处所在的位置。
于是这条记录带着另一个 nonce 返回，ChaCha20-Poly1305 认证失败，把 pump 一起带走。

它表现得像「偶发」而不是像 bug：大记录是否与下一帧共享同一次读，取决于套接字时序，因此
`test/security/secure_link_test.dart` 的「over a real socket handshake, control
message and bulk bytes all arrive」时而通过时而失败。单独重跑该用例得到一次失败、一次
通过——一个以真实套接字为对象的测试出现这种间歇性，才把注意力从测试本身引向解码器。

## Decision

**`next()` 把帧的载荷从读缓冲区拷出来。** 返回的帧拥有自己的字节，因此解码器此后可以
自由地增长、追加与压实该缓冲区：已经交出去的东西不再指向它。各解码辅助函数仍以视图
构造字段——`ChunkFrame.data`、`SealedFrame.nonce`、`SealedFrame.cipherText`——但它们
现在指向的是这份自有载荷，而它不会再被写入。

这条不变量写在 `FrameDecoder` 自身之上，这样下一个新增帧种类的人只需要满足一条规则，
而不必去重建某种「每个辅助函数各自的约定」。

线上格式没有任何变化，协议版本仍为 1。

## Testing

`test/protocol/frame_test.dart` 的「decoder buffer reuse」组里有两个用例，在下一帧的首
字节已经进入缓冲区的情况下解码一个 512 KiB 的帧，一个是 sealed，一个是 chunk。有这次
拷贝时它们通过；去掉拷贝后，sealed 那个用例报告的 nonce 变为 `{"t":"after"`——即下一帧
的字节——于是这条回归直接点名损坏本身，而不是在好几层之上以一个看起来像「配对秘密不对」
的认证错误浮出来。

## Alternatives considered

**让 `_compact()` 改为分配一个新缓冲区，而不是原地 memmove。** 否决：它单靠自己并不能
堵住这个洞。`_start == _end` 那条路径同样会把游标归零而什么都不搬，随后的 `add()` 就会
写在偏移 0——盖住刚刚交出去那一帧的字节。要堵住两条路径，就意味着每次缓冲区排空都得分配
一个新缓冲区，而请求/响应式协议里这是最常见的情形；付出这个代价，只为省掉一次仅对批量
帧才有意义的拷贝。

**只在帧确实保留视图的地方拷贝——`ChunkFrame.data`、`SealedFrame.nonce`、
`SealedFrame.cipherText`——不动 `next()`。** 否决：它把「这一帧是否拥有自己的字节」
变成每个解码辅助函数都要被逐一审计的性质，而某个后来开始保留视图的辅助函数照样能编译
通过。它唯一省下的是每条控制消息的一次拷贝，也就是几十字节——因为 chunk 与 sealed 帧
两种写法都只付一次拷贝。

**让调用方在推进解码器之前自己拷贝所需内容。** 否决：调用方能遵循的那条规则本身就是错的。
损坏发生在**交出该帧的那一次** `next()` 内部，而不在之后的某次调用里，所以任何调用方纪律
都躲不开——帧到达时就已经是坏的。

**把这种别名关系作为已知约束写进文档。** 否决，理由相同：一条无法被遵守的约束，就是一个
带注释的 bug。它还不得不一路穿透 `SecureLink`（其 pump 会跨着解密那个 `await` 持有帧），
以及未来每一个在解码器再次推进之前触碰某块分片字节的消费者。

## Consequences

- 帧是持久的。框架层不再有任何隐藏的「有效期到某时」窗口，这个类也不再依赖调用方及时
  消费每一个帧——而那是任何消费者都无法被指望长期保持的性质。
- 解码路径上每次多出一次 memcpy。对一条批量记录而言，这与 `SecureLink` 在组装记录的密文
  与标签时所做的那次拷贝同量级；对一条控制消息而言是几十字节。
- 暴露该缺陷的那个 `secure_link_test` 用例不再时好时坏。它此前被记为 flaky，而「偶发」
  正是掩盖这类缺陷的失效模式：代码在每一次运行里都是错的，只是有时才可观测。
