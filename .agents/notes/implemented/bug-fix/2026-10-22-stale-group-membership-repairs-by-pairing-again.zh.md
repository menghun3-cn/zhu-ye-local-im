# Agent Note: 陈旧的设备组成员关系通过重新配对恢复

Status: implemented

[English](2026-10-22-stale-group-membership-repairs-by-pairing-again.md) | 中文

## Problem

设备组成员关系和组密钥会一起持久化，但对端仍可能只保留了一次配对的其中一半。
例如，一台设备记得另一台设备是组成员，而后者已经丢失组密钥。后者因此会关闭
会话监听，也不再广播会话端口；前者仍看到 `isInGroup == true`，所以不会提供
普通的「配对」操作，同时又因为没有可拨号的端口而不能提供「连接」。对话行因此
变成死路：自动重连持续失败，用户也看不到修复关系的入口。

## Decision

对话行现在区分三种操作：连接、配对和重新配对。如果对端已在本机设备组中、
有已知地址，但没有广播会话端口，就显示「重新配对」。该操作复用现有的点击配对
对话框，因此仍由受控的配对交换恢复缺失密钥；本机不会直接修改成员关系或密钥。

「连接」仍要求对端既在组内，又有可拨号的会话端口。「配对」仍只用于已经发现、
但不在组内的设备。已经属于设备组、却既没有地址也没有端口的对端仍不可操作，
因为界面不知道应向哪里发送配对请求。

## Testing

组件回归测试先配对两台设备，再删除其中一台已保存的 `session.groupSecret`，
用各自的同一份 profile 重启两台设备，然后打开另一台的对话列表。两台都重启，
是为了让陈旧成员关系的断言不再依赖旧会话要等多久才超时。测试断言没有密钥的
设备仍被列为组成员且没有会话端口，并断言其对话行提供「重新配对」，而不是
「连接」或「配对」。

## Alternatives considered

**发现没有广播会话端口时自动移除陈旧成员。** 否决：缺少端口也可能是已配对设备
正在启动时的短暂状态；不接受配对请求的对端同样不会广播端口。自动删除成员关系
会把一次临时观察变成永久的信任丢失。

**不经过对方用户确认就自动配对。** 否决：配对是整个设备组的认证边界。静默发起
配对会让仅仅出现在局域网中的设备触发交换，也会移除唯一用于确认对端的决定。

**仍然显示连接，让握手失败。** 否决：对端已经声明没有会话监听，所以按下之前就
知道操作会失败；报告失败也不能恢复缺失的密钥。

**让对话行没有操作。** 否决：这正是本次报告的缺陷。用户能看到两台设备，而且现有
协议已经提供了恢复流程，隐藏恢复入口只会让用户卡死。

## Consequences

- 单边或陈旧的成员关系可以通过正常的配对确认重新建立。
- 启动过程中的临时状态不会被转换成破坏性的 profile 修改。
- 既没有地址也没有会话端口的组成员会一直不可操作，直到发现层为它定位；界面仍
  不会猜测地址。
- 对话行的三种操作现在由一个明确的决策点产生，而不是两个可能同时为假的布尔值，
  以后新增状态不会再悄悄导致没有按钮。
