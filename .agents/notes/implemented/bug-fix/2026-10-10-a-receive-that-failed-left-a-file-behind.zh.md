# Agent Note：一次失败的接收，留下了一个文件

状态：implemented

[English](2026-10-10-a-receive-that-failed-left-a-file-behind.md) | 中文

## Problem

一次没走完的传输，会在用户选的目录里留下东西。字节原来直接写在文件的**最终名**上，所以被打断的接收会留下一个戴着对方名字的空文件——看起来是「收到了」，打开却什么都没有。真实磁盘上留下的痕迹把形状说得很清楚：

```
WinDirStat.exe       0 B           09:24:47   ← 卡住的那次接收
WinDirStat (2).exe   4,214,704 B   09:25:01   ← 同一个文件，重试
```

重试拿到了文件，但没拿到**名字**：`incomingPathFor` 遇到重名是编号而不是覆盖，这对用户自己的文件是对的，对一次谁都没完成的传输留下的残骸是错的。于是目录里两样都留着——一个不成立的 0 字节文件，和一个只因它才存在的 `(2)`。

同一套安排还有第二笔代价，已经付掉了。`acceptInto` 原先在接收被**答复**的那一刻就记下文件路径，而那一刻一个字节都还没到；图片消息于是去解码一个空文件，失败且永不重试，画出一个坏掉的框（PR #35，`0857ff7`）。那一半修好了。剩下的是磁盘上那个文件，也就是这份记录要讲的事。

## Decision

接收先写到一个由本机取名的暂存名，等每个字节都校验、哈希通过之后，再改名成它最终的名字。

```dart
// lib/app/views.dart
File stagingPathFor(Directory directory, String name)
// → <目录>/<净化后的名字>.<16 位十六进制>.part

// lib/app/app_controller.dart，acceptInto 里
final staged = stagingPathFor(directory, item.name);
final sink = await FilePayloadSink.open(staged);
// ……然后，当 Transfer 的 outcome 是 TransferCompleted：
await landing.sink.close();
final finalPath = incomingPathFor(landing.directory, landing.name);
await landing.staged.rename(finalPath.path);
// ……而当 outcome 是别的：
await landing.sink.close();
await _discardStaged(landing.staged);
```

三个细节各自都是一个决定。

**暂存名和最终名在同一个目录里。** 改名只有同卷才是改名——放到系统临时目录，最后一步就变成复制，而复制本身也会被打断，留下半个文件顶着一个看起来完整的名字。同目录，最后一步就是原子的。

**暂存名自己说明了身份。** `<名字>.<token>.part`——用户在传输过程中打开目录，看到的是一件没完成的东西，看得出来；旧名字把这件事藏在对方的文件名后面。token 让同一个名字的两次尝试彼此分开，也让暂存文件不会撞上用户已经拥有的名字。

**最终名在改名那一刻才决定，不在答复那一刻。** `incomingPathFor` 是在字节发布的瞬间被问的，所以一个在 Offer 被接收时还空着、之后被占掉的名字，会被编号而不是被覆盖。提前决定、延后改名在常见情况下也行得通，但会把最后一步交给一个可能已被别人拥有的名字。

作为这套改动的一部分，`FilePayloadSink.close()` 变成了一个共享的、可等待的 future。改名需要句柄先消失，而关句柄有两个互不知情的调用方：Transfer 自己在落定时关掉它的 sink，落盘的所有者在改名之前再关一次。一次「先返回、其实还没关完」的第二次 close，会交出一个当时还动不了的文件。

## Alternatives considered

**失败时删掉那个最终名的文件。** 最小的修法，否决：它把真正要紧的那个窗口——传输的整个生命期——继续留着，用户目录里躺着一个名字可信的空文件。而且它用「删掉」来解决 `(2)`，前提是得确认那个文件是我们的，而这条路上判断错了就意味着删掉用户自己放的东西。

**在 Offer 被答复时就决定最终名，只把字节写到暂存名。** 否决：名字会在整个传输期间被占住，于是用户在此期间新建的文件、或同名文件的第二次接收，会在改名时被覆盖。晚一点编号，才是让「撞名」这个问题得到正确答案的做法。

**写到系统临时目录。** 否决：跨卷，发布这一步就不再是原子的，而这正是整套安排唯一要买到的东西。

**启动时清理残留的 `.part`。** 留作可能的后续，不在这轮做：这次修掉的是 *Transfer* 主动放弃的那些文件，也就是 App 看得见的每一种结束方式。崩溃或被强杀仍会留下一个，但它明说自己没完成、也不占最终名，所以扫一遍是打扫卫生，不是正确性。现在做，就意味着要先定一套临时文件保留策略，那是另一个问题。

**把写下的字节留着，以便续传。** sink 支持 `resume` 偏移，`cancel` 的注释也把那些半成品字节说成「让这次尝试可续传的东西」，但没有谁调用它：`acceptInto` 用 `resume: false` 打开 sink，那些字节从来没有读者。留着的是垃圾，不是能力。真要做续传，需要的是一个**能再找回来**的暂存名——那是一个关于命名方式的决定，不是关于要不要删这个名字的决定。

## Consequences

- 第一次尝试夭折的文件，重试时拿到的是它要的名字，而不是一个「从未到达的文件」旁边的编号。
- 正在接收的目录里会短暂出现 `<名字>.<token>.part`；它诚实地表示自己没完成，并在传输结束时消失。
- `localPath` 出现在 Transfer 结束之后，而不是结束的那一刻——发布是一次关句柄加一次改名。会话靠控制器的通知重绘，而想要一张已落地图片的测试现在等的是那个路径，不是那个状态。
- 崩溃仍会留下一个 `.part` 文件。它明确地没完成、也不占用最终名，这比旧行为严格更好；这是启动清理唯一能覆盖的那种情况。
- `dart test` 直接覆盖了新函数（`stagingPathFor` 把文件暂存在目录内、用的不是最终名、同名两次尝试不会相撞），也覆盖了端到端行为：一次被取消的接收留下一个空目录，而同一个文件的重试落地为 `report.pdf`。
