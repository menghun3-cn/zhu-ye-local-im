# Agent Note: 没提到表情的那份更新日志

Status: implemented

[English](2026-10-20-the-changelog-that-did-not-mention-emoji.md) | 中文

## Problem

表情功能发出去了 —— 合了、发了、用户也装上了 —— 而它从来没有被告知过。

`feat: 会话支持发送表情，表情按钮旁附最近使用与全部表情` 是提交 `7eb9ecf` 的
主题，它由 PR #104 合进 `develop`，并被 tag `v0.1.10` 带上了。此后每一个构建里
都有它。但 `v0.1.10` 的 `CHANGELOG.md` 条目里写的是可拖动分隔条与气泡宽度修复，
没有提到表情；`v0.1.11` 的条目 —— 也就是**第一个真正发布出去的版本**、第一个
用户能读到说明的版本 —— 同样没有提到它。

这件事要紧，是因为 CHANGELOG 不是躺在仓库里的一份文档。`release.yml` 会把某个版本的
`CHANGELOG.md` 段落取出来，作为 GitHub Release 的正文发布；「关于」页读的是同一段
正文，用来显示新版本改了什么。**更新日志就是发布说明，也是应用内的更新面板。**
一份漏掉了它的更新日志，意味着用户在唯一本该告诉他们这件事的界面上，从来没被告知。

这不是措辞取舍的问题。那个提交就在发版所依据的区间里：

```console
$ git log v0.1.9..v0.1.10 --oneline
a5f9ae1 Merge pull request #106 from menghun3-cn/release/v0.1.10
d664b8a chore(release): 0.1.10
8729602 Merge pull request #105 from menghun3-cn/feat/message-bubble-width
edfe596 refactor: 会话列的最小宽度改为推出来的，两栏宽度改为量出来的
d683bc5 feat: 会话列表与会话之间加分隔条，可拖动调整两栏比例
abb215f fix: 消息气泡宽度上限此前从未生效，长消息会横穿整个会话
b1cf41b Merge pull request #104 from menghun3-cn/feat/send-emoji
7eb9ecf feat: 会话支持发送表情，表情按钮旁附最近使用与全部表情
```

表情提交明明白白列在里面，而据此写出的条目里没有它。

**这是怎么可能的。** 一个版本的更新日志是在发版那一刻、由发版的人手写的。
`git-publish` 技能会生成草稿、拿给人确认，而格式门禁（`changelog_check.py`）检查的是
条目**长得对不对** —— 版本号与日期的标题、取值受限的分类、每个分类下至少一条列表项。
这些检查全都在管形状，**没有一条在管内容**：没有任何东西问「这个区间里的提交，
是不是都被写进去了」。

于是一个 `feat:` 提交就可以被漏掉，而没有任何东西会失败。版本发出去了，说明发出去了，
功能就此隐形。

这与
[两次改写都没能改倒的那个探针](../bug-fix/2026-10-20-the-probe-that-survived-two-rewrites.md)
记的是同一类缺陷：一个得靠人记住的步骤，住在一件与它无关的地方旁边，
唯一的失败方式是沉默。那份笔记给打包探针的解法是「让清单自维护，让判断能被机器查」，
这里该用同样的解法。

## Decision

**更新日志要做完整性检查，而且跑在那个一直会跑的门禁里。**
`test/process/changelog_entries_test.dart` 读 `CHANGELOG.md` 与 git 历史，
当某个版本的条目没有交代清楚它区间里的提交时，测试失败。

检查以提交的 **subject** 为准，因为更新日志条目就是从 subject 来的。
一个版本区间里凡是 subject 带 `feat:`、`fix:`、`refactor:`、`perf:` 或 `docs:` 前缀的
提交，都必须被该版本条目下的某一条列表项交代到 —— 被交代的那一条里要出现
这段 subject 的一个能区分出它的片段。

`chore:`、`test:`、`ci:` 属于基础设施，排除在外 —— 这与 `git-publish` 技能自己写的
分类规则一致。

**一个版本的区间是它*改了什么*，不是它的历史里有什么。**
发布用的 tag 并不排在一条线上：release tag 指的是生产分支上的合并提交，
而那个合并提交把集成分支的工作以**新的**提交号带了进来。所以
`v0.1.12..v0.1.13` 会列出 `v0.1.12` 已经发过的改动，
而集成分支上的那些提交甚至不是先前那个 tag 的祖先。
于是检查改问一个关于**树**的问题：先前那个版本的树里，
是不是已经有这个提交带来的东西？一个没带来先前版本没有的东西的提交，
是先前版本已经交代过的改动，就不再问它。

**更新日志本身不参与这个判断。** 更新日志是发布**产出**的东西，不是它带的东西：
任意两个版本的它都不一样，而它并不说明这个版本带了什么。
把它算进去，会让每个碰过更新日志的提交都像是新改动。

**这条规矩从 `v0.1.8` 起成立。** 再往前的条目，写的时候一个版本的说明是概述而不是
清单，而改写历史不是测试该做的事：那些条目就是那些版本当时发布的东西，
事后被改写的发布说明，已经不是当初宣布的那份了。
`v0.1.8` 起的条目是当清单写的，检查守的就是它们。

**检查要能点出它期待的是什么。** 失败信息说清是哪个版本的条目缺了什么、
缺的是哪一条提交，而不是只说一句「更新日志不对」。点不出缺口的门禁，
等于把找缺口这件事留给读者。

**补上漏掉的条目。** 表情功能最早随 `v0.1.10` 发出，而 `v0.1.11` 是第一个
真正发布出去的版本 —— 两个条目都带着这条列表项：两个版本对应的构建里都有这个功能；
而 `v0.1.10` 那个 tag 的 Release 从未出现过，它的那份说明本来就是「这个 tag 打算发什么」
的记录。

这道检查在自己落地时又找出一处遗漏：`v0.1.13` 漏掉了随它一起发布的 README 改动
与截图脚本的修复。它的条目现在两条都补上了，已发布的 Release 说明也同步更新 ——
仓库里写一件事、发布页上写另一件事，正是这道检查要防的那类缺陷，只是高了一层。

**已发出的功能，也要由它自己的 Agent Note 认领。** 表情功能那份笔记记的是决定与取舍，
对更新日志一个字都没提 —— 因为更新日志是在发版那一刻由另一个步骤写的。
把它们接在一起的是门禁，不是笔记。

## Alternatives considered

**信任 `git-publish` 技能里那句确认提示。** 否决：那句提示是让人对着提交清单核对
列表项 —— 正是已经失败过的那次比较。提示可以被忘掉、被跳过、被匆匆扫一眼；
测试不会。

**从提交自动生成更新日志。** 否决：更新日志是人写的中文散文 ——
「消息气泡的宽度上限此前从未生效」不是「fix: 消息气泡宽度上限此前从未生效」的机械变换。
自动生成会把作者写的句子换成提交主题，对读者来说那是一份更差的发布说明。
检查保留作者的身份，只核对覆盖面。

**改成检查每个 `feat:` 是否都有 Agent Note。** 否决：那是另一条性质，而且它抓不到这次的问题。
表情功能**是有**完整 Agent Note 三件套的 —— 更新日志照样把它漏了。

**只检查最新的那个版本。** 否决：`v0.1.10` 的条目里同样没有表情，而它的 tag 至今还在
`master` 上，指着一个从未出现过的发布。只往前看的门禁会留下已有的错记录。

**问历史，而不是问树。** 否决，而且先试的就是它：最自然的问题是
「这个提交是不是先前那个 release tag 的祖先」，而对集成分支上的每一个提交，
答案都是否 —— 生产分支是以新的提交号把那部分工作合进来的。
一段对先前版本明明发过的工作一律回答「否」的历史，会让检查把同一份工作数两遍，
每次发布都失败。树回答的才是真正被问的那个问题。

**把检查放进 `changelog_check.py`，而不是 `dart test`。** 只在一个理由上否决：
`changelog_check.py` 是 `git-publish` 技能里跨仓库共用的模板，写在 Python 里；
而本仓库自己的门禁是 `dart test` —— 那是任何一台开发机上不用装 Python 就能跑的那一个。
这个检查需要 git 历史，技能脚本没有理由去知道它；而本仓库的测试门禁本来就是
管发布流程其余一切的地方。

## Consequences

- **功能不可能在门禁全绿的情况下悄悄发出去而不被公告。** 下一次发版只要有一条 `feat:`
  没被写进条目，`dart test` 就失败。
- **检查读 git 历史，所以它需要仓库。** 历史拿不到时（源码压缩包、浅克隆）它跳过自己，
  而不是因为技术性原因失败 —— 那种情况下的把关者是发版本身，它总是在完整仓库里跑的。
- **表情那条列表项现在出现在 `v0.1.10` 与 `v0.1.11` 两处。** 已经发布出去的
  `v0.1.11` Release 正文在 GitHub 上直接改正 —— 因为那份说明已经发出去了，里面没有它。
- **`v0.1.13` 的条目补上了它缺的两条列表项**，已发布的 Release 正文也同步改正。
- **同一类遗漏从此对每一个新功能都有人管。** 「定期检查更新」那个功能在 `v0.1.9`
  里也有一模一样的缺口，由同一道检查覆盖。
- **`v0.1.8` 之前的条目保持它们发布时的样子。** 检查不要求重写它们 ——
  事后被改写的发布说明，已经不是当初宣布的那份了。
