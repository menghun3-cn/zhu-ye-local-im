# Agent Note: 收到的图片被裁成了正方形

Status: implemented

## Problem

收到的图片看着不像它自己。`ImageBubble` 把每张图都塞进固定的 200×200 方框里，用的
是 `BoxFit.cover` —— 先把图放大到盖住方框，再把溢出的部分切掉。碰巧是正方形的照片
几乎看不出损失；而对人真正会发的形状 —— 截图、手机照片 —— 损失很大：4:1 的截图只
剩下中间四分之一，竖图只剩中间一条横带。气泡尺寸没错，图是错的，唯一能真正看清文件
的地方是点开后的原图视图。这是从打好的 Windows 包里报上来的：「接收的图片，未正确
显示预览」。

## Decision

**先把图的形状量出来，再把盒子做成那个形状。** `ImageBubble` 改成
`StatefulWidget`，订阅图片自己的 `ImageStream`，在拿到第一个 `ImageInfo` 时记下
`Size(width / scale, height / scale)` —— 图自己的尺寸 —— 再缩到两边都不超过 200 像素，
**绝不放大**。然后 `Image` 放在一个正好这么大的 `SizedBox` 里，用 `BoxFit.cover`：
盒子本来就是图的形状时它一点也不会裁，只用来遮掉取整到整像素时可能留下的那条细缝。

绝不放大：32 像素的图标就画 32 像素。放大到 200 像素预览的是解码器的猜测，不是文件。

**仍是三种状态，含义一个没变。** 还没量出尺寸 → 占位块；量出来了 → 图本身；解码失败
→ 原来的「名字 + 破图」兜底，而且现在也不再画成可点的 —— 读不出来的图没有可打开的东西。

**占位块是接近横幅比例的 200×132，而不是零尺寸。** 零尺寸会让气泡先塌下去、图到了再
弹回来，那看起来像故障而不是加载；已经接近常见形状的盒子，只会在图到达时长长一点点。

**订阅加在 `didChangeDependencies` 而不是 `initState`。** 解码是按显示器的像素比缓存的，
而那个比值要等 widget 进了树才知道。已经在 Flutter 缓存里的图，会在 `addListener` 时
**同步**交回来 —— 也就是在 `didChangeDependencies` 期间，而这个阶段调 `setState` 是错的
—— 所以这种情况直接把字段写掉，紧接着的那次 build 就会读到它。

## Alternatives considered

**固定 200×200 的方框配 `BoxFit.contain`。** 形状保住了，但会留边：4:1 的图放进方框，
上下各多出一条空白气泡，那预览的是盒子而不是图。盒子必须**就是**图的形状，而想知道
那个形状只能先解码。

**完全不给尺寸，让 `Image` 在 `ConstrainedBox` 里自己长。** `RenderImage` 确实会按自身
尺寸、在约束内等比地给自己定尺寸 —— 但那要等解码完；在那之前它取
`constraints.smallest`，也就是 0。气泡会在解码前几帧是一条空缝，然后跳到全尺寸，而且
没有占位块盖住这段。

**方框配 `BoxFit.cover`** —— 也就是原来那样。这就是那个 bug。

**把图片尺寸、或者缩略图，放到协议上传过去。** Offer 带的是 digest，接收方画的是它校
验过的那个文件。为显示细节加尺寸或预览通道是协议改动，而且会让发送方能描述出一张
和它实际发的不是同一张的图。

**用 `ResizeImage`/`cacheWidth` 按显示尺寸解码。** 省的是解码开销，和预览的形状无关；
何况这张图用户本来就能点开看全尺寸，多这一个旋钮只是多一个能拧错的地方。

## Consequences

**消息的高度在图解码出来之前不再已知。** 缩略图的高度跟着图走，所以会话没法提前把位置
留出来，靠的是那个固定占位块让图的到达不成为一次跳动。同一条消息画两次 —— 先占位块、
再图 —— 是正常的帧序列，不是错误。

**`FileImage` 的 scale 是 1，所以图的像素数就是它的逻辑像素数。** `Image.file` 一直如此，
旧代码也继承了这一点。在这里的后果是：200 像素这个上限是**图片像素**上的上限 —— 60 像
素的 logo 就画 60 逻辑像素宽，在 3 倍屏上是个偏小、略糊的缩略图，而不是清晰的那种。真
要解决就按显示器像素比解码，但那不是这次要改的事，而且那样小图会更小。

**气泡现在会把同一张图解析两次 —— 一次量尺寸，一次画。** 两次都走 `FileImage` 且配置
相同，所以第二次命中缓存，不会解码两次。`ImageBubble` 自己不持有任何字节流，而会话在
每个进行中的 Transfer 的每个进度 tick 上都会重建，这一点很重要。

**原图视图没有动。** `showImagePreview` 本来就是把图不加约束地放在 `InteractiveViewer`
里；错的只有缩略图。

## Testing

新增 `test_flutter/ui/image_bubble_test.dart`。它读的是布局**实际**给这张图的尺寸 ——
那是用户唯一能看见的东西：

* 4:1 的图被排成 200×50 —— 这条断言在旧的 `BoxFit.cover` 方框上必然失败，那时会是 200×200；
* 1:4 的图被排成 50×200，说明另一个方向的上限也成立；
* 40 像素宽的图被排成 40 像素宽，即盒子会缩到小图大小而不是把它放大；
* 文件不存在的图退回到名字，并且完全不画 `Image`；
* 没有 `onOpen` 的气泡里没有点击目标；有 `onOpen` 的，点缩略图会调用它。

夹具是由引擎编码出来的、指定尺寸的真 PNG（`test_flutter/support/ui_harness.dart` 里的
`writePng`），而不是写死的字节数组：预览的形状来自解码，所以一个**看起来像** PNG 的夹具
测到的是兜底分支而不是预览。

`test/app/app_controller_test.dart` 新增「a received picture keeps a path worth drawing」，
钉住这条链的另一半：图片 offer 在被接收之前没有可画的路径，而落地的图有一条路径，读回来
就是发出去的那些字节。
