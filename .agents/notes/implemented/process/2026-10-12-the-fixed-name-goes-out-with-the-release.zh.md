# Agent Note: The fixed name goes out with the release

Status: implemented

[English](2026-10-12-the-fixed-name-goes-out-with-the-release.md) | 中文

## Problem

[固定名别名](2026-10-12-a-fixed-name-for-the-package-lan-scripts-pull.md) 让拉包方有了一个
不变的 URL，但它只被发布进 `build/dist` —— 那台恰好正在对外提供文件的机器上的目录。局域网
之外的机器根本够不着它。它唯一的通道是 GitHub Release，而那里的每个附件名里都带着版本号，
于是 `releases/latest/download/<名字>` 照样得先知道版本号。别名替局域网去掉的那个要求，对
其余所有人还留着。

而这正是本仓库自己的分发一直在撞的场景：局域网是**提供**包的地方，外网才是取包的人、以及把
取包这件事自动化的人所在的地方。一个给局域网之外的机器做初始化的脚本 —— 构建机、同事放在
另一个网络里的笔记本 —— 只能去问 API 当前版本是多少，或者每次发版都改一次；后者恰恰是别名
存在的意义所在。

上一版决定[考虑过这件事，并否掉了](2026-10-12-a-fixed-name-for-the-package-lan-scripts-pull.md)
（「让 CI 的通配把别名一起收进 Release」），两条理由：那样一个 release 会为两个文件各带两个
名字；而 release 一侧的「最新」早就存在了，它是 tag，不是文件名。这两条今天依然成立。变的是
天平另一头的分量：一个只在一个网络里有效的固定地址，对真正需要它的人来说不算固定地址。

## Decision

两个别名连同它们的 `.sha256` 侧车，与带版本号的产物一起附到 Release 上。`release.yml` 的
`windows` job 从上传两个文件变成六个 —— 带版本号的一对、别名一对、两个侧车 —— release job
把下载到的全部附上。于是外网的机器可以这样拉包：

```
https://github.com/menghun3-cn/zhu-ye-local-im/releases/latest/download/LocalTransfer-latest-windows-x64-setup.exe
```

绿色包把 `-setup.exe` 换成 `-portable.zip` 即可。`releases/latest/download/<名字>` 解析到
「最新那个既非草稿也非预发布的 release 里、名字正好是它的那个附件」，所以那个名字必须是别名：
里面不能有版本号。逐次发版变化的是别名所在的那个 release，不是它的名字。

**release job 现在会因为没有它们而失败，而不是照常发出去。** 在 `gh release create` 之前多
一步，逐个核每个别名：文件存在且非空、侧车存在且非空、`cmp` 说别名与本版的产物逐字节相同。
随后 `sha256sum -c ./*.sha256` 用真工具把每个侧车验一遍。没有这一步，缺别名到拉包方那里表现
为 404 —— 一个「下载失败」，它不会告诉任何人发布这一步漏了东西；而上一版遗留的别名则会变成
一个固定地址，安安静静地提供错误的构建。

**官网的附件匹配跳过别名。** `site/app.js` 原来靠匹配附件名后缀（`setup.exe`、`portable.zip`）
决定每个下载按钮指向谁，而别名正好以同样的后缀结尾。API 先返回哪一个就会被选上，于是下载卡片
可能显示「最新版本 v0.1.1」，旁边那个文件名里却没有版本号 —— 正是命名规则要防的那种错配。
后缀匹配现在优先带版本号的产物，只有在没有带版本号的产物时才退回别名。

**下载区把两个固定地址写出来了。** 它们以纯文本写在 `site/index.html` 的按钮下面，因为需要它们
的人在写脚本，按钮不是他们来这儿要的东西。用纯文本而不是让 JavaScript 填：这个地址不依赖 API，
那它就不该依赖 API 调用成功。

## Alternatives considered

**让 CI 的通配（`build/dist/*-portable.zip`）把别名收进去。** 最短的写法：路径本来就匹配，连
路径清单都可以不要。没选，因为那个目录里还有 `使用说明.txt` 和上一次运行留下的东西，而且用通配
的话，没人能靠读工作流看出一次 release 到底该包含什么。那六条显式路径就是这句话本身。

**Release 保持三个附件，改去文档里教人调 API。** 拉包方去调 `GET /releases/latest`、读
`assets[].browser_download_url`、按后缀挑 —— 也就是官网那套做法搬进 shell。没选，因为它让每个
拉包方都依赖 API 的可用性、限流和 GitHub 的 JSON 形状，只为了拿到一个本来可以是常量的 URL。它还
没法离线工作，而正在被初始化的机器很可能就是离线的。

**只附别名，不要带版本号的那对。** 一个文件一个名字，也就没有「我该下哪个」。没选，因为带版本号
的名字才是主名字：从没有版本号的名字下下来的包，事后无法被识别，而每一份说「我用的是最新版」的
反馈都会缺掉最关键的那个事实。带版本号的一对留着，别名是那个图省事的入口。

**让 tag 滚动，这样 `releases/latest` 就不需要别名。** GitHub 没有滚动 release：tag 指向一个
提交，「最新」是按发布日期解析的，不是按 tag 名。所有 release 共用一个 tag 名，会让每次发版都和
上一次的 tag 撞名，并丢掉 release 列表赖以排序的版本。

**一个跳转服务，或者一个用 302 应答的 Pages 文件。** 没选，因为跳转是又一个可能挂掉的东西，而
「没有服务端」是这个项目承诺的一部分。Release 附件本来就是 GitHub 在提供，缺的只是一份固定名。

**只发别名，把版本写进文件里。** 与上面「不要带版本号的那对」同一个理由被否，另加一条成本：那样
这个名字就得靠打包脚本之外的什么东西来与 `pubspec.yaml` 保持一致。

## Consequences

**换来了。** 一个在任意能上外网的地方都有效的地址，永远不用改；并且因为别名只在打包脚本自己的
检查通过之后才写，它不可能指向一个没通过检查的包。侧车也跟着上，于是局域网之外的拉包方也能校验
一次走公网的下载 —— 那正是下载更容易损坏的场合。

**代价。** 一个 release 现在带七个附件：三个产物、两个别名、两个侧车。其中两个与另外两个逐字节
重复，于是 release 页面为那两个文件各显示两个名字。接受：重复是那个常量地址得以存在的代价，别名
的名字里写着 `latest`、它复制的产物就在旁边，而另一个选择是让每个拉包方在拿包之前先去查出
版本号。

**没有覆盖。** 本次改动之前发出的 release 没有别名，固定地址对它们会 404；下一个 tag 起才有效。
`releases/latest` 永远不会解析到预发布或草稿，所以预发布也不提供那个固定地址。另外，没有任何东西
会把别名补到旧 release 上 —— 把本机的别名拷到已发的 `v0.1.0` 上被否掉了：那些字节不是那个 tag
构建出来的字节，而 `AGENTS.md` §9 最后一句正是这件事。

**门禁仍未覆盖。** `AGENTS.md` §5 里没有哪道门会跑 `release.yml`；它第一次诚实的运行是下一个
tag。这是这一带第四个只能靠推理、而不是靠跑一次来发现的缺陷类别（[少了那个 D 的定义](../bug-fix/2026-10-12-a-define-that-was-spelled-without-its-d.md)、
[只在一侧跑过的构建步骤](../bug-fix/2026-10-12-two-build-steps-that-had-only-ever-run-on-one-side.md)、
[别名本身](2026-10-12-a-fixed-name-for-the-package-lan-scripts-pull.md)）—— 而「在 PR 上跑打包脚本
与发布步骤」的那个 CI job 仍然没有被写出来。
