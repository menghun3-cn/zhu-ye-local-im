# Agent Note: 交付前做三次对抗性代码审查

Status: implemented

[English](2026-11-24-adversarial-review-gate.md) | 中文

## Problem

AI 辅助开发让写代码很快，而现有 §5 门禁（`analyze`、`format`、`dart test`、
`flutter test`）保证的是代码能编译、测试能通过——但没有任何环节强制对 diff
本身做一次敌意审读。测试固化的是「已经想到的用例」；自我审查倾向于按写代码
时的方式重读代码，会复现产生它的同一批盲点。能活下来的缺陷，压倒性地是
没人构造过输入的那类。

## Decision

AGENTS.md §5.1 规定：任何代码交付（提 PR、提交、标记完成）之前，必须对
本次改动做 3 次相互独立的对抗性代码审查。每次审查换一个攻击视角——
正确性（畸形输入、边界条件、并发时序、错误路径）、安全与契约（越界访问、
敏感信息泄露、协议/磁盘/网络格式被破坏的可能，并对照 §7 平台事实约束核实）、
一致性与维护性（与 AGENTS.md、`.agents/notes/`、邻近代码风格的冲突，重复
抽象、死代码、遗漏的门禁与文档）。审查对象是相对 `develop` 的完整 `git diff`，
不是只看新增文件。每轮发现的问题必须修复或写明不修的理由，三轮不得合并成
一次通读充数，审查结论随 PR 描述或提交信息记录。纯文档、纯配置、无行为
改动的改动只需 1 次。

## Alternatives considered

**只做一次认真的自我审查。** 否决：单次审查继承作者的框架，倾向于验证
意图而非攻击意图。三个具名视角强制审查者构造作者没有考虑过的用例。

**只靠现有门禁加 PR review。** 否决：门禁检查的是编译、格式和已知测试用例，
无法判断新代码路径在敌意输入下是否可达、是否与平台事实矛盾。PR review
发生在工作被标记为完成之后——本规则把敌意审读移到交付之前。

**用检查清单脚本代替判断。** 否决：失效模式是推理遗漏，不是步骤遗漏；
脚本能枚举命令，不能构造对抗性输入。规则刻意要求记录发现，使走过场的
审查可见。

## Consequences

今后每个非平凡改动都带三轮有记录的审查，代价与 diff 规模成正比，也让
「看着没问题」式的交付更难无声通过。纯文档/配置改动的豁免把成本挡在
不可能破坏运行时行为的改动之外。若审查沦为仪式（结论都写「无发现」却
拿不出证据），补救方式是收紧「什么算发现」，而不是删除规则。
