# Agent Note：官网是三个文件，不是一条构建链

Status: implemented

## Problem

项目需要一块地方，回答「这是什么东西、怎么装、装完会撞上什么」，而不必先让人去克隆仓库。
需求也很明确：用 `site/` 目录存页面，自动发布到 GitHub Pages。

最顺手的做法恰恰是这个仓库会反感的做法。这里其他每一件交付物都是可复现、可核对的 ——
`scripts/*.ps1` 出包、`test/` 与 `test_flutter/` 量源码树、`release.yml` 从 tag 出产物。
一个必须 `npm ci && npm run build` 才能看一眼的官网，会再加一条「在这台机器上跑得通、
在那台上跑不通」的工具链，而它的全部内容不过是些说明文字。

## Decision

**`site/` 就是三个文件，没有别的。** `index.html`、`styles.css`、`app.js`。
没有构建步骤、没有打包器、没有包管理器、运行时不加载任何第三方脚本或字体 ——
所以 `upload-pages-artifact` 原样上传该目录，工作流里一个编译动作都没有。

- **设计语言是借来的，不是重新发明的。** 令牌直接来自 `design-preview/styles.css`：
  同一个品牌绿、同样的发丝线、同一套字阶、同一套 `reveal` 编排。新的只有版式层，
  因为那份文件是应用稿，不是官网。于是改一个颜色意味着两边都要改 —— 这一点写进了
  `AGENTS.md` §6.3。
- **只在 `master` 部署**（`push` 过滤 `site/**`，外加 `workflow_dispatch`）。
  按 §2.2，`master` 是生产分支；官网描述的是用户**真的能下载到**什么，
  所以它跟着发布走，而不是领着发布走。留 `workflow_dispatch` 是为了一个错别字
  不必发一个版本。
- **下载按钮是降级，不是失效。** 它们出厂就指向 `releases/latest`；GitHub API 有响应时，
  `app.js` 换成最新 Release 里那个确切的产物，并把真实文件名填进去。离线、被限流、
  或者还没有第一个 Release，页面就用手上原有的链接照常工作。
  一个全部职责就是发下载的页面，不能发出一条死链。
- **主题先跟随系统，再记住选择。** `<head>` 里一段内联脚本在首帧之前就设好 `data-theme`
  （隐私模式下 localStorage 会抛，就地吞掉），所以不会闪一下错的配色；开关随后
  把显式选择持久化。

## Testing

- 两个工作流都能被 `package:yaml` 解析（`pages.yml`、`release.yml`，0 失败）——
  解析不了的工作流就是永远不会跑的工作流，而 GitHub 只在推送之后的 Actions 页告诉你。
- 页面没有自动化测试；它是静态标记，除了浏览器预览能看到的东西，没有多少逻辑值得钉住。
- `pages.yml` **没在本地跑过，也跑不了**：上传 artifact 的是 GitHub 的 runner，
  提供访问的是 GitHub 的 Pages 服务。第一次真跑，就是第一次带着 `site/**` 推到 `master`。

## Alternatives considered

**从分支发布（`gh-pages` 或 `docs/`）。** 否：那会造出第二份官网，而真源有两个的那天
就开始漂移。Actions 部署让 `site/` 成为官网唯一存在的地方。

**引入静态站点生成器（Hugo / Eleventy / Astro）。** 否：生成器换来的是模板与内容集合，
而这一页两者都不需要。它还会让「看一眼官网」变成「先装工具链」，
恰恰是这个仓库一路在避免的性质。

**整页从 GitHub API 取。** 否：正文是静态的，不该取决于一次网络请求、一个限流额度、
或者 GitHub 是否在线。只有版本号和三个下载链接是动态的，因为只有它们真的会变。

**所有按钮都指向 `releases/latest` 就收工。** 作为**唯一**手段否：那会逼用户自己去
一列文件里挑对的那个，而文件名正是他们分辨「绿色包」和「安装包」的依据。
为此花一次 `fetch` 把确切产物填进去是值得的，那个普通链接做兜底。

**不做官网，让 README 顶替。** 否：需求就是要一个官网，而 README 是写给
已经决定要读代码的人的。

## Consequences

**换来的。** 一个靠拷贝文件就部署、可以当 diff 评审、双击 `index.html` 就能打开的官网 ——
在任何一台机器上，不需要工具链。

**放弃的。** 说明文字现在有两处：`site/index.html` 和 `packaging/使用说明.txt`
说了很多同样的事，而没有任何东西让它们保持一致。随包的那份是装进 zip 里的、
也更权威；官网是更短的摘要。改一边不会动另一边，也没有门禁会发现。

**欠着的。** 第一次部署必须从 `master` 发出，也就是说它跟着下一次发布一起上线，
不会单独走。
