# Agent Note: 把 Windows 打包变成脚本化的自检构建

Status: implemented

[English](2026-10-08-packaging-is-a-script-not-a-ritual.md) | 中文

## Problem

`build/dist/*.zip` 才是仓库之外的人真正运行的东西，而它在一天之内两次悄悄偏离了源码。

第一次：修「打开会话崩溃」的提交进了库、六道门禁全绿，但包里装的仍是上一次的构建。
反馈是「为什么在别的机器上是灰的」—— 别的机器跑的就是那个旧 `.zip`，因为整套门禁里
没有任何一道会去产出它。`dart test` 与 `flutter test` 量的是源码树；压缩包量的是
「上一次有人记得跑 `flutter build` 并手工把目录拼起来」的那一刻。

第二次：包落后两个提交，而且完全缺 `vcruntime140.dll`、`vcruntime140_1.dll`、
`msvcp140.dll` —— 与此同时它自己的 `使用说明.txt` 承诺这三个文件随包附带。
`local_transfer.exe` 是动态导入它们的，所以在任何没装 VC++ 运行库的机器上，
这个压缩包根本起不来。而在这台机器上它不会失败：`System32` 里有。

这两次都**看不出来**——盯着源码看不出，把门禁重跑一遍也复现不了。它们都是
「被手工拼出来的人工产物」所特有的性质。

## Decision

打包是一个脚本：`scripts/pack-windows-portable.ps1`。它构建、从 Visual Studio 的
可再发行目录定位 VC++ 运行库、组装目录、写出压缩包，然后**验证它刚写出来的那个压缩包**。

验证步骤是脚本存在的理由，不是附属功能：

- 逐个必需文件都**在压缩包内**查找，而不是在磁盘上；
- 检查目录布局，免得包里悄悄多套一层目录；
- 在包内的 `app.so` 里检索本次新增的界面文案，且文案挑的是**新代码独有的完整句子**；
- 把压缩包解压到临时目录并启动，确认它保持响应、且发现端口与配对端口都绑上。

`-SkipBuild` 用于只改了说明文件时重新组包。`-Smoke` 追加启动检查。

## Alternatives considered

**在 `AGENTS.md §5` 里加一道「构建产物」门禁。** 不作为主要机制：那会把一次持续数分钟的
Windows 构建塞进每次提交的必经路径；而且**构建成功并不等于压缩包里有新代码** ——
上面第二次失败就发生在一次成功的构建之后。

**信 `build/windows/x64/runner/Release` 的 mtime。** 正是这套推理产出了第一个过期包。
它也看不见「缺运行库」—— 那是组装步骤的性质，不是构建步骤的。

**继续手工组装，把清单写进说明文件。** 手工那一步恰恰是在时间压力下被跳过的东西，
而且跳了两次。一份放在手工步骤旁边的清单，扛不住那种让手工步骤被跳过的时间压力。

**从 `C:\Windows\System32` 抄运行库。** 那不是允许的再发行来源，并且会让包悄悄绑定到
本机恰好装的那个版本。Visual Studio 的 `VC\Redist\MSVC\<ver>\x64\Microsoft.VC143.CRT`
才是受支持的来源；脚本会在两个 program-files 根下、所有已安装版本里搜索，而不是写死路径。

## Consequences

- **被检查的对象变成了压缩包，而不是源码。** 门禁全绿不再蕴含「包是对的」；
  而脚本是拿到一个「被检查过的包」的唯一途径。
- **包内的说明文件生成自 `packaging/使用说明.txt`。** 它放在版本库里而不是紧挨构建产物，
  因为它是一份由人维护的文档 —— 放在 `build/` 下意味着新 clone 只能产出最小兜底版，
  而完整内容（配对、端口、防火墙、排查）就只存在于某一台机器上。构建日期与 commit 号
  在每次运行时改写，而不是存在模板里 —— 存在模板里就会过期。
  为兼容早期手工组装留下的布局，仍会依次退回 `build/dist/使用说明.txt`。
- **脚本用「覆盖 + 报告」代替删除**：就地覆盖，然后对 staging 目录里「当前构建不产出」的
  文件发出警告。开发这个脚本所用的沙箱会拒绝 `build/dist` 下的删除操作——**连删单个文件也拒绝**——
  所以「先删再建」那条路在那里走不通。覆盖对一个可能正被人看着的目录来说也是更保守的行为。
- **包增大了 173 KB**（三个运行库 DLL），从 12.20 MB 到 12.44 MB。这是「它在干净机器上真能跑」的代价。
- 改动任何用户可见文案的人，应当预期验证步骤会失败，直到脚本顶部的探针列表被更新。
  这是有意的：那个列表就是「这个包是最新的」这句话的定义。
