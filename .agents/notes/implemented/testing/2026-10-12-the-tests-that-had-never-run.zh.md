# Agent Note：一道跑不起来的门禁第一次跑起来，和它一直背着的九个期望

Status: implemented

[English](2026-10-12-the-tests-that-had-never-run.md) | 中文

## Problem

[`2026-09-29-dart-test-as-the-core-gate.md`](2026-09-29-dart-test-as-the-core-gate.md)
记了一段本机 `flutter test` 完全跑不起来的日子 —— 深信服 aTrust 拦掉了每一次
loopback WebSocket 握手，每个文件都在加载阶段就失败。`dart test` 一直能跑，于是被
立成「永远能跑的那道门禁」。widget 测试照写不误，放在 `test_flutter/`，每次改动由
`flutter analyze` 做类型检查。

这套安排的代价不在缺少运行器，而在于**八个 widget 期望和一条读源码的断言，是在从未
执行过的状态下被写出来、被评审、被合并、被当成覆盖率的。** 绿色的 `analyze` 被读成
「widget 套件通过」读得足够久，以至于它不再被读成「它编译得过去」—— 而这正是上一份
笔记警告过的区别。

2026-10-12 运行器恢复，第一次真实运行报出 `+105 -8`；`dart test` 自己也报了一个失败。
九个都不是产品缺陷，每一个都是从未被告知自己错了的测试：

| 位置 | 它断言的是 | 实际成立的是 |
| --- | --- | --- |
| `test/platform/android_bridge_test.dart` | `seams.dart` 里**第一个** `MethodChannel(` 的通道名 | PR #47 在它上面加了 host shell 的通道之后，第一个就不再是 paths 通道。Kotlin 写着 `…/paths`，测试读到的是 `…/host` |
| `test_flutter/ui/shell_test.dart` | `themeMode` 翻到 light 的那一帧就该解析出浅色调色板 | `MaterialApp` 会把一套主题淡入到另一套，那一帧携带的还是它**从**哪来的调色板 |
| `test_flutter/ui/pages_test.dart`（设置页） | 「一切正常。」—— 设置面的最后一行 | 该面是 `ListView`；800px 下这一行在折叠线以下，**根本没被构建**，`find.text` 自然匹配不到 |
| `test_flutter/ui/pages_test.dart`（选中的图片） | 输入框里以 `Text` 形式存在的图片文件名 | 图片以自身字节的缩略图形式绘制，名字在它的 tooltip 上 |
| `test_flutter/ui/pages_test.dart`（一次选多个） | 两条传输按被选中的顺序排列 | `controller.transfers` 是**新→旧**，因为会话就是这么画的 |
| `test_flutter/ui/window_settings_test.dart` ×2 | 点完单选钮/开关**之后**的文案与提示行 | `pumpUntil` 只在条件仍为假时才泵帧，因此被 tap 同步满足的条件，是在树还停在被点之前那一帧的状态下被观察到的 |
| `test_flutter/ui/composer_attachment_test.dart` | 睡 200ms 之后，托盘应显示破图标记 | 200ms 的真实时间只是猜测，解码那时还没给出答复。它的 teardown 还会去删一个已被解码图片映射住的文件，Windows 拒绝删除 |

最后两条才是重点，因为它们不是某一个测试写错，而是**测试台本身的缺口**，后面每个测试
都会继承。

## Decision

**等待必须画出一帧，说出口才作数。** `pumpUntil` 现在在条件成立**之后**再泵一帧。
它的循环只在条件为假时运转，因此一个在进入 `onSelectionChanged` 的路上就被 tap 满足
的条件 —— `SegmentedButton`、`SwitchListTile` —— 会被报告成「窗口还停在被点之前那一
帧」。这个辅助函数的承诺是「窗口上看得见」，不是「条件为真」，而两者已经分叉了。

**要看整页，靠窗口尺寸，不靠滚动。** `tallWindow` 移到测试台里，与 `wideWindow`、
`narrowWindow` 并列；断言设置页底部的那条测试用它。该页是懒列表，折叠线以下的行走根本
没被构建；为它滚动一下，就等于把滚动本身也写进了断言。

**解码是要等的，不是要睡的。** `letDecodeSettle` 等缩略图给出答复 —— 要么出像素，要么
出字节解不开时 `errorBuilder` 换上的那个标记 —— 不再固定睡 200ms。睡觉分不清「慢」和
「这个编解码器本来就不会结束」，而后者恰恰是值得抓的那个 bug。

**解码过的图片会映射住自己的文件，所以它的清理只能尽力而为。** `pngFixture` 改为经由
`tempDirectory` 写盘。那个辅助函数本来就吞掉 Windows 在映射未释放时拒绝的删除，理由与
它文档里写的一字不差。

**读源码的断言要锚在它真正指的那个声明上。** `android_bridge_test.dart` 从
`defaultPathsChannel = MethodChannel(…)` 里读字符串，而不再取「文件里离顶部最近的那个
通道」。在一个已经长出第二个声明的文件上用首个匹配的正则，是一个会悄悄换掉主题的测试。

由此留下的规矩：**从未执行过的期望不是证据。** 只要一道门禁有一段时间跑不起来，它恢复
后的第一件事就是重读自己被告知了什么；而看结果的人要记住的第一件事，是里面的断言当初
是闭着眼睛写的。

## Alternatives considered

**删掉那些事后发现难以满足的断言。** 否决：它们每一条都关乎真实行为 —— 每种主题解析出
哪套调色板、设置页最后一行是什么、两个附件以什么顺序发出、坏掉的分片显示哪个标记。
删掉它们等于删掉覆盖，而不是删掉那个错误，同一类错误下次照样能进来。

**放宽它们 —— 设置页那行改用 `findsWidgets`，附件顺序改比对集合。** 否决：这会让失败
消失，同时把每一条主张都削得比它本来要说的更弱。`{image, file}` 说不出「图片按图片走、
文件按文件走，**且**按被选中的顺序」，而那正是这条测试存在的意义。

**只修测试台，各个测试不动。** 否决：九个里有五个就是各自面前那个测试的一次性笔误，
修测试台会把它们藏进一次绿色的运行里。

**保留 200ms 的睡眠，把它调大。** 否决：任何一个数字都是关于这台机器的猜测，而且测试会
在一台「解码根本不会答复」的机器上继续通过 —— 而那恰恰是它唯一要抓的结局。

**把设置面改成 `SingleChildScrollView` 里的 `Column`，让每一行都被构建。** 否决：
通知卡片最多渲染二十条，一个会构建用户看不见的东西的面，就是一个输入越多越慢的面。
懒构建是对的，错的是测试看错了尺寸。

**让设置页那条测试滚到它要问的那一行。** 与既有的窗口设置测试选用高窗口同一个理由否决：
主张是关于页面上写着什么，而滚动会把滚动自己的行为也塞进断言。

## Consequences

- **整套门禁第一次整体变绿**：`dart test` 通过 485 条，`flutter test test_flutter`
  通过 120 条。这两个总数读者可以直接与下一次运行对照；在今天之前它们都不存在。
- widget 套件里的每一次等待现在多花一帧。这是让辅助函数能说到做到的代价，而 16ms 低于
  这套测试会观察到的任何东西。
- **留了一条已知的偶发测试。**
  `test/app/app_controller_test.dart` 的「a copy travels to a peer that mirrors」
  最多等 10s，等一条镜像条目经由真实 socket 落地。它在一次全量运行中失败过一次，单独跑
  三次三次通过，且不到一秒。这是负载下的计时问题而非缺陷；记在这里而不是用一个更长的
  超时把它糊过去，是为了让一条点名它的红色 `dart test` 被读成「机器当时很忙」，而不是
  「剪贴板回归了」。
- `test/platform/` 里那套读源码的模式，从此明确地耦合在一个声明名上，而不是文件的形状
  上。重命名 `defaultPathsChannel` 会让那条测试大声失败，这正是期望的行为：失败信息里
  写着 Dart 要的通道名，读者能看出它是一个真实存在的名字。
- widget 套件是这个项目第三样「等到它能用之后才量」的东西 —— 前两样是套件自己第一次
  运行才发现的 `ControllerScope`，以及绿色包里那两个正在寻找一句已被删掉的话的探针。
  期望写起来便宜，闭着眼睛写却昂贵。
