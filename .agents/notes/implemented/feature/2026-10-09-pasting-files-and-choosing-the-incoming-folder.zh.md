# Agent Note: 往输入框粘贴文件，以及选择它的落点

Status: implemented

## Problem

两条要求来自实机 Windows 打包版的使用，说的都是同一件事：一件用户本来只能绕远路做的事。

**已经在剪贴板里的文件，粘不进来。** 输入框能*发送*文件，但只有回形针按钮一条路——它打开
的是操作系统自己的文件选择器。在资源管理器里复制的文件、截下来的图、从浏览器里复制的图片，
这些都已经在剪贴板上了，而在消息框里按 Ctrl+V 对它们毫无反应。也不可能反应得了：Flutter
自带的 `Clipboard` 在每个平台上都只读写**文本**，别的什么都不碰，所以文件和图片不是「没处理」，
而是对输入框根本不可见。通往一条消息的唯一道路，是先把它存到磁盘上再手动挑一次。

**接收文件的目录只能手打。** 设置界面把它（`factReceivedFiles`）当成一条事实报出来，仅此而
已；接收流程背后的对话框也只是一个文本框。`askForDirectory` 压根没有办法够到平台自己的文件
夹选择器。一个只能手输的目录，就是大多数人设不了的目录：目录的路径不是一个人记得住的东西，
网络共享更不是他能拼出来的东西。

## Decision

**输入框接管 Ctrl+V，并先把剪贴板交给会话。** `_ComposerField` 新增
`PasteIntoComposerIntent`，同时绑到 Ctrl+V 和 Cmd+V，于是这个组合键在 `TextField` 自己的粘贴
**之上**被应答，而不是与之并存。`ConversationComposer.onPaste` 调用
`_ConversationViewState._pasteIntoComposer`，它经由下面那道缝读剪贴板，并**返回它到底发出去
没有**——先文件，后图片。当答案是否的时候——没有对端、没有文件、没有图片——文本框原本的文本
粘贴会在 `_pasteText` 里被手工复现，连「替换选区、光标落在插入内容之后」这条规则一起，因为
接管组合键恰恰就是让框架自己的粘贴再也跑不起来的原因。所以只装着文本的剪贴板行为不变；新的
是装着文件或图片的剪贴板会变成一条消息。

**剪贴板经由一道缝来读。** `lib/ui/clipboard_paste.dart` 定义 `ClipboardPaste`（`files()`
返回路径，`image()` 返回编码后的字节），由 `SystemClipboardPaste` 实现于 `pasteboard` 插件
之上，并以 `PasteResolution` 作为替换点。这与 `FilePicker`/`PickerResolution` 是同一个形状，
理由也相同：平台通道在 `testWidgets` 函数体里没法应答，所以测试替换不掉的剪贴板，就是测试驱动
不了的流程。`pasteboard` 是在 Windows 上能看见文件和图片（`CF_HDROP` 与 `CF_DIB`）的那个插件；
Flutter 自带的 `Clipboard` 看不见。

**粘进来的图片按字节命名。** 截图过来时完全没有名字，所以 `lib/ui/pasted_image.dart` 嗅探
PNG/BMP/JPEG/GIF/WebP 的魔数（`imageExtensionOf`），把字节写到临时目录下的
`pasted-<微秒>.<扩展名>`（`writePastedImage`）。把它写下来，是它成为一次 Transfer 的原因：
引擎给出摘要、从路径流式读取，而图片在下面任何一层都不是特例。对于画不出来的字节，这个函数
回答 `null`，那是调用方「原来这并不是一张图」的信号；它不用扩展名兜底，是因为把 `.png` 这个
名字安在一枚 JPEG 的字节上，只会得到一张注定画不出来的气泡。

**接收目录成为一条 profile 偏好，而且可以被选出来。** `DeviceProfile.incomingDirectory`
——null 表示「用平台默认」——会被持久化（写成**缺失的键**，绝不写成显式的 null），并通过
`LocalTransferController.incomingDirectory` / `setIncomingDirectory` 暴露出去。`HomeShell`
把 `controller.incomingDirectory ?? seams.defaultIncomingDirectory` **解析一次**，把那个值交给
三个页面，于是「接收的文件去哪儿」在运行中的应用里只有一个答案。`SettingsPage` 把它显示出来，
配一句说明当前是「已选」还是「未选」的提示，以及一个「更改…」按钮，打开的是**同一个**
`askForDirectory` 对话框——接收流程用的也是它，这样一个文件夹无论提前设置还是在文件到达时
回答，都是用同一种方式选出来的。`_DirectoryDialog` 新增「选择文件夹…」按钮，走
`FilePicker.directory()`（`getDirectoryPath`），它只把结果**填进**输入框而不直接提交：输入框
保持着可编辑，以便填一个原生对话框够不到的路径。

## Alternatives considered

**把文本粘贴留给框架，文件和图片另走一条路。** 没有那样一条路可走：组合键到达的是获得焦点的
输入框，而输入框的粘贴只认文本。接管组合键并手工复现文本那一种情况，是两者都能成立的唯一形状。

**把粘进来的图片按字节发出去，而不是写一个临时文件。** Transfer 是从路径读的——offer、摘要、
sink——把裸字节穿进去，等于为了一个调用方多造一种「成为 Transfer 的方式」。那个文件是被故意
留下的：发送方自己的气泡正指着它。

**字节不是已知图片时，猜一个扩展名。** 一个对字节撒谎的名字，比一条消息都没有更糟；那张气泡
只会画不出来，而失败会出现在离原因很远的地方。

**在每个需要它的页面里各自解析接收目录。** 三个页面各写一次 `?? 默认值`，就是一个设置的三次
意见分歧的机会。外壳解析一次，传值下去。

**让文件夹选择器的结果立刻提交，不经对话框。** 这个对话框与接收流程共用，而那里用户正处在
一次决定中间；把答案填进输入框，既保住了一次确认，也保住了路径的可编辑——选择器看不到的共享
目录还得靠它。

**为新的载荷形态提升 `wireProtocolVersion`。** 没有提升，也没什么可提升的：粘进来的文件按
文件走，粘进来的图片按图片走，两者线上本来就都承载得了。提升版本会拒掉那些本来工作得好好的
对端，把一处显示差异换成一次连接失败。

## Consequences

**Ctrl+V 现在有两重含义，由剪贴板决定。** 剪贴板上是文件或图片时，Ctrl+V 发出一条消息，消息框
里什么也不留；上面是文本时，Ctrl+V 照旧粘进框里。这正是那条要求要的行为，也是它唯一的意外
后果：同一个组合键并不总会让消息框发生变化。兜底的那条路才是让寻常情况保持寻常的东西，也正是
最容易无声坏掉的一环——所以有一个测试在只装着文本的剪贴板上按真实的 Ctrl+V，并断言文本落进了
框里。

**文本粘贴这条路径现在是应用的代码，不再是框架的。** `_pasteText` 重新实现了 `TextField` 的
规则（替换选区、光标落在插入内容之后）。它必须与文本框的行为保持同步，而它只在兜底路径上
运行——于是它退化了，只粘文件的用户根本看不见。

**粘进来的图片会在临时目录里留下一个文件。** 这是故意的——发送方的气泡要照那个路径作画——也
就意味着粘一下午截图会攒下一批由操作系统回收、而非由应用回收的文件。文件名以时钟为种子并带
冲突后缀，因为同一微秒内的两次粘贴否则会共用一个路径，第二次写入会把第一次 Transfer 还在
读的文件截断。

**`flutter test test_flutter` 在这台机器上又能跑了，而它一直藏着两处潜伏的失败——都在本次改动
中修好了。** 深信服对本机 loopback 的干扰消失后，widget 套件跑得起来了，其中两个用例因与本
功能毫无关系的原因失败。两者都已用**未修改的**测试文件、对着 HEAD 的 `conversation_view.dart`
与 `home_shell.dart` 复跑，确认是既有的：

* `two_window_e2e_test.dart` **在 `testWidgets` 函数体里**调用了
  `tearDown(PickerResolution.reset)`。`tearDown` 声明的是一个钩子，只在套件仍处于声明阶段时
  有效，所以那次调用抛出 `Bad state: Can't call tearDown() once tests have begun running`，
  在一行都没跑之前就让用例失败——也就是说，这条端到端传文件用例**从来就没有真正跑过**。现在
  改成了 `addTearDown`，用例通过。
* `pages_test.dart` 的「Enter 发送并把光标留在框里」在发送落地的那一帧断言了 `hasFocus`。
  `_ConversationComposerState._send` 是在**帧后回调**里重新请求焦点的——这是故意的，好让请求
  落在重建输入框的那一帧之后——所以光标晚一帧才回来。一个探针确认再加一次 pump 之后
  `hasFocus` 就为真。该用例现在等待这个有文档记载的行为，而不是早一帧去断言它；产品本身从来
  没错。

## Testing

`test/ui/pasted_image_test.dart`（新增，纯 Dart——它必须能被 `dart test` 加载）钉住每种格式的
魔数嗅探、那些不得被误认成的近似字节，以及 `writePastedImage` 按字节给文件命名、并拒绝它画不
出来的东西。

`test/profile/device_profile_test.dart` 钉住接收目录：初始未设、设置后记住、去空白、空或纯空白
回答即清空、未设时不出现在 JSON 里、键缺失时解码为未设，以及往返之后仍然保留。

`test_flutter/ui/pages_test.dart` 按人的操作方式驱动流程。剪贴板上的一个文件和一张截图各自
变成一条消息，走的是**真实的 Ctrl+V**，对象是 `ScriptedClipboard`——被断言的不只是它做了什么，
还有快捷键表本身。只装着文本的剪贴板仍然粘进框里，并且什么也不发送。设置页的文件夹按钮经由
`ScriptedPicker` 驱动平台选择器并记住答案，而被取消的对话框什么也不改变。
