# Agent Note: 接受就是批准的全部

Status: implemented

[English](2026-09-30-accepting-the-request-is-the-whole-approval.md) | 中文

## Problem

配对已经不需要输码了，但仍然以一次比对收尾：两台设备各自画出握手派生的六位
数，双方用户都要确认两边屏幕一致，然后才有一侧提交。于是「应答」的那个人做了
一个决定，紧接着又被递来第二个——同一份请求、同一个答案，这一步之所以存在，
只是因为这条流程一直都有它。

为六位数辩护的理由也被夸大了，值得把它说准。**不管来电的是谁**，两块屏幕都会
显示同一组数字：这串值是握手和两个指纹共同派生的，而来电方送来的指纹是一句
自称，不是事实。链路上一个陌生设备拨通本机、走到提问这一步，它看到的数字与本
机显示给它的一模一样。两块屏幕的比对真正能抓住的是**中继**——第三个设备夹在两
个人中间，各跑半次握手。它从来没能抓住界面真正要回答的那个情形：链路上有台设
备发起了配对，得有人决定放不放它进来。

而那个人看到的，是来电方自称的名字，以及同一句话里写明的「这名字只是自称」。
那句话加上那一次点击，就是准入检查。它下面再画一个两边本来就必然一致的数字，
等于是把它说成了比这更重要的东西。

## Decision

提问只有两个答案，没有第三步。`PairingRequest.admit()` 与
`PairingAttempt.confirm()` 现在由同一个按钮连着跑完
（`l10n.acceptPairing`、`l10n.refuse`），发起方也在自己的用户点过之后立即
自行确认——两边都不再等一次并不发生的比对。

* `_PairingRequestDialog` 只剩一个状态：已提问，然后已了结。它的「接受」对同一个
  attempt 先调 `admit()` 再调 `confirm()`，交换期间显示
  `l10n.pairingCompleting`。`_PairWithPeerDialog` 对 `pairWith()` 交回的
  attempt 做同样的事，然后照旧打开 Session（`connectAfterPairing`）。
* 短认证串仍然派生，仍然在链路上承重。`SecureLink.shortAuthenticationString`
  喂给 `_pairingContext`，配对就是在这上面签准入手信——`pair ` 加两个按序排列
  的指纹、再加这串数字——所以两侧必须仍然商定同一个值签名才能通过验证，而一份
  签名也无法从一次握手挪到另一次。消失的是**展示**：`PairingOutcome.sas` 与
  `PairingAttempt.sas` 仍然携带它，没有任何屏幕读它们。
* 展示它的组件已删除，连同指代这一步的文案：`_BigCode`、`_Confirmation`、
  `compareDigits`、`theyMatch`、`pairingPreparing`、`continuePairing`、
  `cancelThisPairing`。
* 应答方把来电方移入的那个阶段不再叫「比对」——`_Receiving.decide` 及其
  `_deciding` 集合——因为接下来发生的并不是比对。

补偿控制就是原本就在的那些，而且值得点名，因为它们现在就是全部：提问上写着
来电方自称的名字、以及「这是自称」那句话；它就是一个用户能拒绝的普通对话框；
应答可以在设置里关掉，且这个偏好扛得过重启；而应答方只把设备组秘密交给一个
它已经读过准入消息的对端。

## Alternatives considered

**把六位数藏在「查看详情」的折叠里。** 否决：这个检查只有在真有人去做的时
候才有价值，而应用无法知道有没有人做过。一个可选的、无法核实的、并且被所有
「本就不懂它为什么重要」的人跳过的控制，比没有控制更糟——因为它仍然被文档记
为一道控制。

**在应答方的最终屏幕上、答复之后显示六位数。** 否决：那它们就出现在本该由它们
来支撑的那个决定**之后**。

**只在应答方还没有设备组时才显示六位数。** 否决：为一个六位数本来就不覆盖的威胁
增加状态。来电的是谁，两块屏幕都会一致，所以限制**何时**显示并不能让它变成对
**谁**在提问的检查。

**让监听器自动放行来电方，一次点击都不要。** 否决：那就是「谁先问谁进来」。
那次点击就是准入闸门本身，所以去掉六位数并不会让它变成可选——而是让它成为仅
剩的那一样东西。

## Consequences

- 配对总共两次点击，每台设备一次：在设备卡片上点 **Pair**，在另一台上点
  **接受 / Accept**。不再有从一个屏幕读出来、拿去和另一个屏幕比对的东西。
- 负向保证，直说：链路上任何一台设备，只要完成开放握手、并让一个人答了「接
  受」，它就进组了。六位数从来没有覆盖这个情形。用户真正失去的，是靠比对两块
  屏幕发现夹在两台真设备之间的中继的能力。
- 输码路径的性质没有变——不知道短码的对端根本无法完成握手——而「录下一次输码
  配对后可离线穷举约 50 位」这个上限仍然成立，这也是该路径继续当兜底的原因。
- `test_flutter/ui/pages_test.dart` 从屏幕上把两半都钉住：允许请求就是配对的
  全部，拒绝则谁都没配上。共享脚手架 `pairThroughWindows` 点的是「接受」按钮，
  并等待两侧都报告 `isPaired` 与 `isServing`，所以双窗口端到端测试走的就是人会
  点的那一次点击。
- 密钥规则没有变化，包括本流程依赖的那一条：应答方先读完对端的准入消息，再决定
  交出哪个秘密。它们由
  [配对改为点击式，不再输码](2026-09-30-click-to-pair-no-more-typing.zh.md)
  负责，本笔记是从它手里接过「确认」这一步的。
