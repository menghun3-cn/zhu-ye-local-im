# Agent Note: 拖进来的文件和选好的文件一样，先在输入框里等着

Status: implemented

## Problem

输入框有好几条进文件的路，但规则不一致。点回形针、粘贴 —— 以及
[选好的文件先在输入框里等着](2026-10-09-a-picked-file-waits-in-the-composer.md)
之后的暂存 —— 都落在附件托盘里，等「发送」。而拖拽是例外：拖到会话历史区上，
松手那一刻就发出去了（`_sendDropped`）；拖到输入框本身上则什么都不发生，
因为 `DropTarget` 只包着历史区。同一个框，两条路，两种承诺 —— 而且拖放那条
路甚至没有盖住整个框。

## Decision

**一条进路，一条规则。** `DropTarget` 现在包住历史区**和**输入框 —— 顶部
header 仍在外面，因为它是框架而不是写消息的地方 —— `onDragDone` 以
`_stagePaths` 收尾，和选择器、粘贴是同一个调用。拖进来的文件出现在附件托盘里，
只有按下「发送」才会发出。`_sendDropped` 已删除：不再存在「拖放即发送」这条路。

**遮罩说的是拖放实际做的事。** 它盖住整个拖放区域，写「松手加入输入框」
（`dropToAttach`），取代「松手即发送」（`dropToSend`）；图标也从
`file_download_outlined` 换成 `attach_file` —— 两者都是因为承诺从「发送」
变成了「加入」。

**这反转了
[选好的文件先在输入框里等着](2026-10-09-a-picked-file-waits-in-the-composer.md)
的拖放那一半。** 那篇笔记里「拖进来的文件仍然立刻发送」不再成立；按
implemented 笔记的规则，反转要写新笔记而不是改写旧笔记，所以旧笔记原地更新、
在此互链。

**`classifyDrop` 已删除。** 它已经没有调用方 —— 拖放路径和其它所有进路一样，
都经由 `classifyPaths` 分类。

## Alternatives considered

**保留拖放即发送，只是把目标放大。** 否决：同一个框仍是两条规则 —— 拖放即发、
选择即等 —— 而区别从来不在用户的意图，只在文件走的是哪条路。需求是让拖放
和输入框的其它进路行为一致。

**输入框上松手=暂存，历史区上松手=即发。** 否决：两套遮罩、两种承诺，而且
同一个目标的含义会随落点所在的像素而变。一个拖放区域、一条规则，才是用户
能预期的版本。

**保留 `dropToSend` 这个 key、只改文案。** 否决：一个叫「发送」的 key 盖在
「加入」的行为上，和「一个选择器」那篇笔记已经删过一次的是同一种谎。打包
探针清单（`scripts/packaging-probes.json`）记的是 key，所以它随改名一起动了。

## Consequences

**得到的。**「不点发送什么都不出去」现在是一条没有例外的规则：选择、粘贴、
拖放全部先暂存。拖放区域也盖住了输入框 —— 拖到输入框上本来就是人们预期
会落的地方。

**代价。** 拖放比以前多一个动作 —— 要再点一次「发送」—— 而且学会过
「松手就没了」的用户要重新学会看托盘。缓解是遮罩文案：文件还在半空时，
新承诺就写在遮罩上。

**测试。** `test_flutter/ui/pages_test.dart` 新增「a dropped file waits until
发送 is pressed」：直接以 `DropDoneDetails` 调用 `DropTarget` 的 `onDragDone`
—— 操作系统的拖拽在 widget 测试里驱动不了 —— 文件出现在托盘里且此时没有
任何 Transfer，按下「发送」之后才产生。
