# Agent Note: 应用自己安装自己的更新

Status: implemented

## Problem

程序已经能告诉用户「有新版本」，却给不了。侧栏把「更新」钉在目的地下面，关于页把答案
变成一句话并给了下载页 —— 接下来的活全是用户的：离开程序、找到发布页、从七个附件里
认哪个才是自己这种形态的包、下载、然后手工换目录（绿色包）或者跑安装包（安装版）。
需求是一句话 —— 应用内一键下载/静默替换/重启 —— 而这句话说的是一个动作。

让它不只是一个下载按钮的，是三件关于平台和本仓库的事实。

**Windows 上运行中的程序不能覆盖自己。** `local_transfer.exe`、
`flutter_windows.dll`、`data\app.so` 在进程存活期间都是打开的，而且从进程内部没法
关掉它们。任何跑在**这个程序里面**的东西，都没法把新包放进旧包所在的位置。

**两种形态的包，两个不同的主人。** **安装版**归它的安装器管：卸载项里记着版本号，
背着安装器换文件会让那个版本号变成假话 —— 诚实的升级方式是跑新安装包、让它自己干。
**绿色包**没有安装器，也没人可以问。

**发布页上有个不能认错的文件。** 每个附件都发两遍：一遍是带版本号的名字，一遍是固定
名的别名，而别名的后缀和带版本号的那个**完全一样**。按 `.zip` 匹配的选法等于按 API
恰好列出那七个文件的顺序来选。

## Decision

**第二个进程就是刚下载下来的那个包。** 它被解到自己的目录里，带
`--apply-update --staged <目录> --target <目录>` 启动，然后等旧的那个走掉，再把自己
盖到位。不是脚本、也不是随程序附带的小助手：本产品不打任何解释器进去，也不想为了这事
起一个；而一个助手本身还得靠它要实现的那套机制来更新。由此带来的结果是这件事的**特性**
—— *完成更新的代码，是写得最新的那版代码* —— 于是对这套机制的修复，会搭着它所在的那
次更新一起到达需要它的机器。

**只在 Windows 上，而且在任何 await 之前就说清楚。** `supported` 就是
`Platform.isWindows`，同步读出来，于是关于页可以**整个不提这个入口**，而不是画一个
按下去只会得到一句「失败了」的按钮。干不了活的按钮比没有按钮更糟。

**该取哪个包，由一个文件回答。** `安装说明.txt` 在安装版里有、在绿色包里没有，因为
`packaging/local_transfer.iss` 会把它拷进去，而 `scripts/pack-windows-portable.ps1`
不会。另一条路 —— 读卸载注册表键 —— 机器更多、要下到原生侧，而且回答的是一件目录里的
一个文件已经回答了的事。

**附件是按名字**点名**的，不是匹配来的。** `updateAssetName` 用发布页报出的 tag 拼出
`LocalTransfer-<版本>-windows-x64-portable.zip` 或 `…-setup.exe`，`updateAssetFor`
照着这个名字精确找。那个 tag 就是答案里本来就带着的版本号，没有需要推断的东西。

**校验和来自发布接口本身。** GitHub 在每个附件上返回 `digest: "sha256:<hex>"`（对着
已发布的 v0.1.1 核过：七个附件全有），于是「期望的哈希」是跟着「点名文件的那个答案」
一起来的。发布页没给 digest 的，**拒绝更新**（`UpdateInstallFailure.noDigest`），而不是
信它。这是刻意的：正在取的那些字节马上要被盖到正在运行的程序上，而「它来自我们自己拼出
的 URL」在 URL 会被重定向到 CDN 的前提下根本不算一次检查。以 `.sha256` 侧车为来源被否掉
了 —— 它只存在于 `latest` 别名上，用它就意味着要么去调和两个可能互相打架的答案，要么
为每个带版本号的文件都发一个别名。

**先校验才解包，先解包才替换。** `_download` → `_matchesDigest` → `_unpack` →
`isAPackage` → `dropStagedTree`。每一步都能拒绝，而四种拒绝是四句不同的话。

**交接分两相落树。** 新包的每个文件先以 `.ltnew` 后缀拷到它要去的位置旁边 —— 这一相里
目标目录**一个字节都没动** —— 之后才把这些后缀改名去掉。因此拷贝阶段的失败（盘满了、
那个目录其实不可写）会让正在运行的这版包原封不动，要收拾的只有垃圾；只有改名可能留下
混合态，而改名不搬运字节，这就是在不额外要一个目录、不中间重启一次的前提下能做出来的
最短窗口。改名会重试（40 次、每次隔 250ms），因为被替换的那版刚被要求退出，而 Windows
会一直占着程序的文件，直到运行它们的进程消失。

**原生 runner 在单实例检查之前先读命令行。** 为完成更新的那次启动改两件事，两件都是因为
它要替换的那份**还在运行**：它不是本程序的第二份拷贝（因此必须跳过
`HostShell::AcquireSingleInstance` —— 否则新包会找到旧窗口、把焦点交给它、然后静默退出），
以及它不能被一次点击关掉（因此 `SetQuitOnClose(false)` —— 一次把进程砍在半路的点击会让
目录里各留一半）。控制台附加保持在最前；`main.cpp` 保持纯 ASCII，因为 `windows/runner`
下的源文件里一个非 ASCII 字节在 CP936 下就是 `C4819`、再往后是 `C2220`，而六道门禁根本
不编译 `windows/**`。

**`main()` 在打开任何东西之前先回答那个旗标。** `UpdateHandoff.parse` 跑在装缝之前：
一次交接不开任何 socket、不绑任何端口、不问平台要任何目录 —— 这正是重点，因为它要替换的
那版还占着发现端口。它确实会开一个窗口：旧窗口关掉到新窗口打开之间的这段，覆盖了拷一份
完整的应用加一次重启，一台这么久什么都不显示的机器读起来就是崩了。那个窗口也是唯一能报
出失败的地方 —— 到那时旧版已经没了，新版还没到位。

**安装版把活交给 Inno Setup，而安装器必须把程序带回来。**
`Process.start(setup, ['/SILENT', '/SUPPRESSMSGBOXES', '/NORESTART', '/update'])`。
原来那条 `[Run]` 带着 `skipifsilent`，于是静默安装换完文件、没人重新拉起程序 ——
`local_transfer.iss` 因此加了一条 `[Run]`，判据是 `[Code]` 里的
`UpdateWasRequested() = WizardSilent and CmdLineParamExists('/update')`。`/update`
这个参数就是让那条只在「本程序自己发起的安装」时生效的东西：脚本化的 `/SILENT` 安装仍然
只是安装，而交互安装仍然归第一条管。

**解包用系统的 `tar -xf`。** Windows 10 1803 —— 本程序本来就要求这个版本 —— 自带能读
zip 的 `bsdtar`。在 Dart 里写个 zip 阅读器，等于为了读一个这台机器已经能读的文件写几百行
代码，而且那几百行还得在路径、编码、权限上都对。

**进度是一个阶段，下载时再加两个字节数。** 用封闭集合（`UpdateInstallStage`）而不是
一句话，理由和 `UpdateOutcome` 一样：把阶段变成词属于知道用户读什么语言的那一层。
长度未知时 `fraction` 是 null，这就是为什么除下载以外的每一步进度条都是不确定式的
—— 那些步骤确实没有长度。

**死掉的交接只留一个文件，读一次。** `.update-failed.txt` 由失败的那个窗口写进目标目录，
下次启动 `previousFailure()` 读走即删，所以那句话只出现一次。没有它，一次失败交接留下的
唯一痕迹就是一个来了又走的窗口。

**交接留下的东西在下次启动时清掉。** `clearStaleUpdateStages` 删掉系统临时目录下
`local_transfer_update_*` 前缀、且修改时间早于一小时的目录。它在 `main()` 里以
`unawaited` 启动 —— 打扫不能挡着首帧 —— 而那个时间上限正是让它不会删掉**此刻正在跑**
的交接的暂存目录，那是个正在被执行着的目录。

## Testing

`test/ui/update_install_test.dart`（纯 Dart，无 widget）覆盖纯净的那部分：两种形态各取
哪个文件、被落下的 `.ltnew` 不算暂存包的一部分、`isAPackage` 收什么拒什么、
`dropStagedTree` 会覆盖旧内容**并且**在拷贝阶段抛错时目标目录一个字节都没动、
`UpdateHandoff.parse` 把只带旗标没带目录的命令行读成交接而不是普通启动、报告被读一次就
没了、以及陈旧暂存的清扫同时按前缀**和**按时间。

`test/ui/update_check_test.dart` 也是新的：`parseRelease`/`parseAssets` 对手写 JSON，
`GitHubUpdateChecker` 对本地 `HttpServer`（widget 测试没法替掉一个响应，而重点是 404 和
500 会得出两个不同的答案）。

`test_flutter/ui/about_page_test.dart` 覆盖那张卡片：入口只在「已经知道有新版本」**并且**
「本版能替换自己」时才出现；按下它会把这一页手上的答案交给安装器；下载中会显示字节数；
每种失败都各自成句并且按钮再次提供；以及一次死掉的交接留下了什么会被说出来。

有一个坑值得记下来，因为它吃掉了一轮：交接阶段画的是
`LinearProgressIndicator(value: null)` —— 一根不确定式进度条，只要在屏上就一直动 ——
所以测试按下安装按钮之后再 `pumpAndSettle` 永远等不到静止。等树安静下来，等于在等一个
正在退出的进程。于是改成显式两帧，理由写在那个 helper 旁边。

## Alternatives considered

**一个 `.bat` 或 PowerShell 脚本，等旧进程结束后拷文件。** 否掉：本产品不打解释器进去，
而一个必须靠它所实现的机制来更新的脚本，只是把同一个问题下移了一层。

**随程序放一个小更新器 exe。** 否掉：它得靠它要更新的东西来更新自己。把它塞进发布包里
只能解决「已经有新版的那些机器」。

**`.sha256` 侧车文件。** 作为期望哈希的**来源**否掉 —— 见 Decision。作为**想法**没有
否掉：本实现只是把同一个事实从「已经点名文件的那个答案」里取，缺了就拒绝。

**按后缀挑附件。** 否掉：别名和带版本号的文件共享后缀，选谁就取决于 API 列出它们的顺序。

**把下载的字节直接写进程序目录。** 否掉：那样一次下到一半的下载、或者一个其实不是包的
东西，会在任何人注意到之前就把正在运行的那版毁掉。

**删掉新版已经没有的文件。** 暂时否掉：这需要一份「旧版曾经发布过什么」的清单，而目前
没有任何东西在写它。后果是一次更新可能留下陈旧文件，这件事写在这里，而不是以后被发现。

**手工替换安装版的文件，而不跑它的安装器。** 否掉：卸载项会一直报着旧版本号，之后的
修复/卸载都会从一个混合体上开工。

**为这事单独写一份 sha256，或者只为它引入 `package:crypto`。** 这不是一个能成立的选择：
`crypto` 本来就在依赖里，而 `sha256.bind(file.openRead())` 能流式处理 20MB 而不整份读进
内存。

**用 `package:http` 下载。** 否掉：`HttpClient` 在 `dart:io` 里，而这段代码为了 `File`
和 `Process` 本来就已经 import 了它；而且数字节的回调要的就是裸流，不是它上面的一层包装。

**在帧所在的 isolate 上做拷贝。** 否掉：那是几千个文件，而转圈是唯一在告诉用户「这不是
崩溃」的东西。

**按 pid 等旧进程，而不是重试改名。** 否掉：交接并不保证知道 pid —— 而且 pid 也不是关键
所在。关键是这个文件**此刻**能不能改名，而这正是重试在问的问题。

**用「真操作一次」来判断目录可不可写。** 用探针文件否掉：探针可以在 20MB 下载**之前**
试，而这就是当初要问这件事的原因。

**加回滚：留一份旧包，失败了再放回去。** 否掉：磁盘代价翻倍，而报告文件覆盖了用户真正
需要的东西 —— 被明确告知。两相落树才是把这个窗口压小的东西。

**在交接窗口里显示文件计数。** 否掉：拷贝在另一个 isolate 上，逐文件汇报要开 port 和
`Stream`，只为给一个没人能据以行动的数字。窗口说的是「正在发生什么」，用户需要的就这个。

## Consequences

**换来了什么。** 被告知有新版本的用户，不用离开程序就能拿到它；而两种形态各自得到尊重
「文件归谁管」的那种升级方式。

**开发树是第三种形态。** 由 `flutter build windows --release` 产出、并在它自己的目录里
运行的那种包没有 `安装说明.txt`，于是被当成绿色包：在这样的树上按那个按钮，会就地替换
`build\windows\x64\runner\Release`。它只有「自己构建过这个应用、然后又按了一个写着
『下载并更新』的按钮」的人才会碰到，而且重新构建就能恢复 —— 但这是「以标记文件判形态」
这条规则的真实后果；另一条路（既没标记也没有 `使用说明.txt` 就拒绝）会连绿色包一起拒掉，
而那恰恰是最需要这个功能的形态。

**没有回滚，两相落树就是全部的缓解。** 从第一次改名到最后一次之间，目录里是混合态。
在那里的失败会留下 `.ltnew` 和一个换了一半的包，下次启动读到的报告会说出来。这是设计
决定而不是疏忽：唯一完整的答案是原子地换目录，而 Windows 对一个打开着的目录不提供这个。

**安装版能不能成功，现在取决于 Inno Setup 的参数。** `/SILENT` `/SUPPRESSMSGBOXES`
`/NORESTART` `/update` 就是契约，而那个 `[Code]` 函数是让「重新拉起程序」只对这个调用者
生效的东西。将来某次安装脚本改动如果重命名了 `[Run]` 条目或者丢掉了 `WizardSilent`，
会让重新拉起静默失效 —— 文件是对的，窗口不回来。

**又一件只能靠真跑来验的东西。** 原生那一半 —— 被跳过的单实例检查、不因关闭而退出的
窗口、`--apply-update` 能不能活着穿过 `GetCommandLineArguments` —— 六道门禁一道都不覆盖，
它们根本不编译 `windows/**`。它是靠构建 release、跑打包脚本的冒烟测试核的；而旗标到达
Dart 这一条，由同一个脚本的字符串探针核 —— 那里现在多了两句新句子。

**两个缝，不是一个。** `UpdateInstallResolution` 与 `UpdateResolution` 并列，而不是塞进
它里面：问版本在 `update_check.dart`，做替换在 `update_install.dart`，把两者合成一个名字
只会让其中一个文件为了那个 resolution 对象去 import 另一个。每个 pump 关于页的 widget
测试现在都得装一个 `ScriptedUpdateInstaller`，因为 `supported` 是在构建卡片时读的。

**关于页多了一个按钮和一句话。** 手工升级的说明仍然在卡片上，而解释那个按钮的提示只在
按钮出现时才替换掉它 —— 见 `aboutUpdateInstallHint` 与 `aboutHowToUpgrade`。显示哪一句
用的就是「决定这个入口到底存不存在」的同一个条件。
