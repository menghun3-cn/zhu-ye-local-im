# Agent Note: 对话在进程结束之后依然存在

Status: implemented

## Problem

对话从来没有被写下来过。`LocalTransferController` 把本次运行参与过的每一个传输都当作 `_Tracked`
放在一个列表里，会话列表和会话视图都读这个列表，于是进程结束就是对话结束。由此产生两个后果，使用者
用上一天就会各遇到一次。

**重启会把每一个会话清空。** 一台跟另一台聊了一上午的设备，回来时什么都没有：同一个对端、同一个
名字、标题里还是同一个地址，底下却没有历史。传输页也一样糟糕——它过滤的是同一个列表。

**列表上限是一百条，而这个上限会删掉历史。** `_pruneTransfers` 在列表超过一百条时丢弃已结算的记录，
这对一份「活动列表」是对的，对「唯一的一份记录」是错的：一个活跃的会话会悄悄忘掉自己的开头。

除此之外，当时根本没有办法把某一条消息从屏幕上拿掉。右键只提供「给我看看那个文件在哪」和「复制那张
图片」，以及发送还在途中的「停止发送」——而对文本消息（也就是绝大多数消息）什么都没有：菜单压根不会
打开，因为一个会弹出空菜单的处理器会吞掉那次用来选中名字复制的右键。

## Decision

**消息在结束时被记住，记住的是一份记录，而不是一个句柄。** 结算是一个传输变成历史的时刻，也是唯一
一个真有东西值得留下的时刻：在那之前，一条消息要么是一个别人还在等的问句，要么是还没到达的字节。
因此 `MessageRecord` 只持有「一条已经结束的消息在会话里会显示什么」——谁、什么类型、何时到达、何时
结束、怎么结束、条目、文本的正文，以及它的字节落在了哪里——不带任何活动部分。使用者还能答复的 offer
和使用者还能停下的 send 都属于某个会话（Session）的对象，而会话同样活不过进程。

**对话写进自己的文件 `messages.json`，就在 `profile.json` 旁边。** 同一个目录，因为两者都属于这台
安装的每用户状态，而不是使用者的文档。不同的文件，因为两者彼此毫无关系：配置文件里装的是一个丢不起的
身份，且极少重写；对话则每有人打字就变一次，而且重新聊一遍就能重建。`MessageStore` 与 `ProfileStore`
同形——一个接口、两个实现，`FileMessageStore` 先写临时文件再改名；不能解码的文件被移到 `.corrupt`
并在 `notices` 里报告——一段对话不值得为它拒绝启动。

**每次都整份写出。** 归档每条消息一次，删除每次一次；一个人每分钟最多也就发几条消息。在这个频率下
日志式写入什么也买不到，而一个「永远是旧列表或新列表」的单文件，是读者可以信任的文件。列表从最旧的
一端起以 `maxRememberedMessages`（1000）为界——那一端正是人早就翻过去的一端。

**`transfers` 是活动列表与记录的合并，按句柄（handle）连接。** 当前运行里的消息由它的 `_Tracked`
绘制，因为那才是能报告真实状态和真实字节数的东西；来自更早一次运行的消息由它的记录绘制，那里每一个
被接受的字节都已到达，进度就是 1。只要两者同时存在，它们描述的就是同一条消息——归档并不会把它从活动
列表里拿掉——所以它们是按 `TransferView.handle` 连接而不是拼接，且以活动的那份为准。排序按 `at`
由新到旧，以 id 作为并列时的次序：`List.sort` 不是稳定排序，否则同一毫秒落章的两条消息会在有人正看着
的时候互换位置。

**句柄由对端和传输 id 组成。** id 是随机生成的，且只在**承载它的那个会话内**唯一，而会话不是一辈子：
重新打开一个会话再发一次会产生新的 id，而那两次会话是同一个对话。能穿越每一个会话的是对端，所以是
这一对在给一条被记住的消息命名。分隔符是 NUL——指纹和十六进制 id 都不可能含有它。

**删除一条消息是本地的、单向的、无条件的。** 它把消息从活动列表和记录里同时取出，把对话写出去，并且
不告诉对端任何事——协议里没有这种消息，也不该有，因为一段任何一端都能改写的对话，是两端无法被信任为
一致的对话。字节留在原处：收到的图片仍然是使用者拥有的文件，而使用者见过的每一个通讯应用里，「删除
这条消息」的意思都是「从我的屏幕上拿掉」。

**在还在传输时被删除的消息，保持已删除。** 传输本身继续跑：直到它结束为止，它归引擎所有，而停下它是
**另一个**动作——同一个菜单在上面一行就提供。因此记录被打上标记（`_Tracked.dismissed`），而那个本来
会归档它的回调会检查这个标记——没有这一条，结局会在使用者刚删掉之后的一瞬间把消息放回屏幕。

**每条消息都提供「删除」，因此右键总是被接管。** 对文本消息来说这是有意的行为改变——它过去会把右键
放行，好让人选中名字去复制。现在菜单里总归有东西，所以那条「防止空菜单吞掉手势」的守卫已经没有任何
适用情形。

**文本消息的正文画成普通文本，复制它这件事移进了菜单。** `SelectableText` 自带一个手势识别器，而
Flutter 把一次点击交给手势竞技场里最内层的成员——于是在文字上点右键会弹出平台自己的「复制 / 全选」
工具条，永远到不了消息的菜单。「删除」就会变成在除了最常发送的那一类消息之外的所有消息上都能用。因此
正文画成 `Text`，而「复制文字」与图片的「复制图片」并排放在同一个共享菜单里：这个能力是搬家，不是被
丢掉；而且现在复制的是整条消息，而不是指针恰好落在的那几个字。

## Alternatives considered

**把对话放进 `profile.json`。** 否决：两者的写入节奏与价值正好相反。配置文件极少重写，装的是身份种子
和组密钥；对话每结束一条消息就要重写一次。共用一个文件意味着一次损坏或被截断的对话可能让设备丢掉它的
身份，而这是本产品唯一无法恢复的损失——配置文件存储自己的文档注释也正是这么说的，解释它为什么把损坏
的配置移开而不是覆盖。

**把 `Transfer` 或 `TransferView` 原样序列化。** 否决：两者都持有活动对象——流、completer、offer
和 send。一条被记住的消息按定义没有任何活动部分，而一个携带它们的格式，等于在每一次重启时承诺恢复
无法恢复的东西。

**把未答复的 offer 也记住。** 否决：offer 是一个**对方**正在等的问句，而对方已经不等了——它的会话
随着先结束的那个进程一起死了。恢复它会把「接受 / 拒绝」两个按钮画在屏幕上，去对应一个没人会答复的
传输，而按下按钮就会失败。

**让「删除」顺带取消在途传输。** 否决：这是两种不同的诉求，菜单两个都给了。「停止发送」关乎线路，会
告诉对端；「删除」关乎本机的记录，不告诉对端。把两者合并意味着一个只想把消息从屏幕上拿掉的使用者，
还必须去打断一个本来工作正常的传输。

**告知对端某条消息被删除了。** 否决：协议里没有这种消息，加上一条会让对话变成任何一端都能改写的东西。
本产品的全部前提就是两台设备报告同样的字节；一个会传递的删除会成为这条前提的第一个例外，而没有任何
使用场景需要它。

**像活动列表那样按插入顺序绘制。** 否决：插入顺序是关于本进程的事实，而一个活过进程的对话没有插入
顺序可以援引。时间戳是唯一能穿越的排序，而且它们需要并列时的次序，因为没有任何东西保证两条消息在
毫秒上不同。

**只用位置、或只用传输 id 来连接两份列表。** 否决：id 只在一个会话内唯一，所以同一个对端的两个会话
——重启前后——可能撞上；而位置一旦记录是从文件里读回来的，就什么都说明不了。

**保留可选择的正文，让平台的工具条去答复在文字上的右键。** 否决：这样「删除」恰好在最需要它的那些消息
上不可达。而同时保留两者的另一条路——压掉工具条，再让菜单从一个绕过手势竞技场的原始指针监听器上打开
——是父级伸手越过一个 Flutter 有意交给子级的手势，而且会让可选择正文在每一次右键时无缘无故地折叠掉
使用者的选区。一条消息一个菜单，也正是 `TransferContextMenu` 存在的意义。

## Consequences

**对话现在要以明文存在磁盘上。** 记录里装着每一条消息的正文和每一个收到的文件的路径，以 JSON 写出、
不加密，就在身份种子旁边同一个每用户目录里。这是磁盘上「静态数据」的真实变化，也是对「持久化对话」的
诚实读法：加密这个文件需要一把钥匙，而这台设备唯一能在重启后还在的钥匙，正是配置文件已经存在旁边的那
把。这里把它记为一条已知性质，而不是一个待补的缺口。

**裁剪不再丢历史。** 一个从活动列表里被丢弃的已结算传输，那时早已被归档，所以消息仍留在对话里；活动
列表现在只是本次运行「有真实状态可画」的部分。

**两份列表必须一致，且有一个测试这么说。** `transfers` 在句柄上合并它们，所以同时在两边的消息只能
画一次，而一次删除必须把两边都去掉。`test/app/app_controller_test.dart` 为此新增了自己的一组：由第二
台设备（同一份 store）读回的一条已结算消息、一次把消息同时从屏幕和文件里去掉的删除、一次留下对话其余
部分的删除、一个**不会**被记住的未答复问句、一条在传输中被删除且保持已删除的消息，以及上限从预置记录
里丢掉最旧六条。`test/history/` 覆盖记录自身的往返，以及文件存储的坏输入路径。
`test_flutter/ui/delete_message_test.dart` 覆盖屏幕上的另一半：一条文本消息——也就是背后磁盘上什么
都没有的那一类——提供「删除」和「复制文字」两项，不多不少；一个已经落地的文件仍然在「删除」旁边提供
它的文件夹动作；而「复制文字」把整条消息交给剪贴板，文件则永远不会被提供这一项。

**在文本消息上右键现在会打开菜单。** 这是「删除」无条件可用所带来的唯一可见代价，也是它被写在这里而
不是留给别人去发现的原因：用副键选中消息里的名字不再可用，因为手势被接管了。传输页和会话页画的是同
一个菜单，而这正是共享的 `TransferContextMenu` 一直以来的用途。

**消息正文不再可以拖动选中。** 它原本是 `SelectableText`，现在换成了 `Text`，原因见上。代价是没法在
一条消息里拖出一段选区；换来的是「复制文字」，它复制整条消息，而且对从磁盘读回来的消息和刚发出去一条
的消息一样可用。这件事值得写下来而不是留给别人去发现：在一个气泡里拖出选区再按 Ctrl+C，现在什么都不
会做。
