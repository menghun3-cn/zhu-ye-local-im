# Agent Note: 建立连接改在对话列表里完成

Status: implemented

[English](2026-10-08-connect-from-the-conversation-list.md) | 中文

## Problem

一次对话是怎么开始的，本来有三个毛病，而这三个毛病其实是同一件事的三个侧面。

**「建立连接」待错了地方。** 设备页的每张设备卡片上都有一颗「连接」按钮，点下去先拨号、再把用户弹到对话页并打开那条会话。于是这个动作从一个页面开始、在另一个页面结束，而它起步的那个页面，讲的正是硬件——地址、端口、最后在线时间、本机自己的指纹。想找人说句话，得先去翻一遍设备清单。而且设备页一台设备一张卡、一张卡一颗按钮，「到底从哪连接」这个问题的答案跟设备数量一样多。

**扫描到的设备，在连上之前根本看不见。** 对话列表的准入规则是「已连接**或**有历史」：

```dart
if (!peer.isConnected && history.isEmpty) continue;
```

对「我有什么可读的」来说这是对的，对「我能跟谁说话」来说就是错的。一台已经被发现定位过的设备——地址、端口、设备组全都知道——因为在对话列表里，仅仅因为还没人拨过它。这个本就为了装对话而存在的列表，恰恰少了新用户要找的那一条。

**对话列表没有自己的图标，也不该排在第二个。** 列表行画的是对端的平台图标，而在一列对话里，「这是什么 App」这个问题没人问，何况设备页已经答过了。Conversations 还排在 Devices 后面，于是用户天天待的页面，排在只去一次的页面后面。

最后还有一件没人处理过的情况：**两边同时点「连接」**。`PairingService.receive` 绑的是 `anyIPv4`，两个同时的拨打真的会碰上；而开场交换之后握手是对称的，所以两边都能走完。真正**没有**发生的，是会话。两边都以为自己是拨打方，也都以为应该把对方的尝试当成「第二条连接」拒掉——应答侧当时是这么写注释的：

```dart
// No Session is opened from this side: the Device that dialled opens it,
// and a Session dialled from both ends at once would have each end refuse
// the other's as a second one.
```

两个人都点了「连接」，配对成功了，然后谁也说不上话。那条避免双拨的规则，对危险的判断是对的，对怎么处置危险则错了。

## Decision

### 设备就在对话列表里连

`ConversationsPage` 列出**发现的每一台对端设备**，连没连上都列。一台被发现的设备，就是一段用户还没开始的对话，所以那一行本身就带着开始它的那颗按钮：

- **连接**——当 `peer.isDiallable && peer.isInGroup`，即有地址可拨、且所拨的是一个设备组。
- **配对**——当 `!peer.isInGroup && peer.address != null`；配对是把设备拉进组的方式，所以它是更靠前的那一步。
- **什么都没有**——两者都不满足时：没有端口的对端，就是完全不接受连接的设备，一颗注定失败的按钮比没有按钮更糟。

这两个判定条件是原样从 `_PeerCard` 抄过来的，这是有意的：那个判断是关于对端的事实，不是关于某个页面的，「两个页面按同一种方式读它」正是它们不会各说各话的原因。

`_PeerCard` 交出了按钮和拨号。`_ConversationTile` 把两样都接了，那里的 `_connect` 只有一行——`controller.connect(peer.fingerprint)`——因为会话本来就是选中的：这一行只会出现在用户正看着的那个列表里。拨号仍然走 `guarded`，失败会被报出来，界面不动。

### 对话排第一，设备排第二

`_conversationsSurface` 变成 `0`，`pages` 与 `destinations` 在同一次改动里重排，`test_flutter/support/ui_harness.dart` 里那五个常量对调。`home_shell.dart` 里这两个列表是按构造对齐的，所以要动就一起动。

### 对话行按对话的画

`lib/ui/labels.dart` 里的 `iconForConversation()` 返回 `Icons.forum_outlined`，与导航项用的是同一个图标。对端的平台仍然是一个事实，也仍然留在设备卡片和顶栏上。

### 同时点「连接」，靠一条双方都能算出来的规则，照样连上

`_dialsFirst(self, peer)` 比较两个指纹：

```dart
bool _dialsFirst(Fingerprint self, Fingerprint peer) =>
    self.hex.compareTo(peer.hex) < 0;
```

两边拿同一对值去算，得到相反的结果，这就是全部要求：这条规则必须是两台设备**不可能算出分歧**的那种，而指纹是任意一方用户答话之前唯一拿得到的输入。

应答侧（`_PairingRequestDialog._accept`）赢了就开会话，拨打侧（`_PairWithPeerDialog._join`）赢了就开会话。因此 `showPairingRequestDialog` 除了请求还要收一个 controller——这个窗口要用本机自己的指纹算胜负，赢了还要有地方拨出去。

规则是无条件套用的，但它只在「撞车」时才起作用。平常的配对里，一方按的是「配对」、另一方答的是一个请求，两边走在不同代码路径上；应答侧赢了就去拨一个已经在等它的对端，输了则按「配对」的那一方本来就要拨。输的一方背后永远有 `connectAfterPairing` 那条 24 次、每次 250 毫秒的重试循环兜着，这也就是吸收「Discovery 还没重新学到对端在哪个端口」的那层。

## Alternatives considered

**连接按钮留在设备卡片上，同时在对话列表里再加一个。** 否：两个地方都表示「连接」，两套判定条件必然走样；而且用户会把设备页读成一个它已经不再回答的问题的答案。

**让设备页那一行点了就拨，而不是挂一颗按钮。** 否：还是同一个页面干同一件事，而且行本身的含义变得含糊——已连接设备的那一行现在的意思是「打开会话」，一行不可能在未连接时表示拨号、已连接时表示打开，除非逼用户去学一个状态机。

**只列出在组内、因而必然有按钮可挂的已发现设备。** 否：组外的对端恰恰是新用户最需要看见的那一台，因为把它配对进来就是下一步该做的事。藏起来只会把人赶到设备页去确认它存在。

**列出已发现的设备，但不给「配对」动作，理由是配对属于设备页。** 否：配对会在**对方**设备上弹出一个窗口，它是两个人之间的互动，就该待在两个人正在说话的地方。而设备页保留了配对卡片——那颗「是否应答请求」的开关——所以「常驻状态」那一半仍然留在那里。

**用「谁拨的配对」来拆同时连接的平局。** 否：那正是旧代码依赖的不对称，也正是两边唯一不共享的事实。撞车的定义就是双方都拨了，这条依据却把撞车描述成「只有一方拨了」。

**让两个同时的拨号撞一下，输的一方在收到拒绝后重试。** 否：拒绝会以 `AppRefusal.sessionAlreadyOpen` 落到输的一方，但「输赢」在那儿推不出来——两边都会重试，两边又都会被拒，重试逻辑本身还得再要一套平局规则。用一个比较能解决的事，去换一个同样需要那个比较的重试循环，是亏的。

**两边都开会话，让 `connect` 现成的 `sessionAlreadyOpen` 拒绝来收场。** 否：那个拒绝正是**阻止**会话的原因，而不是化解撞车的原因。`connect` 是在第二次拨号时抛异常，而不是采纳第一次，所以两端最终各自拿到对方的拒绝，谁都没有会话。

**把平局规则放进配对层，那里本来已经区分了两种角色。** 否：等角色出现的时候，撞车已经输掉了——`PairingService.receive` 已经把第二个入站请求当成它那一个请求收下了，双方都自认 `initiator`。这个决定必须建立在一个双方开局就都持有的事实上，所以它用的是指纹。

## Consequences

- 本应用发现的设备会在没有任何人拨号之前，自己出现在对话列表里，行上带着连接（或配对）。这就是「一开始扫描到则在对话列表里面显示」的行为，而它只改了一处代码：`_conversationsOf` 里那个 `continue` 没了。
- `conversationListEmpty` 和 `conversationPickOne` 不再让用户去设备页，因为那里已经没有这里没有的东西。两种语言在同一次改动里都更新了。
- 就会话而言，设备页现在是只读的：它描述对端，并在一台已连接的对端上给出 `openConversation`。`_PeerCard` 不再接收 `LocalTransferController`——这个类型签名本身就在说明它已经没有动作了。
- `test_flutter/support/ui_harness.dart` 新增了 `conversationListed` 与 `conversationConnectable`，`openConversation` 改成点对话列表而不是设备卡片。`conversationOffered` 保留为设备页的信号，端到端的传文件流程改走列表。
- 同时点连接现在会连上。这个行为**没有**测试覆盖：驱动两个窗口在同一帧里各点一颗按钮，不是 `pumpUntil` 表达得出的东西；而其中可测的部分——`_dialsFirst` 是反对称的、每侧只拨一次——已经被覆盖到的单拨路径蕴含了。这是一处明写的覆盖缺口，不是疏漏。
- `_PairingRequestDialog` 现在会拨号，所以 `showPairingRequestDialog` 要收 controller。只有请求、没有 controller 的调用方已经无法弹出这个窗口——这是对的：那个组合本来就不可能走完用户刚刚批准的这次配对。
