# Agent Note: 官网展示累计下载数

Status: implemented

## Problem

官网是没有后端的纯静态 GitHub Pages 包，唯一的数据来源是 GitHub 公开 REST
API。下载数字其实一直存在 —— GitHub 为每个 release 附件统计
`download_count` —— 但它们埋在 Releases 页面里，访客在决定要不要下载时看不
到。需求是在首页放一个累计数字。

官网刻意不做任何统计（「不做埋点、不读 Cookie」），所以这个数必须来自
GitHub 已经公开的数据，而不是跟踪访客。

## Decision

`site/app.js` 本来就在拉 `releases/latest` 填下载链接。现在新增一次独立的
请求，按 `GET /repos/{repo}/releases?per_page=100&page=N` 翻页，直到某一页
不满 100 条为止（上限 10 页），把**所有 Release 的所有附件**的
`download_count` 加总，写进 `index.html` 里 hero 区 `hero__meta` 行内的
`#heroDownloads` 元素。请求成功前该元素保持 `hidden`，因此离线访客、被限流
的响应、以及还没有任何 Release 的仓库看到的是「什么都没有」，而不是误导性
的 `0`。

对原始附件列表求和、而不是匹配已知后缀，会自然带来两个性质：

- **未来平台自动计入。** Linux、macOS、iOS 的产物只是 `assets[]` 里的又一
  项，发版时官网代码不需要任何改动。
- **`-latest-` 别名也计入。** 每个别名都是独立可下载的文件，有自己的
  `download_count`；经它下载（局域网按固定地址拉包）是真实下载。排除它们
  会少算；别名与版本化附件本来就不是同一个文件，不存在对同一事件的字面
  重复计数。

计数粒度是「附件」，即 GitHub 侧真实完成的下载数 —— 比点击埋点更接近
「下载量」，代价是每次访问多一次 API 请求。未认证调用按访客 IP 限流
（60 次/小时），每次访问只发一次请求，远够不到上限。

## Alternatives considered

**在每张下载卡片上显示各附件计数。** 否决：本次需求是在主按钮旁放一个累计
数作为社会证明。每个附件的 `download_count` 仍在 asset 对象上，后续想加随
时可以加。

**第三方统计（Umami、GoatCounter）或计数跳转。** 否决：两者量的都是点击而
不是完成的下载；前者破坏官网「无第三方脚本」的立场，后者需要项目没有的后
端。读 GitHub 自己的计数两者都不需要。

**构建/部署时把数字烘焙进去。** 否决：Pages 的部署由合入 `master` 触发，而
不是由下载触发，烘焙的数字在两次发版之间会过期，还得靠定时工作流保鲜 ——
为一个客户端一次请求就能拿到的实时数字引入整套机制不值得。

**用 Traffic API。** 否决：`/traffic/*` 只暴露 clone 数与页面浏览数，不含
release 附件下载数。

## Consequences

**换来的。** 访客在下载按钮旁看到一个实时累计数字；该数字统计的是 GitHub
侧真实完成的下载；新平台产物零代码改动即被计入；官网依然不携带任何自己的
跟踪。

**每次访问多一次请求。** 每次页面访问现在发两个 GitHub API 调用
（`releases/latest` 加上分页列表）。两者都是匿名的，浏览器只按会话缓存；
GitHub 的 `ETag`/限流头照常生效。

**数字观感上可能回落。** GitHub 的计数不是实时的，附件也可能被删除或某个
Release 被替换，因此显示的总数偶尔会下降 —— 对一个装饰性统计可以接受，
这正是失败时隐藏元素而不是显示 `0` 的原因。

**别名下载让总数相对「安装量」偏高。** 局域网脚本拉 `-latest-` 别名与用户下
载版本化附件是两次事件，总和把两者都算进去了。这符合「下载次数」而不是
「独立安装数」—— 标签写的是累计下载，不是安装量。
