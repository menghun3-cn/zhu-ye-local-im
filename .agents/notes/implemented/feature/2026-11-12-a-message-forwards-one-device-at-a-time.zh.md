# Agent Note: 一条消息每次只转发给一台设备

Status: implemented

## Problem

会话能发、也能重发，但不能*转给别人*：从一台设备来的文字或文件，没有
办法送到第二台设备，除非重新敲一遍或重新挑一遍文件。用户要的是每个
消息应用都有的两种形态——转发单条、多选若干条逐条发出——外加一条硬
约束：每次转发只选一台设备，多选的内容按每条一个 Transfer 发出，绝
不打包。

决定一切的约束是：转发*是什么*。它不是新的线路消息，也不是复制一条
记录——它是经由与手打消息相同的门重新发送的一次发送。这意味着内容
必须仍然*在这台机器上*——文字在 `TransferView` 里，字节在
`localPath` 处。有些消息回答不了这个问题。

## Decision

**`TransferView.canForward` 是唯一的判定。** 它和被判定的视图放在一
起（`lib/app/views.dart`），菜单、选择模式的勾选和控制器问的是同一
个问题：已结束、不是未发送草稿，并按类型区分——文字/表情需要非空
`text`；文件/图片需要 `localPath` *且* 恰好一个名称；剪贴板永远不可
转发。多项目发送只留下聚合名称，所以半个文件夹不是那个文件夹，这条
消息整体不可转发。仍在途的也排除，因为它的字节还没有到齐。

**转发就是发送，走现有的门。** `LocalTransferController.forwardMessage`
按 `PayloadKind` 分派到 `sendText`/`sendEmoji`/`sendFile`/`sendImage`/
`sendAppOwnedImage`——转发的文件以普通文件提议的形式到达，对端像回
答任何文件一样回答它，而不是悄悄写盘。文件/图片的 `localPath` 已不
存在时，在排队之前抛 `AppRefusal.localFileMissing`：为不存在的字节
留草稿，只会把失败推迟到重发时。

**离线走草稿的路，而不是拒绝。** `noSessionOpen` 与
`noPeerConnected` 被捕获，内容经 `queueUnsentMessage` 留下，欠给目
标设备——与对方离线时打下的消息完全一样。其余失败依旧响亮。

**`forwardMessages` 是循环，不是事务。** 每个视图按给定顺序各自发
送、各自一个 `Transfer`；失败计数，余下的照常发出。顺序由调用方
负责——会话把视图按时间先后交给它，因为 `transfers` 本身是最新在
前——函数返回失败数而不抛出，批量的 toast 才能报出
`forwardFailedCount` 而不丢掉已经发出的那些。

**一个对话框，两条入口。** `forwardToPickedDevice`
（`lib/ui/forward.dart`）是唯一的道路：消息菜单上的「转发」和选择
栏上的「转发」最终都到同一个设备选择——列出全部对端，离线的也列
出并标注，先连上的再按名称排序——以及同一份计数与 toast 汇报。它
返回是否选中了目标，这样用户中途取消时选择模式能保留勾选。

**选择模式换掉的是输入框，不是会话。** 消息菜单上的「多选」带着该
消息进入选择，该消息预先打勾；可转发消息的气泡长出勾选框，不可转
发的干脆不给勾选而不是给一个点不动的勾。操作栏显示已选数量、取
消和转发。点消息即切换勾选；切换会话或取消即退出。原消息从不被改
动——转发只给*目标*的会话添东西，来源保持原样，包括允许转发回原
来的对端。

## Alternatives considered

**把多选打包成一个 Transfer。** 被需求本身否决：接收方必须把这些
消息看作它们本来的样子——各自独立的状态、各自可删。打包还需要一
个在线路上并不存在的报文形状。

**把 `MessageRecord` 直接复制进目标的历史。** 否决：那是在伪造到达
——目标没有同意、没有应答任何提议，它自己的设备会持有引擎从未见过
的消息。转发是一次发送，所以走发送的路，落在发送该落的地方。

**多项目传输也提供转发、只发第一个文件。** 否决：悄悄发出用户所见
内容的一部分，比干脆不提供这个操作更糟。`canForward` 直接在前面
说不。

**批量遇到第一个错误就整体失败。** 否决：这些消息是互相独立的发
送；一个被移动的文件不该连累选择里的其余部分。计数失败并汇报数字
是诚实的总结——成功的那些已经作为新消息可见了。

## Consequences

**得到的。** 转发不需要线路协议改动、不需要新的 Transfer 类型、不
需要持久化改动——转发的消息和任何其他 `Transfer` 一样，于是历史、
未发送草稿、删除与已结束记录契约全部原样适用。两个入口（单条菜单、
批量操作栏）不会漂移，因为它们共享 `canForward` 与
`forwardToPickedDevice`。

**代价。** `forwardMessages` 逐个发送并逐个等待，所以大选择是一串
往返而不是并行提议——这是有意的：用户挑选的顺序本身就是信息的一
部分。勾选之后、发送之前文件被移动的，会单独失败并计数而不点名；
toast 说的是几个，不是哪几个。

**测试。** `test/app/views_test.dart` 按类型钉住 `canForward`。
`test/app/app_controller_test.dart` 的 `forwarding` 组在真实配对设备
上钉住发送——顺序保持、离线变草稿、被移动的文件计为失败、还在的
文件以提议形式到达。
`test_flutter/ui/forward_message_test.dart` 钉住界面：两条菜单项、
选择器、勾选，以及批量以独立消息发出。
