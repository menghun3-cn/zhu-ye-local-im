# Agent Note: 常驻应答配对请求，取代「开着窗口等连接」

Status: implemented

[English](2026-09-30-pairing-requests-instead-of-a-window.md) | 中文

## Problem

[点一下就配对](2026-09-30-click-to-pair-no-more-typing.zh.md) 上线时带着一步操作，而这一步是**对方**的用户既看不见、也做不了的：被配对的那台设备必须先点「接收连接」，让那个窗口一直开着，等待发起方点「配对」。监听器的寿命等于窗口的寿命，这带来三个问题。

它要求错的人做准备。需要被准备好的，恰恰是**被配对**的那一方——桌上那台已经收拾好的机器，而它的主人多半根本没在看它。发起方的屏幕上没有任何东西提示「对面得先开着窗口」，所以一台没人准备的设备被拨过来时，结果是 `Connection timed out`；这读起来像网络坏了，而不像「对面没开窗口」。

它加不了第三台设备。一个窗口只对应一次配对。要把第三台设备加进设备组，**已经配好**的那台设备的用户必须回头把窗口再开一次——这与设备组本来的含义相矛盾：设备组是一组你可以直接发东西过去的设备，不需要先对其中任何一台做什么。

它对自己状态的描述也是错的。一台没人开过窗口的未配对设备，显示「监听：不接受连接」——这句话被写成关于这台设备的事实，用户很自然地读成「这台机器的配对坏了」，而实际只是「我们还没开始」。

窗口存在是有真实理由的，替换它之前值得把它写在前面。开放配对的握手跑在 `PairingSecret.openPairing()` 上，而这是一个**公开的常量**，链路上任何设备都能完成这个握手。窗口把这份暴露限制在时间上：开着的时候谁都能拨，关上之后谁都进不来。所以窗口并不是放行来电方的那道检查——6 位数字才是——它限制的是「陌生设备**什么时候**可以来试」。

## Decision

应答配对请求变成了常驻监听，限制它的不再是时钟，而是每次来电都要过的一道人。

* `PairingService.receive({port})` 绑定公认的配对端口并一直应答，直到 `stopReceiving()`。`invite()`——即手输码那条路——在监听器开着时拒绝启动：两者要抢同一个端口，而从请求监听器上进来的来电方没有报出任何可供核对的口令。
* 一个来电方分两阶段应答，而这个顺序就是整个决定本身。先完成握手，因为要摆在问题上的名字就在握手信息里；然后才发出一个 `PairingRequest`。**真正要紧的东西全部等 `PairingRequest.admit()`**：准入交换、6 位数字、以及应答方本来会交出去的那个设备组秘密。一个还没被放行的来电方，手里只有一条链路，别的什么都没有。这就是窗口的替代品——暴露不再是按时间封顶，而是按「有没有人点了同意」逐个封顶。
* 等待仍然是有上限的。`requestTimeout`（两分钟）会把没人应答的请求拒掉，因为来电方是**在等**：一台没人在跟前的设备，应该停止收集拨号者，而不是把它们按在转圈的加载图标上直到进程退出。
* 一次只处理一个。第一台还在屏幕上等的时候，第二台来电直接被拒，而不是排队：两个配对同时在跑，会各自往同一份档案上写，而它们写下的成员名单都会缺掉对方那台设备。一串没人要过的提问，比一句干脆的拒绝更糟。
* 监听器活得比这次配对长。应答完一次请求，它仍然开着，所以下一台设备在同一个监听器上被应答——这本来就是「再加一台设备」必须有的含义。
* 握手中途的连接数有上限（`_Receiving.maxHandshakes`，8）。一个永远开着的监听器，链路上任何东西都能拨；而每一个握到一半就挂住的拨号者，都要占一个任务等完 `handshakeTimeout`，恶意设备开得比它超时还快。第 9 个同时来电会被丢弃——诚实的用户之间永远不会出现这种情况。
* 没人可问的请求当场拒掉（`!requests.hasListener`）。它没有屏幕可以出现，而另一种可能，是对端在等一个从来没人被问出口的问题。
* `DeviceProfile.acceptsPairingRequests`（默认 true）表达用户的意愿，并且会落盘，所以一台被设置成不应答的设备不会在重启后悄悄又开始应答。`AppController._syncPairingListener` 让监听器和它保持一致；绑定失败是**上报**而不是抛出——最常见的原因是同一台机器上开了第二份程序，而那个用户仍然可以主动拨出去。设备页用它做成一个开关，并且**副标题报告的是监听器的实际状态，而不是那个偏好值**——两者可能不一致，一个开关承诺了没在发生的事，那就是在撒谎。
* 应答的是界面，应用层永远不代答。`AppController` 转发 `pairingRequests`，`HomeShell` 订阅它（它是永远活着的最窄的那一层，所以不会因为用户当时停在别的页面上就漏掉请求），`showPairingRequestDialog` 只问一个问题——放行还是拒绝——而那个回答就是全部。一个替用户做主的控制器会让常驻监听变得不安全，所以这个类型是按它的实质命名的——一个带着来电方的**问题**，而不是一个事件。
* 「拨不通」现在会如实上报。`PairingException` 带上了 `unreachable`，界面用它给出一个说清要检查什么的句子——对方程序是否在运行、两台机器是否在同一网络、对方防火墙是否放行入站 TCP 47656——而不是把系统的 `Connection timed out` 直接甩给用户。这是同一次反馈的另外一半，而且它特意做成一个标记而不是去匹配某个短语：它旁边那句话仍然是操作系统自己的措辞，原样保留。
* 应用层那条手输码的路已经删掉。`invite()`、`inviteOpen()`、`join()` 由 `pairWith({host, port})`（点一下配对的拨号）和 `setAcceptsPairingRequests(bool)`（开关）取代。核心层保留 `invite()` 与 `join()`；`lib/ui` 里已经没有任何东西够得着它们，在没有展示口令的界面之前，这是对的。

## Alternatives considered

**保留窗口，再加一个「常驻应答请求」的开关，一键把窗口永久打开。** 否决：它留住了让整个流程错掉的那一步——被配对那台设备的用户仍然必须先去把某个东西打开，而一台从没被碰过的设备仍然配不上。它还把「一个说得清楚的临时状态」变成「一个模式」，后者更难解释。

**让监听器在数字显示出来之后自动放行来电方。** 不行：握手秘密是公开的，6 位数字加两次确认就是**全部**的准入检查。在比对之前放行，等于「谁先问谁进来」。

**照旧发出请求，但先把准入交换跑完，好让提问时就能显示数字。** 否决，而且这正是这次改动绕开的陷阱。`_negotiate` 是应答方决定交出哪个设备组秘密、并把它在密封链路里发出去的地方。在用户点头之前跑完它，就等于把本机的设备组秘密交给了任何完成过一次公开常量握手的来电方——用户被请来批准的，是一份已经送出去的东西。

**把第二个来电方排在第一个后面，而不是拒掉。** 否决：那会排出一串没人要过的提问，在引起它们的那次点击之后几秒才陆续冒出来，而第二个来电方的用户根本看不到自己排在哪。拒绝是可以回答的，排队不是。

**让请求一直挂着，直到有人应答。** 否决：来电方是被阻塞的。一台没人在的设备会一路累积拨号者，每一个都占着链路，每一个都对着加载图标，而分不清自己是「正在被考虑」还是「对面已经没了」。

**让请求走应用层自己的流，由应用层决定要不要自动应答。** 否决：应用层替用户应答，恰恰是这套设计禁止的事；把它做成一条可用的代码路径，就是它重新长回来的方式。

## Consequences

- 设备一启动就在应答请求，所以来电方那一下点击总能找到监听器；往一个设备组里加第二台、第三台、第十台设备，都不再要求组里任何一台设备多做任何事。
- 链路上的设备可以随时对一台正在应答的设备发起配对。拦住它的是人：提问会说明谁来敲门，会明说这个名字只是对方自称的，而对这个提问的回答就是全部的核实。想让自己不被够到的设备，把开关关掉即可，而且这个偏好能扛过重启。
- 配对是只做一次的事。一台设备是否**够得着**，已经不再取决于有没有哪个界面开着：配对监听器只管配对，发文件走的是会话层，而会话层在这次配对落定后就起来了，并且一直留着。
- 窗口从界面里消失了：`showReceiveDialog` 与其状态、`receiveAConnection`、`receiveWaiting`，以及驱动它的两个控制器入口。接替它们的是一个开关、一个对话框，和五个字符串（`acceptPairingRequests`、`pairingListening`、`pairingNotListening`、`factPairingRequests`、`failureCannotReach`）。
- `test/pairing/pairing_service_test.dart` 里有一组叫 *What a Pairing request must never do* 的用例，把设计所依赖的不变量钉住了：来电方在被放行之前什么都拿不到（它的 `joinOpen` 尚未返回，两边也都没有秘密）；第一台还在屏幕上时第二台被拒，且不影响第一台；没人应答的请求到期即被拒，之后也无法再被放行；监听器与手输码那条路互斥；关掉监听器就收走端口；应答完一次请求后监听器仍在，供下一台设备使用。
- `test/app/app_controller_test.dart` 覆盖应用层的开关，`test_flutter` 覆盖它在屏幕上的样子——包括「数字在提问之后」，也就是上面那条不变量的用户可见形态。
- 测试脚手架跟着流程改了。`pairDevices` 现在负责拨号、在控制器层应答请求并确认，扮演被配对那台设备的用户；因为它是在界面**底下**应答而不是通过界面应答，所以它必须在宿主窗口被 pump 起来**之前**运行，并且用一条显式断言把这件事说出来，而不是留给下一个读代码的人从超时里倒推。需要在屏幕之前先拿到一台已配对设备的测试，改成先配对、后 pump。
- 窗口里的「配对」按钮只能拨公认的配对端口，因为屏幕上没有地方放端口号。所以一个把整条流程都走界面来测的用例，必须绑定那个默认端口；而只需要请求机制的用例，则拨设备实际绑定的端口——这样两个测试文件（`flutter test` 会让它们并行跑）就不会互相抢端口。
- `requestTimeout` 默认两分钟，并且是可注入的，所以到期行为用毫秒来测，而不是靠等。
