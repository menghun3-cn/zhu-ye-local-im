# Agent Note: 选好的文件先在输入框里等着，点发送才发

Status: implemented

## Problem

选中一个文件，它就被发出去了。回形针、图片按钮和 Ctrl+V 最后都落在同一个地方：
`_pickAndSend`/`_pickAndSendImage` 打开系统自己的对话框，然后把返回的东西在同一个呼吸里
送上网。中间没有任何时刻：没法为这个文件配一句话，没选错之后收不回来，发完屏幕上也没
留下任何能说清刚才发的是什么 —— 唯一的记录是已经在对方机器上落地的那条消息。上一轮刚
把粘贴也做成了同样的形状，于是这成了一个模式而不是一次疏忽：三条进输入框的路，三次立
刻发送。需求原文是「选择文件、选择图片，点击发送之后再发」。

## Decision

**输入框持有草稿。** `_ConversationViewState` 增加 `List<StagedAttachment> _staged`
—— 路径、要显示的名字、以及对面会不会把它画成图片 —— 三条路现在都改成**暂存**：
`_pickFiles`、`_pickImage` 和 `_pasteIntoComposer` 都以 `_stagePaths` 收尾，
按选择顺序分类并追加。

**发送才是放行的动作。** `_sendMessage` 先发输入框里的文字，再逐个发已暂存的文件，
一个文件一条消息 —— 和以前「选中的文件」一样；图片按图片发，这样对面会画出来。
输入框和托盘**只在整次发送成功之后**才清空，所以发送失败时草稿还在原处，用户可以重试，
不必重新选一遍文件。输入框空、托盘也空时，什么都不发。

**暂存的东西看得见，也拿得回来。** `_AttachmentTray` 在输入框上方画一排 `Wrap` 小片：
该类型的图标、名字（限宽 180 像素并带 tooltip）、以及一个移除的 `IconButton`。用 `Wrap`
而不是单行或底部抽屉 —— 两个文件一行放得下，十六个放不下，而一个**悄悄藏起第十一个**
的输入框会发出用户看不见的东西。移除控件是真正的 `IconButton`，因此保住了焦点环、键盘
激活和语义标签；手搓一个可点的字形会把这三种一起丢掉。

**`classifyPaths` 成为原语，`classifyDrop` 写在它之上。** 托盘必须按用户选择的顺序显示
文件，而旧的 `({images, files})` 二分法把这个顺序扔掉了。现在存在性检查和
`looksLikeImage` 各只有一处，在 `classifyPaths` 里；拖放路径仍在用的 `classifyDrop`
只是把它的结果分组。

**拖进来的文件仍然立刻发送。** 拖拽时盖在会话上的提示写的是「松手即发送」，所以拖放是一
个人决定「把这个发出去」，而不是「围着它写点什么」，这一条不动。这是本次改动引入的唯一
一处不一致，它写在代码里也写在测试的说明里，而不是留给别人去发现。

## Alternatives considered

**维持选中即发送，再加一个撤销。** 需求正好相反；而且在对方已经被要求接收这个文件之后
的「撤销」不是撤销。

**把暂存的文件当成「还没发的消息」放进消息队列。** 会话是**已经发生过**的事情的列表；
一个还没被 offer 出去的东西属于输入框，不属于历史。

**点发送时弹一个确认对话框。** 在已经回答过的地方再问一遍，而且它依然没给出一句话的空
间 —— 而那句话才是这个文件想配的东西。

**托盘做成底部抽屉或一个路由页。** 它会盖住它本该陪着的输入框，而且需要一个返回的地方。

**把拖放也改成暂存。** 站得住脚 —— 那样「不点发送什么都不出去」就是一条规则 —— 但拖放
的提示已经白纸黑字承诺了立刻发送，而需求点名的是那两个选择按钮。保持原样，并在此标注。

**没有东西可发时禁用「发送」。** 能去掉一个空转的按钮，但也会让按钮随着输入和粘贴忽隐
忽现，把点击目标从指针底下移走。

## Consequences

**托盘会让输入框变高。** 文件多时输入框换行、会话区变矮。上限取决于一个人手动会暂存多
少；另一个选择 —— 让托盘滚动或分页 —— 比这件事本身需要的机器多得多。

**在暂存和发送之间被删掉的文件会在发送时失败。** 引擎在构造 offer 时才打开路径，所以
消失的路径会变成输入框本来就会报的那个 guarded 错误。暂存项留在托盘里，而这正是有用的
那一半：用户能看出是哪一个。

**草稿属于某一个会话。** 外壳按 peer 给 `ConversationView` 加 key，所以切换会话本来就
会重建 state；`didUpdateWidget` 仍然会清空托盘，于是「草稿不会跨进别人的会话」是这个
widget 的性质，而不是它的调用方碰巧怎么加 key 的性质。

**粘贴一个文件从一个动作变成两个。** Ctrl+V 把它放进框里，然后还要点发送。这正是要求的
行为，也正是它让同一次 Ctrl+V 之后还能补一句话；但它改变了这个组合键**达成**的事，对已
经学会旧行为的人来说，这一条最容易被读成退化。

**调用方要把托盘传下去。** `ConversationComposer` 新增 `attachments` 与
`onRemoveAttachment`；分别默认空列表与 null，所以不需要托盘的调用方（测试、将来的其它
界面）不必知道有托盘这回事。

## Testing

`test_flutter/ui/pages_test.dart` 新增「choosing a file for the composer」一组：选中的
文件出现在托盘里，并且在按下发送之前**不存在任何 Transfer**；选中的图片发出去时按
`PayloadKind.image` 走；暂存的文件可以被移除，移除之后发送什么都不发。两条粘贴测试现
在断言同样的两步 —— 文件出现在输入框里且 `controller.transfers` 仍为空，之后发送才产出
消息 —— 于是粘贴路径和选择器路径被同一条规则约束。

`test_flutter/e2e/two_window_e2e_test.dart` 的端到端文件传输，现在在「选好文件」和
「offer 到达另一个窗口」之间多了一次点击发送 —— 那正是人会做的事；那一次点击之后的部分
没有变化。
