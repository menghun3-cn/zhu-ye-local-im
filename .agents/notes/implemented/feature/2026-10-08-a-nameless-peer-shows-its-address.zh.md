# Agent Note: a nameless peer shows its address

Status: implemented

## Problem

一台应答了 Discovery 却没有报上 Alias 的设备，在界面上是一片空白；而两台这样的设备
彼此无法区分。

Alias 是**对方自称的**。它藏在对方发来的 `hello` 里，而发来空值的设备——刚装好还没
人改过名的、不实现该字段的客户端、或者故意不说话的设备——就没有名字可显示。每个要
渲染名字的地方都得自己编一个，而需要它的两处编出了**不一样**的东西：

- `PeerView.displayName` 退回口令的前 8 位十六进制。
- 配对提示框退回 `pairingRequestUnnamed`，那句「一台还没报上名字的设备」。

两者都不算错，但两者都不是名字。在设备列表上，口令那条兜底更糟：它稳定、也确实能标识
对方，但它是握手期间对方**自称**的东西，而对一个正在找「我旁边这台笔记本」的用户来说，
它是八个十六进制字符，回答了一个没人问的问题。列表里若有两台都没报名字的设备，用户看到
两行十六进制，根本没法判断哪台是桌上那台。

与此同时，**App 手里已经有一个更好的答案，却没用**。应答过 Discovery、或者主动拨进来的
设备是有地址的——而且是这一侧**观察到**的地址，不是对方提供的。那是屏幕上唯一一个对面
选不了的事实，也正是用户判断「这是哪台机器」所需要的东西。

## Decision

对端显示名的解析顺序，按信息量从多到少：

1. **Alias**，对方报了就用它。那是对方自称的名字，也是唯一有人认得的名字。
2. **地址**，没有 Alias 时用它。`PeerView.displayName` 即
   `alias ?? address ?? fingerprint.short()`。
3. **口令短前缀**，只有两者都没有时才用。

**无论对方是否接受 Session 都用地址。** 通过 Discovery 看到、却没报 Session 端口的设备
虽然无处可拨，但「它在哪」依然比一句占位语有价值，所以 `isDiallable` 不参与名字的判定。

配对提示框遵循同一顺序，用的是**接受该请求的那个 socket** 读出的地址。为此
`PairingRequest` 新增了 `callerAddress`：它在 `_answer` 里由
`socket.remoteAddress.address` 填入，因此是传输层观测到的、而非调用方发来的东西。它可空，
而 `pairingRequestUnnamed` 那句仍是最后一档兜底——传输层报不出远端地址是**真实可能**，
不是理论上的。

这里**刻意不改设备自己的默认名**。一台从未改过名的设备，在自己的 profile 里仍然叫
「Unnamed device」：首次启动时它还没绑定任何网卡，所以自己也没有地址可给；而真正要紧的
地址，本来就是**对方**观察到的那一个。

Alias 依然是自称。这次改动不让没名字的对端变得**可信**，只让它变得**可辨认**。口令仍然是
唯一值得带外核对的东西，配对提示框也照旧这么写。

## Alternatives considered

**保留口令兜底，什么都不改。** 它已经上线、也确实能区分对端。它输在答错了问题：用户面对
两行没名字的记录，想知道的是哪台机器是哪台，而口令是**自称**、不是**地点**。地址是地点。

**把设备自己的默认 Alias 改成自己的地址。** 这正是请求字面上说的那半边，也是错的那半边。
首次启动的设备还没打开监听——要拿地址就得枚举网卡，而多网卡的机器还得**选**一个，那是
用户从没要求 App 替他做的决定。它还会把一个瞬时事实写进本该稳定的 profile：换了网络的
设备会一直用旧地址自称。用户真正需要的地址是**对端**的，而那一侧本来就知道。

**两者都显示，形如 `alias (address)`。** 信息更多，但以界面面积为代价否决：`displayName`
喂给列表行、标题、对话框题目和排序，而这些地方**本来就单独渲染了地址**——
`describePeerAddress` 把它放进副标题，会话页头在整个会话期间都留着它。把它编进名字，
会在它已经出现的地方再印一遍。

**每台设备给一个不同的占位符，比如「Unnamed device 2」。** 它确实解决了两台无名字设备
互相区分这个真正的抱怨，但那个序号毫无意义：它取决于发现顺序、每次运行都会变，也不告诉
用户任何可行动的信息。地址做同样的事，而且是真的。

## Consequences

设备列表上出现多台没报名字的设备时，现在可读了：每一行以用户能对上机器的地址打头；
会话列表的排序也跟着变，因为它按 `displayName` 排。

地址不像 Alias 那样稳定。换了网络、或经不同网卡被访问的对端，显示名会变。这是接受的：
它反映现实，副标题里的口令才是固定不变的那个，而想要固定名字的用户可以自己给设备改名。

`PairingRequest` 多了一个成员，因此该接口的任何实现都必须提供它。实现只有一个
（`_Caller`），且该接口是 pairing 包内部的，所以代价是一个编译错误，而不是一次迁移。

退回 `pairingRequestUnnamed` 现在只在传输层报不出远端地址时可达。`Socket` 一定有，所以
在本 App 实际走到的路径上这句话实践上是死代码、作为护栏活着；只有当接口不再可空时，
删掉这个字符串才是诚实的做法，而它保持可空，是因为地址是**传输层**的属性，不是请求的。

## Testing

`test/app/views_test.dart` 钉住三级顺序：Alias 优先于存在的地址；地址在有、无 Session
端口时都显示；两台地址不同的无名字设备显示不同；口令只在两者都缺席时出现。

`test/pairing/pairing_service_test.dart` 在点按配对那个用例里，对着**真实 loopback 拨号**
钉住 `callerAddress` —— 这正是它诚实的地方：该值必须来自被接受的 socket，伪造的替身
证明不了这一点。
