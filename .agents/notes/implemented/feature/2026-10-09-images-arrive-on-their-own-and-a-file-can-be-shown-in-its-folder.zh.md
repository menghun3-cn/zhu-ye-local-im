# Agent Note: 图片自己就到了，落地后的文件能打开所在目录

Status: implemented

## Problem

两个要求，都关于「东西过线之后」的那一段时间。

**「传输接收完毕后，可以右键选择打开所在目录」** —— 文件落盘之后，用户没有办法走到
它跟前。接收方选好了目录、看着进度条走完，然后只能自己去把那个目录找出来。应用从头到
尾都握着那条路径（`_Tracked.localPath`，以及由它来的 `TransferView.localPath`），却
一次都没有把它交出来。

**「图片类发送不需要接收，直接发送后自动接收显示」** —— 一张图片被问得和文件一模一样：
接收方要先面对「接收 / 拒绝」和一个目录对话框，然后才看得见东西。文本早已改成到了就收；
图片是两者之间的那一种：它像文件一样真的传字节、真的落盘，但**文件那个问题存在的唯一
理由** —— 这东西该放哪儿 —— 早已由本机的设置回答了，设置里就存着接收文件的落地目录。
还去问，就是应用当着用户的面忘记了自己的设置。

## Decision

**「落点」是那条判据，而且只由一个函数说出。** 控制器新增 `_landingFor`，回答一个到达
的 offer 该去哪里，四个 `PayloadKind` 因此分成三路：

| kind | `_landingFor` | 含义 |
|---|---|---|
| `text` | `''` | 就地接收；正文就在 offer 里，所以它不落到任何地方 |
| `image` | 档案里选定的目录，没有就用平台默认目录 | 到达即归档 |
| `file`、`clipboard` | `null` | 这是用户的问题 |

`null` 就是「去问用户」的那个值，所以 `_onOffer` 读的是同一个函数：`null` 把 offer 交给
界面，`''` 走 `_acceptInline`，其余任何路径走 `_acceptIntoDefault` —— 它先把目录建出来
（这样「图片进 Downloads/LocalTransfer」从第一次使用起就成立），然后走普通的 `acceptInto`
那条路。

**空字符串是故意的，不是 null。** 文本**哪里都不落**：它没有 sink、没有字节、没有摘要。
这和「还没人决定它该去哪儿」是两件不同的事，把两者合并会让文本重新看起来像一个问题。

**`_answerableOffer` 读同一条规则，而不是重述一遍。** 只有当控制器**没有**自行作答时，
`TransferView.offer` 才非空 —— 也就是文件，或者一台无处可写的机器上的图片。规则只住在
一处，所以有目录的机器不可能为一个它正在接收的传输画出提示，没有目录的机器也不可能把
图片悄悄写进一个没人指名的目录。

**没有目录的机器保留它的图片提示。** 用户选的目录和平台默认目录同时缺失，就是「无处可
写」这个诚实的情形；它由 `_landingFor` 返回 null 来表达，于是图片像文件一样等一等，而
不是失败，也不是被写到某个说不清的地方。

**`defaultIncomingDirectory` 变成了 `LocalTransferController` 的构造参数。** 平台把收到的
文件放在哪儿是**平台的事实** —— Windows 上是用户的下载目录，Android 上是应用的私有目录
—— 而 `lib/app` 不许向平台问任何事。它由 `lib/ui/app.dart` 从 `PlatformSeams` 注入，就像
各页面早已被告知的那样；null 表示「没有」，也就是尚未验证的 Android 构建解析出来的结果。

**「它在哪儿」是一个右键，而且属于用户当下正在看的那个界面。** 已经落定、且文件就在本机
的传输，会在一份上下文菜单里给出「打开所在目录」—— `TransferContextMenu` 同时包住会话里
的气泡和传输列表里的卡片，加上一个 `GestureDetector.onSecondaryTapDown`，在指针处打开
`showMenu`。offer 的**应答**依旧摆在明面上的按钮里，因为藏在菜单背后的决定是没人会发现的
决定；而这属于另一种动作：问题结束之后才会想要的东西。

**`TransferView.localPath` 是唯一的输入。** 收到的文件在 `acceptInto` 写好之后才记下它
（也就是字节校验并关闭之后，那正是收到的图片第一次拥有值得绘制的路径的时刻），而**自己
发出**的文件和发出的图片是立刻记下的，因为发送方自己那份文件在磁盘上早已完整。于是「打开
所在目录」在收发两个方向、在图片和文件两种东西上都成立；唯一没有答案的，是接收方那份还没
决定的文件 —— 那恰恰是磁盘上还什么都没有的那一个。

**打开的是目录，不是文件。** `explorer` 可以用它的 `/select,` 开关高亮某个文件，但那个
开关把参数放在**同一个 token** 里 —— `/select,C:\a b\c.png` —— 而任何看到参数里有空格的
启动器都会把整个参数加上引号，配对就断了。而路径里有空格在 Windows 上是常态，所以取的是
可靠的那一半：目录打开，文件就在里面。

**仅限 Windows，而且它会说出来。** `SystemRevealer` 请求平台自己的外壳（`explorer <目录>`）
—— 和 `external_links.dart` 打开网址是同一种取舍，而不是为了一次调用去买一个原生启动器
注册 —— 在别处一律回答 false。于是调用方显示 `cannotOpenFolder`，而不是留下一个什么都不
做的菜单项。

## Alternatives considered

**连文件也自动接收。** 这是要求最大的那一种版本，已否决：文件的目录确实是到达时提出的真
问题，它也是接收方能说清「东西到底去哪了」的全部依据。这次改动另一半的全部意义，正在于
一个落地的文件有「它在哪儿」可以回答；一个没被问过就归档的文件给不出这个答案。

**图片维持原样。** 已否决：那个问题本机已有答案。这就是那条抱怨的原话 —— 一张图片不该
弹出一个对话框，而那个对话框唯一合理的答案就是接收方早已做好的设置。

**图片一律自动接收，连没有目录时也一样。** 已否决：那会把图片写进一个没人指名的目录，
或者干脆让传输失败，而用户对此无事可做。在无处可写的地方保留提示是诚实的兜底，也正是它
让这个功能在目录尚未探明的平台上也能安全发布。

**在每条消息上放一个按钮或工具条，而不是右键。** 已否决：为一个偶尔才想要的动作，它在
每个气泡上都要占掉一块界面；而会话这个界面，不该为「那东西去哪了」长期花掉一个常驻控件。
右键正是桌面系统里用来问这个问题的那个手势。

**把右键提到整个会话而不是气泡上。** 已否决：气泡才是指针所指、也是文件所属的那个东西。
把处理器挂在外围的界面上，就得先算出用户指的是哪条消息，或者从一次落在留白上的按压里给出
某个文件的目录。

**用 `explorer /select,<文件>` 直接高亮文件本身。** 因上面的参数引号问题否决：路径没有
空格时它能用，有空格时会悄悄打开错的东西，而有空格的路径更常见。

**用一个启动器插件（`url_launcher`、`open_file` 之类）。** 已否决：为一次调用买一个**原生**
注册，而且这个构建声称支持的每个平台都得多维护一样东西。平台自己的外壳已经能做这件事。

**不给 `RevealResolution` 留缝，直接调 `Process.run`。** 已否决：驱动真东西的 widget 测试
会在跑测试的机器上弹出一个资源管理器窗口 —— 一个和断言毫无关系的副作用，而且在无头机器上
根本跑不了。这道缝做成了 `PickerResolution` 的形状，于是测试断言的是它被交到手里的那条路径。

## Consequences

线协议没有动。图片本来就带着摘要和 sink 在传；变的只是**由谁作答**和**它去哪儿**，两者都
是本机的事，所以 `wireProtocolVersion` 不提升，旧对端照常工作。

会话的空态文案现在把规则说了出来 —— 文字和图片会直接送达，文件要等对方确认 —— 而
`openContainingFolder` 与 `cannotOpenFolder` 加入了它，两种语言都有。

任何断言「图片是被 offer 出去的」的测试，现在都必须让接收方在不带默认目录的情况下启动，
因为那是它仍然如此的唯一一种配置。纯 Dart 套件正是为此把这条兜底显式写了下来。

`RevealResolution` 加入了 `PickerResolution` 与 `PasteResolution`，成为又一道必须在
`tearDown` 里还原的可变缝；把它留在装好的状态，它会替下一个测试作答。

`_landingFor` 现在是教会一个新 `PayloadKind` 归属何处的唯一地点：因为 `_onOffer` 与
`_answerableOffer` 都读它，一个应当到达即归档的种类不再需要第二处改动。

## Testing

`test/app/app_controller_test.dart` 新增 `an image with somewhere to go` 一组。第一条断言
一张发出的图片在**没人回答任何东西**的情况下完成：接收方手里没有 offer，它的传输是
`completed`、`needsDecision` 为 false、`offer` 为 null，落地文件的字节与发出的相同、用的是
发送方的文件名、就在这台机器被告知的目录里。第二条断言**用户**选的目录胜过平台默认目录。
在传输那一组里，`an image with nowhere to go is asked about after all` 钉住兜底：没有默认
目录时，图片像文件一样被 offer 出去。

`test/ui/reveal_test.dart` 用纯 Dart 覆盖 `folderOf` —— 它说出文件所在的那层目录，并拒绝
一个裸文件名和空路径，因为没有目录部分的路径会解析到进程的工作目录，打开它就等于打开了一个
没人问起的目录。

`test_flutter/ui/pages_test.dart` 新增 `showing a landed file in its folder` 一组。一条在
传输界面上右键一个收到的文件，断言上下文菜单打开、且它带着的路径就是落地的那个文件；另一条
把图片发给一台有默认目录的机器，断言没有 offer 到达它、会话里画出了 `ImageBubble`、并且
对气泡自己的右键揭示的是同一条路径。两条都装 `ScriptedRevealer`，所以都不会弹出资源管理器。

`test_flutter/support/ui_harness.dart` 现在把 `defaultIncomingDirectory` 同时交给控制器和
各道缝 —— 这正是发行版的接线方式 —— 于是被测的那台设备作答图片的方式，与用户运行的那台
设备一致。
