# Agent Note: Clipboard Mirroring inside an Owner Group

Status: implemented

[English](2026-09-29-clipboard-mirroring-within-an-owner-group.md) | 中文

## Problem

传输能用了。剪贴板还没有，而它是这个产品里更难的那一半。

只要一个设备开始镜像剪贴板，三件事会同时出问题。

**它会打转。** A 应用了 B 那边来的一个值。A 的剪贴板变了。平台把这个变化报出来，于是 A 把它当成一次本地复制捕获、再发给 B。B 应用它，剪贴板也变了，然后两台设备就为了同一个值来回弹，直到双双退出为止。Session 里没有任何东西能阻止这件事：这个环由两个行为完全正确的对端组成。

**Session 是错的信任尺度。** 握手只能证明对端知道 Pairing Secret，而 Secret 决定了谁能连上来。但 Secret 是一个可以被复制的字符串，「这台设备可以收我的文件」和「这台设备可以读我复制的每一个密码」不是一件事。在任何一条已认证的 Session 上交换剪贴板内容，等于在用户只想要前者的时候悄悄给了后者。这个取舍记在
[Owner identity layer gates clipboard mirroring](2026-09-29-owner-identity-gates-clipboard.md) 里；本笔记是它的落地。

**平台之间互相打架，平台自己和自己也打架。** 读剪贴板和写剪贴板的规则不同，而且方向是有意义的：Android 可以在后台写剪贴板，但只有在窗口获得焦点时才能读（`docs/platform-clipboard-constraints.md`）。所以一个只提供「同步剪贴板」开关的界面，等于承诺了一半平台做不到的事。

在能把上面任何一条说清楚之前，还有一个必须先解决的接线问题。`SecureLink.messages` 是单订阅流，而传输引擎已经在读它了。第二个监听者拿不到一份副本，它会把每一帧都悄悄拿走。也就是说，目前一条 Session 上根本没有地方容纳第二种对话。

## Decision

`lib/core/` 下的四块，每一块都是下一块的前提。

### 一条 Session，交给一个 hub 拆分

`session/session_hub.dart` 引入 `SessionHub`：它接管一条 `SecureLink` 上那个唯一的订阅，并对外给出两个视图。

- `hub.transfers` 是一个 `TransferChannel`，给 `TransferEngine` 用，引擎的契约一字未改。
- `hub.clipboard` 是一个 `ClipboardChannel`，给镜像用。

hub 只做分类，不做解释：`ClipboardMessage` 进剪贴板视图；`hello` 与 `helloAck` 被丢掉，因为一个 hub 存在的时候握手已经是历史；其余全部进传输视图，由引擎按它既有的方式决定怎么处理自己不认识的消息类型。

载荷分片是直穿而不是拦截的。引擎是它们唯一的消费者，在路径上再放一个控制器不会复制任何东西，只会多出一个必须有人排空的缓冲区。

### Owner Group 就是那道闸

`identity/owner_group.dart` 增加 `OwnerGroup`：成员 Fingerprint 的集合，永远包含本设备自己。成员是按设备而不是按人算的，因为 Pairing 一次只接纳一台设备，也因为 Fingerprint 是一台设备能证明自己确实持有的东西。

只有处于组内的对端才会被捕获，也只有来自成员的值才会被应用。这就是上一份笔记主张的那条边界，在这里被变成了机械事实：不存在任何一条通往组外设备的镜像代码路径，所以任何配置失误都无法把信任面撑大。

模型在这里，流程不在这里。一台设备如何加入一个组 —— 扫二维码、输入短码并比对短认证字符串、以及能扛过重启的存储 —— 是另一个增量。

### 镜像是一种对话，不是一次 Transfer

用户主动发出的剪贴板内容是一次 `PayloadKind.clipboard` 的 Transfer：它有提议、有应答、有摘要、有回执。镜像不是这种东西。它的定义就是**不需要**任何用户动作，它同一时刻只有一个方向，而且它没有任何东西需要校验 —— 所以它作为一个 `ClipboardMessage` 走。

这条消息带两个 Transfer Offer 没有的字段，而两个都承重：

- `origin`，值被复制的那台设备。这是止住循环的东西：一台设备看到自己的内容回来时，直接无声丢掉，而不是应用之后再弹回去。
- `entryId`，使一台设备能认出自己已经处理过的重复条目 —— 只要 Session 重试过一次或者对端有 bug，这件事就会发生。

### 镜像服务本身

`clipboard/clipboard_mirror.dart` 是服务本体，架在两个接缝之上：`SystemClipboard`（读、写、监听）与 `ClipboardChannel`（发、收）。`ClipboardEntry` 是带着标签的那个值，而它从不打印自己的正文：剪贴板里经常是密码和一次性验证码，所以它的 `toString` 只给 id、来源和长度。

一个镜像服务覆盖所有对端，而不是每个对端一个。因为回声抑制、去重和排序是**剪贴板**的性质，不是 Session 的性质。

### 来源标签是那个止环手段，而且只在一个方向上被拦

进来的条目必须被标记为它实际来自的那个对端。一个把别人的内容换个标签转发的对端，等于往组里塞了一个从来不属于它的值，而标签是唯一能说出这件事的东西。至于被标记为**本设备**、却从线路上过来的条目，会被最先、无声地丢掉 —— 那正是常规的回声情形，把它记进日志只会让日志被正常路径填满。

### 能力是被强制执行的，不是被展示的

`ClipboardCapability` 本来就随每个 `hello` 走。镜像服务会强制执行它：`canOriginate` 为假的平台根本不会被监听变化 —— 不是「监听了再丢弃」，因为那在 Android 上意味着为一次平台必然拒绝的读取弹出权限提示；而 `canApply` 为假的平台会拒绝写入并说明原因，而不是看起来像在工作。

### 排序只在同一来源内部比较

每个进来的条目都带着捕获它的那台设备打上的 `capturedAt`。镜像服务为**每个来源**记住它接受过的最新时间戳，并丢掉不比它新的。不同设备之间的时间戳从不互相比较：时钟没有同步，比较没有意义；而在同一个来源内部，同一台设备的时钟是唯一可得的排序信息。

### 三种模式，一个开关

`ClipboardMode` 是 `off`、`stage`、`mirror`。`off` 不捕获任何东西，也不监听剪贴板；`stage` 的捕获行为和 `mirror` 一样，但把进来的条目扣住，等用户接受；`mirror` 不做任何用户交互直接应用。后两种模式都会开启捕获，因为这个模式描述的是本设备**如何对待**剪贴板，而用户眼里的剪贴板同步就是一个设置项。

## Alternatives considered

**给 `TransferEngine` 加一个回调，转发它不路由的消息。** 改动最小，也不需要新类型：引擎本来就是 `messages` 唯一的读者，把不处理的转交出去就行。否决，因为这会让引擎变成 Session 的分发器 —— 那不是它的职责 —— 而且此后每一种新对话都要给引擎的 API 加一个回调。hub 让引擎的契约原封不动。

**让镜像直接读 `SecureLink.messages`。** 这不是一个可选项：流是单订阅的，引擎先读了，镜像会把每一帧都拿走、让引擎悄悄饿死。

**在镜像关闭期间缓冲剪贴板变化，开启时回放。** 会让「打开开关」看起来像是找回了关闭期间复制的东西。否决，因为它模仿的是一个 bug 而不是平台：一个没在跑的监听者什么都观察不到，而把陈旧复制回放进一个 Owner Group 是比丢一条更糟的失败。这也正是 `MemorySystemClipboard` 用广播控制器的原因 —— 用会缓冲的控制器恰恰会把这个问题盖住。

**每个对端一个镜像。** 能让每条 Session 拥有自己的状态，单独看更容易推理。否决，因为状态不是按 Session 分的：双设备循环是两个剪贴板的性质，按对端拆开的镜像要么得跨对端检测它、要么检测不到。

**用值的文本做回声抑制。** 这正是镜像服务采用的方案，形式是一段容量 16 的已应用值队列。替代方案 —— 只靠 id 登记表 —— 行不通，因为平台报出来的是一次带文本、不带 id 的**变化**，文本是唯一能拿来比对的东西。代价记在 Consequences 里。

**用 Owner 的密钥对而不是设备 Fingerprint 打标签。** 会让「同一个 Owner」本身就是标签，从而不再需要成员集合。否决，因为在本代码库里 Fingerprint 才是到处用来标识设备的东西，而 Pairing 一次只接纳一台设备 —— Owner 密钥需要被引入、分发和轮换，而 Fingerprint 已经被推导出来、也已经在传了。

**接受任何组内成员打的标签，不论它从哪条 Session 来。** 更宽松，而且能让行为良好的对端做转发。否决：这正是那条夹带通道。组内的一台设备可以把它从组外收到的内容换个标签转发进来，而下游没有任何东西能分辨。

**跨所有来源按 `capturedAt` 排序。** 能解决两台设备几乎同时复制时的先后。否决：设备时钟没有同步，跨来源比较是看起来合理的噪声。

**用一个布尔 `mirroring` 取代三种模式。** 更好持久化，也更好渲染。否决，因为 `Stage` 是真实存在的期待 —— 术语表定义了它 —— 而布尔表达不了「我复制的东西发出去，但要替换我这边的东西之前先问我」。

**镜像也走 `PayloadKind.clipboard` 的 Transfer。** 会给每个被镜像的条目一次接受／校验往返和一张回执。否决，因为 Transfer 的中心是一次用户决定 —— 提议／应答阶段的全部意义就是接收方会被问到 —— 而镜像的定义就是不需要用户动作。让接收方自动应答，机制还在，意义没了。

## Consequences

- **没有任何东西从 socket 造出一个 hub。** 那些本该接受连接、跑握手、构造 `SessionHub` 的平台层还没写，所以这个增量可以从测试和一个无界面 harness 抵达，但到不了 App。`SystemClipboard` 同理：接缝有一个内存实现，没有任何平台实现。
- **镜像没有送达确认。** 它是发后即忘的，被一条死掉的 Session 丢掉的条目既不会重试也不会被报告。对一次镜像复制来说这是对的取舍 —— 值无论如何都还在源剪贴板上 —— 但这是这条路径没有的保证。
- **回声抑制可能吞掉一次真正的重复复制。** 最近 16 个被应用的值按文本记住；在这个窗口内再次复制其中某个值不会被重新镜像。它是良性而非正确：组里本来就已经持有那个一模一样的值，所以观察不到任何损失。这个窗口是一个上界，不是正确性论证。
- **重复条目记 256 条、待处理条目留 8 条。** 超过边界就会忘掉最旧的，所以一条足够迟到的、很旧条目的重复会被第二次应用。
- **后配对的设备什么都收不到。** 没有历史可发：之前的剪贴板是平台的状态，不是这个产品的，任何早于 Session 的复制都不会被回放。
- **现在有两种机制承载剪贴板内容。** 镜像走 `ClipboardMessage`；主动发送走 `PayloadKind.clipboard` 的 Transfer。两者的保证确实不同，但 Transfer 那条路还没有调用者，而两者的边界只存在于这份笔记和一句文档注释里。后续增量应当要么给它一个调用者，要么把它删掉。
- **写这份笔记时发现：对端挂断之后 `SecureLink.isClosed` 是 false。** `_runPump` 在帧流结束时关掉了两个控制器，却没有置 `_closed`，而 `_closed` 只由 `close()` 设置 —— 所以这个字段自己的文档注释「True once this link is closed, from either side」对远端并不成立。更麻烦的是 `_seal` 只检查 `_closed`，所以对端已经走了之后再发送，抛出来的是一个传输层错误，而不是干净地失败。hub 通过从自己的流推导关闭状态绕开了这团混乱，但这个不一致是真实存在的、先于本次改动就有的，而且没有在这里修：把「流结束了」和「close() 被调用过」分开需要一个新标志位，因为若直接把 `_closed` 置真，后面那次 `close()` 会变成空操作并泄漏传输层。
