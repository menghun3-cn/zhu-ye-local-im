# Agent Note: A Pairing runs on its own link, and admits only after both users confirm

Status: implemented

English | [中文](2026-09-30-pairing-by-typed-code.md)

## Problem

上一个增量让设备拥有了可持久化的 Owner 身份，以及一个能开 Session 的 `LinkManager`
——但 Session 是用群密钥认证的，而两台从未谋面的设备并不共享任何群密钥。没有任何东西
能把两个陌生人变成同一个 Owner Group：没有办法在被双方已共同持有的秘密上跑一次握手，
没有办法证明对端就是用户想配对的那台设备，没有办法把群密钥交给新设备，也没有规则说明
第三台设备加入之后这个群到底是什么。后续每一项能力——向局域网里发现的设备发传输、在群内
镜像剪贴板——都依赖这一步先存在。

有两件事让它比看上去更难。短码很短——10 个 Crockford base32 字符，50 bit——因为得有人
从一个屏幕读出来、打进另一个屏幕。而群不是一对：第三台设备加入之后，头两台还得能认出彼此。

## Decision

`PairingService` 拥有整个流程，而配对是一种独立形态的连接，不是「换了个配置的 Session」。

- **配对监听自己的端口**（`defaultPairingPort`，47656），与 Session 端口、发现端口都不同，
  配对结束后这条链路即刻拆除。Session 的 responder 必须先完成认证才知道是谁在拨入，所以
  它只可能接受群密钥；没有密钥的设备必须去别的地方，而「别的地方」是一个不同的 socket，
  不是同一个 socket 上的第二条准入规则。
- **短码是唯一的秘密，且从不传输。** 双方各自调用 `PairingSecret.fromCode`，由同样十个
  字符派生出同样的字节，于是
  [SecureLink](../../architecture/2026-09-29-core-wire-protocol-and-secure-session.md)
  里的握手无需任何东西过线就能完成认证。`PairingSecret.random`——二维码路径——仍是更强的
  选择，尚未实现。
- **`PairAdmitMessage` 把自报的 Fingerprint 从声明变成事实。** 握手只证明对端知道短码；
  握手里的描述符是对端自己挑的。所以每一侧都对一个由双方 Fingerprint（固定顺序）与短认证
  串拼成的上下文签名，连同自己的 Owner 公钥一起发出；接收方要求这把公钥的哈希等于对端自报
  的 Fingerprint，且签名可验证。没有这一步，知道短码的设备——比如已经在群里的那台——可以
  自称成任意身份。
- **`confirm` 是对称的，双方都必须调用。** 每一侧发出 `PairConfirmedMessage` 并等待对端的
  那一条；在双方都确认之前谁也不写任何东西。半配对——一台设备相信自己在一个对端毫不知情的
  群里——比没配对更糟。
- **群密钥在首次配对时派生，加入者则继承。** 双方都没有群密钥时，各自从短码派生——两侧
  同样字节，什么都不传。加入既有群的设备会在密封链路里收到该群的密钥，这正是「加入」不会
  把原有成员切断的原因。而双方各自已有**不同**密钥时无法调和，直接拒绝。
- **名册随准入一起传递。** `PairAdmitMessage` 携带发送方的群成员，接收方在接纳发送方的
  同时一并接纳它们。否则群里的第三台设备只会认识与自己配对的那一台，从而拒绝来自第二台的
  镜像——因为决定谁能镜像的那道闸读的就是这个群。
- **成员关系只增不减。** 名册是某个对端对群的看法，而过期的看法不该有能力撤销用户做过的
  移除，所以 `_commit` 只做添加、从不删除。做过移除的设备重新配对，或者在它落地的设备上
  再移除一次。
- **每台设备同时只开一个邀请**，因为两个活着的短码就是两个活着的秘密、来自两次猜测。
  撤销邀请会让它的 `attempt` 失败而不是悬着，这样等待它的界面不会卡在一个永远不会到来的
  对端上；此后连接进来的对端会被丢弃。

### 那六位数字到底值什么

两个用户都会看到对端的身份和六位数字，并且都要确认。数字由握手派生——所以参与了**本次**
交换的设备才知道它们，而两侧无需传输就能一致。它们**不是**短码之上的第二层保护：知道短码
的对端能完成握手并派生出同样的数字，不知道短码的对端则根本无法完成握手。这一点记录为对
`pairing_secret.dart` 中一处旧注释的更正——那条注释声称这种比对是短码弱点的缓解手段；它
不是，而相信它的读者会在脑子里留下一条并不存在的安全边界。

这一步真正的价值在于：准入始终是一个人的决定，做出决定的那一刻对端身份就在屏幕上。实际
适用的上界是短码的约 50 bit：录制下一次短码配对的人可以离线穷举短码，而在两块屏幕上比对
多少次数字都改变不了这一点。所以短码是没有摄像头的设备上的退路，全熵秘密才是首选路径。

## Alternatives considered

**让配对走正常的 Session 端口，用短码派生的秘密顶替群密钥。** 否决：同一个 socket 上就会
出现两条准入规则，而适用哪一条取决于调用方打算怎么用这条连接。另外 Session 是带着 hub、
传输引擎、剪贴板会话一起交出去的，而配对一个都不要。分开端口让每条准入规则各占一个 socket，
也让「连错地方」变成一次拒绝，而不是一次越权。

**由邀请方生成一个全新的全熵群密钥，密封后发过去。** 否决：它终究还是用短码派生的密钥来
密封，所以恢复了短码的录制者同样能恢复这个密钥。这只会多出一条消息、一个超时和一个失败
模式，而天花板由短码决定，不由派生值的长度决定。

**直接拿 Pairing Secret 当群密钥，不再单独派生。** 否决：同一份字节会同时作为配对链路的
密钥和后续每个 Session 的密钥，于是在一处出现弱点就等于在另一处出现弱点，`SecureLink`
自己的域分离也就被迫身兼两职。`_deriveGroupSecret` 让一次性链路密钥与长期群密钥保持区分。

**从某个已经共享的东西派生群密钥，让加入不需要任何消息。** 否决：两台设备在配对之前唯一
共享的东西就是「什么都没有」。把设备加进一个群就意味着把群密钥交给它，而密封的配对链路
是唯一能安全做到这件事的地方。

**任一侧确认即可自行提交。** 否决：「这边确认、那边取消」是再普通不过的顺序——两个人正
看着两块屏幕——而在第一次确认时就提交，恰好制造出双向规则本要防止的那种半配对状态。

**直接发送邀请方的整张 Known Devices 表，而不是成员 Fingerprint。** 本次增量否决：镜像
闸读的是群成员关系而非 Known Devices 表，所以多出来的别名和地址是没人读的载荷，何况加入
的设备在首次连接时本来就会拿到对端的描述符。

## Consequences

- 应用层只靠 `PairingService` 就能完成配对：`invite` 并展示短码、用输入的短码 `join`、
  把数字给两个用户看、`confirm`。它全程不接触 `Socket`，也不接触 `SecureLink`。
- 配对成功会改动群密钥，从而使任何基于旧密钥构建的 `LinkManager` 或 beacon 失效。
  `changes` 是调用方察觉这件事的方式——发出的 `LocalProfile` 与
  `PairingOutcome.sessionSecret` 是同一个值——而据此重建是调用方的职责，不是服务能替它做的。
- 群靠「增长」达成一致，所以在一台设备上做的移除，可能被带着过期名册来配对的设备还回来。
  在移除流程存在之前这只是理论成本；等它存在时，就需要名册版本号，或者一种能传播的移除。
- `KnownDevice.platform` 来自未签名的握手描述符，所以对端可以虚报自己运行的平台。别名是
  签名过的，平台不是；而没有任何地方用它做决策——只用于显示。
- 就录制握手的攻击者而言，短码的上界约为 50 bit。携带全熵秘密的二维码路径是首选路径，
  尚未实现；在它实现之前，产品提供的就是短码，而它的限制写在 `pairing_secret.dart` 里，
  而不是等人踩出来。
- `lib/core/` 依然没有 Flutter 依赖。整条流程由 `dart test` 在真实 loopback socket 上
  驱动——完整配对、错误短码、身份造假、第三台设备加入既有群、取消，以及一个完成握手后
  谎报身份的对端——见[核心门禁](../testing/2026-09-29-dart-test-as-the-core-gate.md)。
