# Agent Note: 删除对话同时忘记设备

Status: implemented

[English](2026-10-28-hard-delete-conversation.md) | 中文

## Problem

对话列表只有一个破坏性动作，名字叫「删除」，实际执行的是 `clearConversation`：清掉消息
和已读水位，对端的其他一切照旧。设备仍留在 Owner Group、收藏集合、共享剪贴板白名单和
`known` 里，于是它会自己重连、保留剪贴板权限，列表行也会在下次启动或下一个信标时重新
出现。用户删了对话又眼看着设备立刻回来，根本无从判断删除究竟有没有发生。

三件不同的事被塞进同一个词：清空聊天、忘记设备、删除磁盘文件。任何只提供一个按钮的
版本都只能挑其中一件，把另外两件悄悄留下。

另一半问题是文件。粘贴的图片在发送前会写进共享临时目录，而收到的文件、用户选的文件
都是用户自己的。之前没有任何地方记录两者的区别，所以一次删除要么不敢动自己的临时文件，
要么就可能误删用户的文件。

## Decision

列表里的删除现在是硬删除 `deleteConversation`，不再走 `clearConversation`。它在一趟里
拆掉一台设备留在本机上的全部痕迹：

- **在途传输被取消，而不只是隐藏。** `Transfer.cancel` 上移到基类，删除用一次调用就能
  停掉两个方向，并告知对端传输已结束。
- **会话被关闭**：已接入的链路被释放，socket 关闭。
- **消息与已读状态清掉**，且清空后不再写回空文件，而是删掉历史文件。为此新增
  `MessageStore.remove`，由 `ConversationReading.isEmpty` 决定是否该删。
- **设备被忘记**，统一走 `DeviceProfile.forgetDevice`：一次删掉已知设备记录、收藏、
  剪贴板白名单和 Owner Group 成员关系。它们描述的是同一台对端，漏掉任何一个都会留下
  一条主人已不在列表里的权限。
- **该对端的剪贴板记忆被清除**，走 `ClipboardMirror.forgetPeer`：暂存项、已应用列表、
  去重与时序状态，都不再保留；系统剪贴板当前内容不动。
- **只删除本应用自己创建的临时文件。** 粘贴图片通过 `MessageRecord` 与 `TransferView`
  携带 `appOwned`，删除拿走的恰好是自己写的那几个文件。

Owner Group 密钥刻意保留：组内其他设备还持有它，轮换密钥是另一件事。对端不会收到任何
通知，也不写持久忽略名单：它随时可能被重新发现并重新配对，从而开始一段全新的空对话。

`clearConversation` 保留不变，也更轻：对话内三点菜单依然只清空消息和已读状态，不忘记
设备、不关闭会话、不碰草稿。

## Consequences

- 从列表删除确实移除了设备：它离开组和剪贴板白名单，会话结束。
- 被删设备可以自己回来，因为本地链路的重配对是自动的；它回来时是一段新的空对话。
- 收到的文件、用户发送的文件、系统剪贴板当前内容，都在删除后保留。
- 已发出的粘贴图片会被清理；旧版本产生的粘贴图片没有 `appOwned` 标记，不做猜测删除。
- 页面本地的 `_deletedPeers` 集合已移除，列表所见即控制器当下所知。
- 未发送的草稿、暂存附件和文本选择不会跨过删除保留，因为选择清空后对话视图被卸载。

## Alternatives considered

**写持久忽略名单，让被删设备无法重新配对。** 否决：本产品的准入边界始终是本地链路，再
加一层不可见的信任会让「靠重配对回来」和「靠信标回来」行为不一致，而没有任何界面解释
这一点。

**通知对端解除配对，并轮换组密钥。** 否决：密钥由组内每个成员共享，因一台设备的决定
轮换它会牵连整个组并断开无关设备。忘记一个对端是本机决定，就按本机决定记录。

**按路径或文件名猜哪些是临时文件。** 否决：粘贴路径写进的是其他程序也会用的临时目录，
删掉一个不是自己创建的文件，远比留下一个残余文件更糟。标记随记录一起走。

**保留单按钮删除，只补一句确认文案。** 否决：按钮本来就在，问题出在它的名字。把复合
动作讲清楚并照着名字去做才是修复；只改措辞，设备依然留在组里。
