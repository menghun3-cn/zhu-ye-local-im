# Agent Note: Offer, stream, verify — and make an interrupted transfer resumable

Status: implemented

[English](2026-09-29-transfer-engine-over-a-session.md) | 中文

## Problem

握手证明对端知道 Pairing Secret，并给两端一条私密通道。但它没说沿这条通道走的字节是否到达、是否完整、是否就是本来要发的那些字节。Session 是一根管；传输是一个承诺，得有东西去兑现它。

在这个产品里，这个承诺有具体的形状。用户把五个文件拖到一个设备名上，或者复制一段文字并期待它出现在另一台机器上。在接收侧，同一个 Wi-Fi 上的陌生人是可以**提议**东西的；若接收方在主人同意之前就开始写盘，那就是被一个素不相识的人塞满了磁盘。在发送侧，「发出去了」不等于「到达了」：发送方对「文件在对面完好」这件事所掌握的证据，并不比握手给的多。

有两条平台事实让这不是纸上问题。Android 拿到的是一个有六小时 `dataSync` 预算的前台服务，所以传输被中断是常态而非例外（见 `docs/android-background-constraints.md`）。而 socket 写入本身不是承诺：`Socket.add` 在任何一个字节离开本机之前就返回了，所以「载荷已到达」的唯一证据是接收方说出来。

## Decision

传输位于 `lib/core/transfer/`，运行在 Session 之上，分三个阶段：

1. **提议（Offer）。** 发送方声明想发什么 —— 种类、条目、大小，以及每个条目的 SHA-256 —— 一个字节都不动。
2. **答复（Answer）。** 接收方列出它接受的条目，以及每个条目它已持有多少字节。凡未列出的即被拒绝。
3. **传输与校验。** 发送方按切片把已接受的条目发过去，说一句 `complete`，接收方回以它实际哈希校验过的结果。到这时，传输才算结束。

- `transfer.dart` —— 共用词汇：`TransferState`、`TransferProgress`、密封的 `TransferOutcome` 家族，以及基类 `Transfer`。
- `byte_source.dart` / `payload_sink.dart` —— 两个存储接缝，各有一个内存实现和一个文件实现。
- `outgoing_transfer.dart` / `incoming_transfer.dart` —— 两个状态机。
- `transfer_channel.dart` —— 盖在 Session 之上的接缝，使状态机无需 socket、无需握手即可被驱动。
- `transfer_engine.dart` —— 路由层：每个 Session 一个引擎、一个工作器，以及各项上限。
- `transfer_limits.dart` —— 设备在「还没问任何人」之前就会拒绝的东西。

### 摘要是字节出发之前许下的承诺

Offer 携带每个条目的 SHA-256，由发送方在**提议之前**把条目完整读一遍算出来。接收方对「它实际写下的字节」做哈希，把自己的摘要回传，发送方再做比对。两端各自独立哈希，谁也不把自己的数字当成对方的事实。

这是完整性校验，不是安全边界。第三方改不了飞行中的字节 —— ChaCha20-Poly1305 已经覆盖了这一点。摘要抓到的是其余全部：在 Offer 之后、读取之前被编辑过的文件；提前结束的数据源；写错 offset 的 sink；写满的磁盘；以及实现单纯就是坏了的那一端。这些才是真正会发生的故障，而它们没有一个是记录层看得见的。

### 续传位置来自 sink，而不是来自调用方

`IncomingTransfer.accept` 接收 sink，并从 `PayloadSink.bytesWritten` 推导续传偏移。这里**故意没有**单独的 `resumeOffsets` 参数：sink 本身就是那个知道盘上有多少字节的东西，而在它旁边再传一个数字，就是第二个可能与第一个不一致的事实来源。把上次中断留下的半截文件交出去，就是续传的全部 API。

带摘要的前缀不是漏洞。sink 会把它收养的字节与之后收到的字节一起哈希 —— 方式是在打开时把前缀先读一遍 —— 所以最终摘要覆盖的是整个条目。接收方无法声称自己持有一个并不属于该条目的前缀；而如果两次尝试之间文件被换掉了，末尾的校验会失败，而不是悄悄拼出一个文件。

### 帧按到达顺序逐个路由

`complete` 的意思是「每个条目的每个字节都已经在线上了」，所以它只能在它之前那些切片**确实写入之后**才被处理。Session 把控制消息与载荷切片交给两条不同的流，因此引擎把两者汇入一个队列，一次只排空一个任务。

这不是为了整洁。两条并发的循环各读一条流，会让 `complete` 超车一个仍在写盘的切片 —— 切片的 `onData` 先启动，随后 await 一次文件写入，而消息的 `onData` 就在这个空档里跑完。接收方于是看到一个偏短的条目，把一次「字节全都到了」的传输判为失败，而发送方收到一份针对好文件的 `corrupt` 报告。内存 sink 恰好是同步写入，把这个竞态盖住了；文件 sink 不会，测试套件就是这样抓到它的。

代价是同一条 Session 上一次慢写入会拖住一条无关消息。一条 Session 承载的是两台设备之间的一次对话，所以这比另一种选择便宜。

### 上限在询问 App 之前强制执行

`TransferLimits.violationOf` 对每一个 Offer 运行。没列条目的、条目过多的、单个条目超过 `maxItemBytes` 的、总量超过 `maxTotalBytes` 的、条目 id 重复或为空的、摘要格式不对的，以及声明大小与文本实际长度不符的 Offer，都会以 `refused` 拒绝，根本不会到达 App。Offer 是对端的声明，所以检查针对的是这份声明。

形状规则故意定得很死。文件条目必须带摘要 —— 没有摘要，接收方就无从校验，这次拷贝也就不带任何保证。text 或 clipboard 的 Offer 必须且只能列一个条目，且其大小等于正文的 UTF-8 长度，因为那份正文走在 Offer 里，它的大小是两端都能算出来的事实，而不是一件需要协商的事。

两个超时只属于发送方，而且接收方那边完全没有定时器。一直收不到回音的发送方终究得停止等待；而正在写的接收方手上有一个用户可以取消的传输，给它加超时只会把一条慢链路变成一次无谓的失败。

### 引擎只做路由，不做决定

`TransferEngine` 只拒绝上限不允许的东西，其余一概交给 `incoming` 上的监听者。一个 Offer 是否受欢迎是 App 的判断 —— 这个问题需要用户、需要一个目标目录，可能还需要一次询问。指称「引擎并未在跑」的传输的消息，会经 `onNotice` 记一笔后被丢弃：一个过期或恶意的 id 不该能把引擎打垮，但本侧的一个 bug 也不该无声无息。

## 发现：一个已关闭的 Session 会把自己的泵打崩

写「session dies 时把传输一起带走」这个用例时，暴露了上一增量里的一个缺陷。`SecureLink.close()` 会先结束两个流控制器，**然后**才关传输，于是排在关闭动作之后的帧仍然会被投递给一个已经完成的控制器。由此产生的 `StateError` 又被泵自己的错误处理捕获，而错误处理试图在同一个已关闭的控制器上把它报出去 —— 那次第二次、无人接管的抛出才是最终逃出来的东西。

`_runPump` 现在既在投递前检查 `_closed`，也在解密之后再查一次；而一旦链路已关闭，错误路径就安静返回。一条被有意拆掉的链路没有东西需要上报。

## Alternatives considered

**直接流字节，跳过 Offer。** 发送方像 socket 一样开始写。拒绝：接收方必须先收下才能拒绝，发送方也无法说明要来多少，而磁盘已满的接收方要等字节已经上线之后才知道。这次往返正是「接收方的用户还能被问一句」的前提。

**把摘要放在字节之后发，当作对到货内容的检查。** 拒绝：攻击者或坏掉的对端可以就它实际发的东西算一个摘要，于是这个检查只证明了内部自洽。承诺必须先于它所承诺的内容，否则它就不是承诺。

**只校验大小，不用摘要。** 能抓截断，抓不到损坏与替换 —— 载荷里翻一个比特就能过。拒绝：它省下一次哈希，换来的保证却实质性更弱。

**让发送方自己记续传偏移。** 发送方维护一份「它认为接收方有多少」的账本，并据此续传。拒绝：只有接收方知道它盘上究竟有什么。发送方账本是第二个事实来源，并且恰好在关键时候过期 —— 崩溃、被杀、写入失败之后。

**只信接收方的校验。** 接收方哈希完说一声「没问题」，发送方就相信。拒绝：如果出错的一方正是接收方，它的抱怨毫无用处；而一个坏掉的接收方报成功，与一个好的接收方无法区分。两端都哈希，然后把两个答案对比。

**每个条目一个 Offer。** 一次拖入五个文件就变成五次传输。拒绝，因为它把问题往上挪：一个手势换来五次决策、五份部分结果，以及一个 UI 不得不凭空发明、而线上格式本就有的分组。

**用序号而不是字节偏移。** 拒绝：offset 是自描述的，也正是中断之后还能续传的原因。序号需要一份持久化的映射来说明每个序号当初指什么，而那恰恰是「崩溃后不存在」的状态 —— 可这个机制存在的意义就是从那场崩溃里恢复。

**把小载荷塞进 Offer 里。** 很诱人，文本本来就是这么走的。但对文件拒绝：Offer 是一个 control 帧，受 `maxFrameBytes` 限制，被当作单个 JSON 对象整体解码并驻留内存。把批量数据塞进去会把每次传输封在 16 MiB，并且在路上给字节做 base64。

**写临时文件、完成时改名。** 未被拒绝 —— 只是推迟。这是避免在最终文件名下留下半截文件的正确做法，而它属于创建 sink 的那一方，因为改名是文件系统层面的决定，而 sink 有意对最终文件名一无所知。记在 Consequences 里，让这个缺口是显式的而不是被默认掉的。

## Consequences

- **没有 socket 背压。** 发送方逐个 await 加密（这会让出执行权），但 `ByteTransport.add` 从不阻塞，所以快的源加慢的链路可以把飞行中的余量堆在内存里。`maxTotalBytes` 给了它一个界 —— 每个 Offer 8 GiB，是个真实的界，但不算小。要真正关掉它需要基于信用的流控窗口，那是一次线上格式变更。
- **传输不跨进程重启存活。** 引擎的状态在内存里，所以被中断的传输是被判失败，而不是被挂起。**字节**是存活的：文件 sink 留下半截文件，针对它新建一次传输就会从停在的地方续上。没有任何东西会自动重新驱动这件事，而在 Android 上，「自动重新驱动」正是那六小时前台服务预算存在的意义。
- **sink 就地写盘**，所以一次被中断的传输会在最终路径上留下半截文件。引用计数与改名是调用方的事。
- **目前还没有任何东西会创建引擎。** 那个应该开监听 socket、跑握手、构造 `SecureLinkChannel` 的 Windows/Android 层还没写，所以这一增量可以从测试和一个无头验收装置触达，还触达不到 App。
- **`transferChunkBytes` 是协议常量**，不是调参旋钮：64 KiB 让一个切片远低于帧上限，同时把分帧与 AEAD 开销压在千分之一以下。改它就是改线上格式，所以将来若要做窗口协商，就得把它纳入版本控制。
- **一次 Transfer 是单向且一次性的。** 没有重启、没有重新协商，也无法向一个正在跑的 Transfer 追加条目。要表达别的东西，就新建一次传输；传输 id 是随机的，所以两台设备同时开传也不会撞车。
