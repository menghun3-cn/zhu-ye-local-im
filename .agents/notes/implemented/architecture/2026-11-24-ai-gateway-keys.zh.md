# Agent Note: 网关以一组命名的客户端密钥鉴权，而不是单个令牌

Status: implemented

[English](2026-11-24-ai-gateway-keys.md) | 中文

> 修正
> [局域网网关与供应商草稿](2026-11-24-ai-gateway-lan-and-draft.zh.md)：
> 单个生成的 bearer 令牌变为可维护的命名密钥列表，每个客户端一个。

## Problem

网关唯一的凭据是一个 `lt-ai-` 令牌，所有调用方共用。两个实际缺口立刻
显现：每个客户端都得拿到**同一个**秘密，因此无法分辨哪个工具花掉了
配额——请求日志能说哪个模型服务了请求，却说不出哪个客户端发起的；
而令牌完全没有生命周期：生成一次、展示一次，轮换或吊销的唯一办法是
手工删文件。

## Decision

**`gateway_keys.json` 保存密钥环；`gateway_token` 迁移进来。**
`AiGatewayKeyStore`（`lib/core/ai/gateway_keys.dart`）在
`providers.json` 旁持久化 `[{name, secret, created_at}]`。首次打开时
播种一个名为 `default` 的密钥：秘密取旧 `gateway_token` 文件的内容
（文件存在时）——所有已配置的客户端零重新粘贴继续工作——否则生成
新的 `sk-<随机>`。密钥明文存储，与它替代的令牌文件一致：它们是按
设计要展示给用户的 bearer 凭据，封装只是把明文挪到别处。

**损坏是错误，绝不是轮换。** `load()` 在文件存在但无法解析时抛出
`AiGatewayKeyStoreException`——此前的 `catch → []` 会把损坏读成
"没有密钥"，随后 `loadOrCreate` 铸造新的 `default`，让所有已配置客
户端静默失联。`loadOrCreate` 现在只在文件不存在时播种：已存在的文
件原样返回，即使是空列表，因此被刻意清空的密钥环不会复活
`default`。`AiRuntime.open` 吞掉该异常让 AI 栈其余部分照常启动；
网关每请求的 `keySource` 会重新抛出（请求失败而不是对轮换后的凭据
放行），设置界面在文件修复前显示"密钥文件已损坏"提示。

**网关接受密钥环中的任意密钥。** `AiGateway` 接收 `keySource` 回调，
每个请求重新读取，因此在设置里增删密钥即时生效——不需要重绑端口、
不需要重启。匹配到的密钥的**名称**（永远不是秘密本身）传给
`AiRouter.chat(clientKey:)`，盖在 `AiRequestRecord` 上；请求日志的
按密钥用量统计于是变成对 `record.key` 的一次分组计数，密钥出现之
前的旧记录归入 `default`。

**认证遵循 RFC 7235，且不泄漏内部信息。** `Bearer` scheme 按大小写
不敏感匹配（`bearer`、`BEARER`、`Bearer` 均可认证；其它 scheme 不
行），密钥比较为常数时间——对 UTF-8 字节做异或累积，局域网下 token
是唯一凭据，响应时序不应泄漏内容或长度。处理器异常统一回答通用
的 `internal gateway error` / `stream interrupted`，而不是把异常
文本回显给调用方。

**界面是列表，不是单个输入框。** 网关 tab 把每个密钥显示为一行卡
片——名称、眼睛切换的掩码秘密、复制、按密钥用量
（`{requests} 个请求 · {tokens} token`，来自请求日志）和删除。"
添加网关密钥"展开一行内联表单：名称输入框（hint 展示约定，例如
"笔记本"）和可选的秘密输入框——留空则生成 `sk-…`——带创建/取消。
最后一个密钥不能删除：零凭据的网关会拒绝所有调用方，那是一扇没钥
匙的锁门。重名或重秘密的密钥被 toast 拒绝。删除密钥前先弹确认——
吊销凭据与删除供应商同等分量；创建按钮在名称非空前保持禁用，
空名称不再是一次静默的无操作。掩码秘密按字符数显示圆点而非
固定数量，自定义密钥的长度得以如实呈现。

## Consequences

- 每个客户端拥有独立的可吊销凭据；按客户端用量统计是分组计数，
  不是新埋点。
- `gateway_token` 只剩迁移来源的角色——新装机不再写它。
- 新密钥不再用旧的 `lt-ai-` 前缀（改用 `sk-` 前缀，与 magpie 的约定
  一致）；迁移来的 `default` 密钥保留原有秘密，前缀照旧。
- 密钥比较对 UTF-8 字节做常数时间累积——任何密钥环规模下成本都
  可忽略，而 LAN 模式让时序成为一个（虽小但真实的）信号。
- `gateway_keys.json` 损坏时网关拒绝所有请求直到文件修复——这是
  诚实的失败方式，好过静默轮换所有客户端依赖的凭据。

## Alternatives considered

- **单令牌加"重新生成"按钮。** 否决：它会同时轮换**所有**客户端
  ——恰恰是你拿不到其中一台笔记本时无法安全执行的操作。
- **像供应商 API 密钥一样用 `secrets.key` 封装每个密钥。** 否决：
  这些秘密的用途就是粘贴进别的工具，界面必须能展示；封装并不能比
  `providers.json` 旁的明文文件多买到任何东西。
- **迁移时删除 `gateway_token`。** 否决：密钥播种后该文件无害，
  保留它还能让回退版本找到自己的凭据。
