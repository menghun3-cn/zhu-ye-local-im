## 1. Multicast across subnets

**mDNS is link-local by design, not a routing limitation.** RFC 6762 §3: *"any FQDN ending in `.local.` is link-local, and names within this domain are meaningful only on the link where they originate"* — analogous to 169.254/16. Queries **MUST** go to `224.0.0.251` / `FF02::FB`. §11 ("Source Address Check") requires responses be sent from the source address, and the spec assumes a single link. ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.txt)) SSDP/UPnP is the same story — link-scoped multicast.

**What is required to cross a router** (any one of):
- **mDNS reflector/repeater** — Avahi's `[REFLECTOR] enable-reflector=yes`: *"avahi-daemon will reflect incoming mDNS requests to all local network interfaces, effectively allowing clients to browse mDNS/DNS-SD services on all networks connected to the gateway… some functionality is lost (specifically the unicast reply bit)."* Also `reflect-ipv` (v4↔v6, "usually not recommended") and `reflect-filters` (allowlist by service name). Warning in the same man page: *"Make sure to not run multiple reflectors between the same networks, this might cause them to play Ping Pong with mDNS packets."* ([avahi-daemon.conf(5)](https://man.archlinux.org/man/avahi-daemon.conf.5.en))
- **IGMP proxy / multicast forwarding** on the router — required because 224.0.0.251 is link-scoped and not forwarded by default.
- Apple's own Bonjour has **no** built-in cross-subnet bridge; Apple's documented answer for multi-link service discovery is **unicast DNS-SD** (RFC 6763 §1: DNS-SD works over conventional unicast DNS with a normal DNS server), which is why Bonjour supports "wide-area" browsing domains. ([RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.txt))

**What AP/client isolation breaks:** it blocks *all* peer-to-peer frames between wireless clients on the same AP, not just multicast — so discovery *and* the subsequent unicast TCP transfer both fail. LocalSend documents this directly: *"Make sure to disable AP-Isolation on your router. If it is enabled, connections between devices are forbidden."* and *"some routers may have it enabled (especially guest networks)."* ([LocalSend README](https://github.com/localsend/localsend)) Warpinator likewise requires the same subnet (below).

## 3. Clipboard constraints, per platform

### Android
`ClipboardService.clipboardAccessAllowed()` gates `OP_READ_CLIPBOARD`. Read is allowed only if one of: holds `READ_CLIPBOARD_IN_BACKGROUND`; **is the default IME** (package compared against `Settings.Secure.DEFAULT_INPUT_METHOD`); the UID is focused (default or focused virtual device); holds `INTERNAL_SYSTEM_WINDOW` **and** has window focus (SystemUI); is the Content Capture service (`BIND_CONTENT_CAPTURE_SERVICE`); is the Augmented Autofill service; or is a privileged VirtualDevice owner. **Writing is unconditionally allowed** (`OP_WRITE_CLIPBOARD` → `allowed = true`). ([AOSP ClipboardService.java](https://cdn.jsdelivr.net/gh/aosp-mirror/platform_frameworks_base@master/services/core/java/com/android/server/clipboard/ClipboardService.java))

`ClipboardManager.OnPrimaryClipChangedListener` exists via `addPrimaryClipChangedListener`, but AOSP re-checks `clipboardAccessAllowed` per listener in `sendClipChangedBroadcast()`, so an unfocused/background listener is **not dispatched**. There is **no** public background clipboard-listener API. **[unverified negative for 14/15/16]**

Android 13 (API 33) copied-content preview: SystemUI's `ClipboardOverlayController`, `CLIPBOARD_DEFAULT_TIMEOUT_MILLIS = 6000`, renders asterisks when the clip is marked sensitive. SystemUI-owned — **no app-facing API to suppress it**. A separate access toast (`showAccessNotificationLocked`, "pasted from clipboard") fires once per clip per UID unless the reader is the clip owner, the default IME, ContentCapture, Autofill, holds `SUPPRESS_CLIPBOARD_ACCESS_NOTIFICATION`, or is the VirtualDevice owner. Auto-clear: `DEFAULT_CLIPBOARD_TIMEOUT_MILLIS = 3600000` (1 h), controlled by DeviceConfig namespace `clipboard` (`auto_clear_enabled`, `auto_clear_timeout`, `show_access_notifications`). `ClipDescription.EXTRA_IS_SENSITIVE` = `"android.content.extra.IS_SENSITIVE"` — documented as a *rendering hint* that *"does not change clipboard behavior or add additional security."*

### iOS / iPadOS
`UIPasteboard.changeCount` increments on add/modify/remove, posts `changedNotification`/`removedNotification`, is updated on app reactivation if another app changed the pasteboard, and **resets to 0 on reboot**. ([changeCount](https://developer.apple.com/documentation/uikit/uipasteboard/changecount))

iOS 14+ notifies the user when an app reads general-pasteboard content originating in a **different** app. iOS 16+ makes programmatic pasting (`UIPasteboard.general.string`) raise an **Allow Paste** alert; `UIPasteControl` (iOS 16+) pastes **without** a prompt, as does `UIPasteConfiguration`. Prompt-free reads: `hasStrings`/`hasImages`/`hasURLs`/`hasColors`, `numberOfItems`, `types`, and `detectPatternsForPatterns:completionHandler:` (iOS 14+) which *"only gives an indication… doesn't allow the app to access the contents, [so] the system doesn't notify the user"* — whereas `detectValuesForPatterns:` does read contents and does prompt. Named pasteboards shared within a Team ID avoid the general-pasteboard prompt. **There is no background clipboard-monitoring mode**; a backgrounded app cannot present the prompt. **[unverified negative]**

### Windows
`AddClipboardFormatListener(hwnd)` → `WM_CLIPBOARDUPDATE` (0x031D), Vista+; `RemoveClipboardFormatListener` to detach. A **message-only window** works for a background app. `GetClipboardSequenceNumber()` returns the sequence number for the current window station. `SetClipboardViewer`/`WM_DRAWCLIPBOARD` are legacy — the chain *"can be broken by an application"*; new apps should use the format listener or sequence number. ([Clipboard overview](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard))

### macOS
`NSPasteboard.changeCount` + `NSPasteboard.general`. **macOS 15.4+** adds `NSPasteboard.AccessBehavior` = `.default` / `.ask` / `.alwaysAllow` / `.alwaysDeny` with an `accessBehavior` property: the general pasteboard defaults to **ask on programmatic access**, other pasteboards default to always-allow. `.alwaysDeny` still permits user-originated paste without notification. ([AccessBehavior](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum)) App Sandbox entitlement implications **[unverified]**.

### Linux
**X11:** the clipboard is a selection owned by a client; any client can request or own it; contents are lost when the owner exits absent a clipboard manager. No permission model. **Wayland:** core `wl_data_device` exposes the selection only to the **focused** client, so background reads are impossible. `wlr-data-control-unstable-v1` (`zwlr_data_control_manager_v1`, v2) lets a "privileged client" manage selections (`data_offer`, `selection`, `set_selection`, `primary_selection`, per-seat) — but is **explicitly deprecated**: *"This protocol is deprecated and not intended for production use. For clipboard management, use the ext-data-control-v1 protocol."* ([wlr-data-control](https://wayland.app/protocols/wlr-data-control-unstable-v1)) `ext-data-control-v1` is in wayland-protocols **staging**. Compositor support for either varies **[unverified]**. `wl-clipboard` provides `wl-copy`/`wl-paste`, including `wl-paste --watch`.

## 4. Platform networking / permission gotchas

### iOS 14+ Local Network Privacy
Governs *"local network operations"*. **Requires** `NSLocalNetworkUsageDescription` (iOS 14+/macOS 11+) — Apple: *"Any app that uses the local network, directly or indirectly, should include this description. This includes apps that use Bonjour… as well as direct unicast or multicast connections to local hosts."* ([NSLocalNetworkUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nslocalnetworkusagedescription)) Bonjour register/browse/resolve all require it, and if you register or browse specific service types you **must** also list them in `NSBonjourServices`. Three states: Undetermined → Allowed / Denied; user-configurable in Settings > Privacy & Security > Local Network. **MDM cannot configure it.** iOS additionally requires the **`com.apple.developer.networking.multicast`** entitlement to send/receive multicast or broadcast, to work with arbitrary Bonjour service types, or to browse all advertised service types — *"The multicast entitlement isn't required on macOS."* macOS gained local network privacy only in **macOS 15**.

Critically: **listening for/accepting incoming TCP and receiving incoming UDP unicast do NOT require local network access; making an outgoing TCP connection, sending unicast/multicast/broadcast UDP, and *receiving* multicast/broadcast DO.** So a sender always needs the permission, while a pure receiver may not. On first operation the system *"may deny the operation immediately, before the user has responded to the alert"* — Apple recommends `NWConnection` or `URLSession.waitsForConnectivity` with retry logic, otherwise you get `NWPath.UnsatisfiedReason.localNetworkDenied`. ([TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy))

### Android
Multicast receive requires `WifiManager.MulticastLock` (acquire/release around the receive window) plus `CHANGE_WIFI_MULTICAST_STATE`; `nsd` documents exactly these. **Android 17 (API 37) blocks local network access by default**: apps targeting 37+ must declare and request the `ACCESS_LOCAL_NETWORK` runtime permission, and *"any attempt to connect to a local IP address without the required permission fails and throws a `SocketException`"* because Dart sockets cannot display an Android prompt. You can opt in to test on Android 16 (API 36). ([Flutter: Request local network permissions on Android](https://docs.flutter.dev/platform-integration/android/local-network-permission), [Android local network permission](https://developer.android.com/privacy-and-security/local-network-permission)) Android 13+ requires `NEARBY_WIFI_DEVICES` for Wi-Fi P2P-style discovery. Android 14+ foreground-service `dataSync` type restrictions **[unverified — developer.android.com was unreachable; the page exists at `/develop/background-work/services/fgs/service-types`]**.

### Windows
Windows Defender Firewall is **on by default**, default behavior: *"block all incoming traffic, unless solicited or matching a rule; allow all outgoing traffic."* Three profiles (domain / private / public); *"public" is the default for unidentified networks*. A Flutter desktop app binding a listening socket therefore triggers a firewall prompt on first run, and on a network classified Public the app may be blocked unless a rule is added or the network is reclassified (`Set-NetConnectionProfile`). LocalSend documents this: *"Make sure to configure your network as a 'private' network. Windows might be more restrictive when the network is configured as public."* ([Windows Firewall overview](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/), [LocalSend](https://github.com/localsend/localsend))

### macOS
Flutter macOS apps are **sandboxed with App Sandbox by default**. Outbound networking needs `com.apple.security.network.client`; without it you get `SocketException: Connection failed (OS Error: Operation not permitted, errno = 1)`. **`com.apple.security.network.server` (incoming connections) is enabled by default only for debug and profile builds** — *"If you need to allow incoming network requests in your application, you must add the `com.apple.security.network.server` entitlement to `Runner-Release.entitlements` as well, otherwise your application will work correctly for debug or profile testing, but will fail with release builds."* Hardened Runtime (needed for notarization outside the App Store) may require additional entitlements. ([Flutter: Building macOS apps](https://docs.flutter.dev/platform-integration/macos/building))

### LocalSend architecture (it is Flutter)
Multi-language monorepo: a **Flutter app** (`app/`) on top of a **Rust protocol core** (`packages/core`: protocol, HTTP server/client, crypto, WebRTC, no Flutter dependency). Dart↔Rust via `flutter_rust_bridge`; heavy networking **never runs on the main isolate** — child isolates for HTTP scan discovery, multicast discovery, HTTP upload and HTTP server, driven by typed isolate actions. State management is **Refena**, not Riverpod; models are `dart_mappable` + `freezed`. The `server/` crate is a separate **Axum WebSocket signaling server** for WebRTC (`/v1/ws`). Protocol **v2.2** is current (`v1.md` and a `v3/` draft exist). Multicast is **announce-only** in Rust: one socket per interface IPv4 address, loopback left on so same-host instances see each other, own messages dropped by fingerprint; responses come back over HTTP as a unicast `register`. TLS uses per-device on-the-fly certs with mandatory client certs; only one upload session is active at a time, with cancellation via drop guards. ([AGENTS.md](https://github.com/localsend/localsend/blob/main/AGENTS.md), [protocol v2.2](https://github.com/localsend/protocol))

## 6. Transfer protocol mechanics

**LocalSend (v2.2).** REST/HTTPS on port 53317. `POST /api/localsend/v2/register` (two-way discovery) → `POST /api/localsend/v2/prepare-upload` (metadata only; receiver accepts/partially accepts/rejects; `?pin=123456` if a PIN is required) → `POST /api/localsend/v2/upload?sessionId=&fileId=&token=` (raw binary body; *"This route can be called in parallel"*) → `POST /api/localsend/v2/cancel?sessionId=`. Reverse/download flow for browser receivers: `POST /api/localsend/v2/prepare-download` then `GET /api/localsend/v2/download`. `GET /api/localsend/v2/info` is debug-only. Error codes: 204 (no files needed), 400, 401 (PIN required/invalid), 403 (rejected), 409 (blocked by another session), 422 (**checksum mismatch**, added in 2.2), 429 (too many requests), 500. Changelog: **2.1** added the `pin` query parameter, the 401/429 codes, and an optional per-file `metadata` object; **2.2** added 422. Files carry `id`, `fileName`, `size`, `fileType`, `sha256`, `preview`, `metadata{modified,accessed}`. The receiver verifies `sha256` and returns 422 on mismatch. **Encryption:** per-device on-the-fly TLS cert; fingerprint = SHA-256 of the cert (a random string when encryption is off); mandatory client certs with peer identity = SHA-256 of the client cert DER; `Register` is not emitted when a payload's claimed fingerprint disagrees with the cert. **Large files / resumability:** LocalSend streams (raw body per file, `"can be called in parallel"`); **resumability is not part of the protocol** — no range/offset API appears in v2.2. **[unverified whether the app implements app-level resume]** The v3 draft adds a **WebRTC data-channel** transport with nonce exchange, token exchange, PIN negotiation, file send/receive headers, **16 KiB chunks**, and explicit delimiters — still a draft. ([protocol README + CHANGELOG](https://github.com/localsend/protocol), [v3/webrtc-diagram.mermaid](https://github.com/localsend/protocol/tree/main/v3))

**Others.** Syncthing uses block-level hashing (BLAKE2b) with an index database, so transfers are inherently resumable and multi-source; optional per-folder password encryption for untrusted devices. KDE Connect uses TLS with cert pinning for trusted devices and `payloadSize: -1` for unknown-length streams. PairDrop/Snapdrop are WebRTC with TURN relay for NATed peers. Warpinator uses gRPC with optional compression. Deskreen is a WebRTC screen stream.

**Protocol-version numbers documented:** LocalSend protocol **v2.2** (v1/v2/v3 drafts); KDE Connect protocol **≥8** required; Syncthing config **version 37**.
